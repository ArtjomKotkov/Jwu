# jwu: есть ли фикс в версии клиента

Если не подтверждены проект и правила, загрузи `skill_view(name="jwu-session-init")` и выполни проверку. Используй только подтверждённый MCP jwu с `workspace=slug` или `terminal(workdir=<проект>)`: `jwu --workspace SLUG …`. Динамические аргументы передавай через argv или экранируй каждый отдельно (`shlex.quote`), включая glob. Для проверки по dev-панели нужен провайдер `jira`; в `local` и `github` не вызывай этот инструмент, не выдавай поиск по коммитам за подтверждение dev-панелью.

- Возьми точный ключ задачи и ветку/версию клиента; сопоставь версию с веткой по правилам контура, при неоднозначности уточни. Проверь, что нужный клон есть в `paths` (`jwu_workspace_paths` / `workspace paths`). Если нет, предложи `jwu-workspace-setup`, ничего не подключай сам.
- `jwu_task_branches(key, branch_patterns=None)` или `jwu --workspace SLUG task KEY --branches --json`, с повторяемым `--branch-pattern 'release/*'` при явном шаблоне. Только чтение: не fetch. Дефолт: `release/*`, `release-*`, `releases/*`, `hotfix/*`, `support/*`, `master`, `main`, `develop`.
- `commits` и `prs` — сведения dev-панели; в `repos` по каждому клону `reached` значит все коммиты, `partial` — только часть (явно скажи, что фикс неполный), `missing` — среди проверенных кандидатов коммитов нет. Ответь прежде всего про спрошенную ветку, не выгружай всё. Открытый PR ещё не доставил фикс своим мержем; упомяни это, не отменяя подтверждённую доставку другим путём.
- `dev_ok: false` или пустой `commits` — не доказательство отсутствия. Предложи поиск по `git log --grep KEY` в подтверждённом клоне. Если нужной ветки совсем нет, клон может быть старым: попроси пользователя обновить его и повтори проверку. Не приравнивай непроверенную ветку к `missing`.

Ответ в задаче — отдельно через `jwu-task-comment`; разбор сборки — `jwu-build-failure`.
