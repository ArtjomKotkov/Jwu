# jwu: продолжить работу в Hermes

## Вход по поручению

Бриф с ключом строки, но без подтверждённой работы → **jwu-start-job**, раздел «Вход по поручению с доски». С точным ID после проверки папки и правил через **jwu-session-init** прочитай `job show ID --json`: сверь контур, цель, полный PR и владение. Продолжай свою работу либо явно переданную без параллельного владельца; при чужом или неясном владельце остановись, не присваивай работу. `paused`, `done`, `cancelled` не дают права создать дубль или молча вернуть статус `active`. Восстанови журнал и остаток; возобновляй только по явному решению об этом цикле, затем перечитай статус. Запрос состояния — только чтение. При прямом вызове без брифа выбирай работу по правилам ниже.

При продолжении работы с изменениями, в том числе после возврата QA, сначала сверь весь согласованный план и проверки с журналом, новыми замечаниями и фактическим состоянием ресурсов. Нет плана или изменились цель, объём, порядок или условия проверки — примени «От анализа до первой правки» из **jwu-start-job**: согласуй и запиши весь актуальный план, не только разницу. Неизменный план заново не согласовывай. Только затем, если это нужно для очередного согласованного шага, восстанавливай копию или стенд.

После каждой фазы примени проверку «перед завершением каждого хода» из `jwu-session-init`. Например, после согласованного применения патча не заканчивай на «тесты не запускал»: если тесты требуют отдельного разрешения, сразу вызови `clarify` с рекомендацией и вариантом паузы.

Сначала `skill_view` → `jwu-session-init`, если не подтверждены папка, `source=cwd`, `slug` и правила. Не пиши при неподтверждённой привязке. Перед кодом прочитай правила нужных тегов (`jwu_rules(tag=…)` / `rules --tag TAG --json`); ⛔ обязательны. MCP только при совпадении контура и cwd по guard; указывай `workspace=<slug>` там, где он есть. CLI ниже — `jwu --workspace <slug> …` через `terminal` с проверенным `workdir`. Уточняй неоднозначность через доступный `clarify` или вариантами в чате. Не выдавай наличие Hermes за установленный git-хук.

1. **Выбери работу.** Точный `#id` → `job show ID --json`; ключ → `jwu_jobs(task=KEY)` / `jobs --task KEY --json`; локальная фича → `jwu_jobs(feature=…)` / `jobs --feature FEATURE --json`; ничего → `jwu_jobs(status="active")` / `jobs --status active --json`. Несколько кандидатов — ID, цель, статус, время обновления и выбор пользователя. Не угадывай контур или сущность по номеру. `provider=local` — никаких внешних задач/PR; при `prs_enabled=false` не запрашивай PR и CI.
2. **Восстанови состояние до изменений.** `jwu_job_handoff(job_id, offline=true, save=false)` / `job handoff ID --offline --json` → `markdown`; если мало данных, `job show ID --json`. Установи цель, ветки/HEAD, последнюю фазу и согласованный план, запреты, решения, незакрытые `todo`, баги без парного `bug-resolved`, тесты и PR. Кеш не выдавай за актуальный статус. Когда запрос охватывает внешние данные, сверь свежие сборки (`jwu_builds` / `builds PR --project P --repo R --json`), комментарии (`jwu_pr` / `pr PR --project P --repo R --json`), и, только для Bitbucket, открытые задачи PR (`jwu_pr_tasks` / `pr-task list PR --project P --repo R --json`). Handoff обнаружил другие PR — спроси, входят ли они в цикл; только в запросе на продолжение привяжи выбранные `jwu_job_link` / `job link ID --pr PR --project P --repo R`. Проверь необходимость правок в каждой ветке отдельно.
3. **Не заводи дубль.** Для того же цикла, который пользователь попросил продолжить, `done`/`cancelled` → `jwu_job_reopen(job_id)` / `job reopen ID`, проверь `active` и запись о переоткрытии. `paused` → при запросе возобновить `jwu_job_status(job_id, status="active")` / `job status ID active`. Запрос «на чём остановились» — только чтение, без переоткрытия, привязки, стенда или возобновления фазы. Новая цель → `skill_view` → `jwu-start-job`.
4. **Сверь ресурсы только чтением.** `jwu_job_resources(job_id)` / `job resources ID --json`; проверь, что копии существуют и совпадают с repo/веткой, работай только в этих `ref`, не в основном клоне. Не запускай второй стенд (проверь `compose_project` и `docker ps --filter label=<label>`). Если копии нет, выясни точную ветку из ресурсов/журнала; если локальная ветка и подтверждённая `refs/remotes/origin/…` отсутствуют, остановись: штатная команда иначе может создать ветку из неверного `HEAD`. Не делай пишущий git автоматически для восстановления.
5. **Сверь план.** Коротко назови цель, фазу, что сделано и что осталось (включая задачи PR, запреты, тесты/CI). Если `decision` «План согласован: …» по-прежнему охватывает работу и проверки, продолжи без ещё одного «да». Если нет — покажи весь актуальный план с проверками и варианты «Делаем / Поправить план / Только анализ». После согласия запиши его целиком в `decision` и перечитай запись. Старый план не разрешает новые цели, публикацию, допуски git или потерю данных.
6. **Исполни остаток.** Загрузи `jwu-start-job` через `skill_view`, следуй фазам, журналу и разделу «Один финальный прогон, один стенд работы»: не повторяй проверенное и не пересоздавай подходящий стенд при возобновлении. Нет рабочей копии, а одобренные правки нужны → disk (`jwu_disk()` / `disk --json`), политика и `jwu_job_worktree` / `job worktree ID REPO --branch BRANCH --json` на каждый нужный repo. При нехватке стоп; ниже мягкого порога только после явного выбора и `hard_ok=true`, ниже жёсткого нельзя. Стенд — по `testenv`, с именем/меткой и портами jwu, после проверки места. Не редактируй в основном клоне. Ревью — `skill_view` → `jwu-job-review` до коммита, по лимиту. Перед паузой допиши фазу, решения, результаты тестов и следующий `todo`, чтобы следующее возобновление начиналось с handoff.
7. **Финиш.** Покажи тексты и собери единый выбор публикации по `jwu-start-job`; не повторяй ранее выполненные внешние шаги и не считай прошлое «да» согласием на новые записи. Цель достигнута → `skill_view` → `jwu-close-job`: «Закрыть и взять следующее с доски / Закрыть / Оставить открытой» для применимых вариантов, одно предложение итога и что будет убрано.
