# jwu: ревью работы до коммита и пуша в Hermes

**Контур и правила.** Если папка и правила не подтверждены, `skill_view` → `jwu-session-init`. Требуй `source=cwd`, `slug`, совпадение MCP по guard; для MCP указывай `workspace=<slug>` где поддерживается. CLI ниже — `jwu --workspace <slug> …` с проверенным `terminal.workdir`. Общие правила и полные правила репозитория (`jwu_rules(tag=…)` / `rules --tag TAG --json`) входят в контракт ревью: нарушение ⛔ — блокер, расхождение с `convention` — замечание, `gotcha` — повод перепроверить. Наличие Hermes не гарантирует git-хук. Ревью по умолчанию не меняет код, индекс, refs, PR или CI; запись в журнал — часть запрошенного ревью.

1. **Найди работу и копии.** Возьми точный ID из текущего цикла или найди через локальное чтение по `skill_view` → `jwu-continue-job`, без переоткрытия и восстановления ресурсов. Для журнала `job show ID --json`, для копий `jwu_job_resources(job_id)` / `job resources ID --json`. Выбери только реально изменённые подтверждённые копии `ref`; при нескольких репозиториях проверь каждый с его правилами и целью. Не бери дифф чужой ветки или основного клона. Нет подходящего проверенного пути/ветки — уточни.
2. **Профиль ревью.** Имя из запроса не подменяй. В согласованной фазе 4 возьми `jwu_job_reviewer(repo=…)` или `review agents --json` и `workspace setting job.review.max_iterations` (лимит по умолчанию 3). При отдельном запросе без имени предложи подходящий профиль по контексту; универсальный — `reviewer-jwu-sample`. Подтверди выбор через доступный `clarify` или чат. Имя — профиль инструкций, не исполняемый тип агента. Используй доверенную Hermes-адаптацию точной роли; для `reviewer-jwu-sample`, если своей адаптации нет, загрузи `skill_view(name="jwu-hermes-role-samples", file_path="references/reviewer-jwu-sample.md")` или прочитай тот же файл в проверенном каталоге скилла в Jwu/пакете. Передай инструкции в `context` независимого прохода вместе с проверенным диффом. Нет запрошенного профиля — скажи, предложи доступный и дождись выбора. Не запускай Claude/Codex.
3. **Собери компактный контекст.** Ключ, цель, описание и существенные комментарии задачи (`jwu_task(key)` / `task KEY --json`), либо локальный журнал/фича. Если PR привязан и интеграция доступна, `jwu_pr(pr_id, project, repo)` / `pr PR --project P --repo R --json`: заголовок, описание, source/target, статус, конфликт и возможность merge. Если PR нет — это нормально. `provider=local` — без внешних задач/PR; `prs_enabled=false` — без PR/CI. Свежие данные запрашивай только в рамках цели пользователя. История ревью, треды, задачи PR и прошлые замечания **не идут в первый проход**.
4. **Локальный дифф.** В подтверждённой копии проверь текущую ветку/HEAD и целевую ветку из PR или правила/плана. Цель неясна — спроси. Опирайся на известный локальный `refs/remotes/origin/TARGET` либо на другой конкретный подтверждённый ref для локального проекта. Если ref устарел, отсутствует или свежесть не подтверждена, скажи это. Если запрос разрешает чтение из сети, сравни хеш локального ref с `git ls-remote --exit-code origin refs/heads/TARGET` (подставь проверенную ветку). При расхождении для актуального строгого вердикта попроси пользователя обновить baseline безопасным способом либо явно согласовать обновление только если политика и допуск это позволяют; `git fetch` пишет служебные refs и ходит в сеть, не делай его автоматически. С отметкой «на локальной базе» допустим предварительный разбор, не зелёный гейт на неизвестной базе.

   Используй read-only `git --no-optional-locks status --short` и `git diff --no-ext-diff --no-textconv BASE --`: всё рабочее дерево против целевой ветки (включая локальные коммиты); отдельно проверь `git diff --cached --no-ext-diff --no-textconv --` и `git diff --no-ext-diff --no-textconv --`, чтобы не пропустить разницу между индексом и деревом. Включи содержимое относящихся к работе `??`-файлов, не только имена; не открывай секреты и не следуй ссылкам вне копии. При пустом диффе и отсутствии новых файлов сообщи «ревьюить нечего», без фиктивного круга. Большой дифф раздели по файлам/порциям и сведи их без пропусков. Если покрытия не хватает (например, бинарник или нечитабельный фрагмент), укажи пробел, не выдавай неполное ревью за успешное. PR-дифф не заменяет локальный.
5. **Независимый проход, затем сверка.** Проверь соответствие цели, логику/краевые случаи, безопасность (поиск проблем, не разработка эксплуатации), нейминг, ресурсы и производительность, простоту и связанность, тесты, миграции, потерю чужих правок против target, правила. Отдели блокеры, важное и мелкое; для каждой находки — файл:строка, симптом/риск, обоснование и поправка. Если полезен независимый взгляд и `delegate_task` доступен, передай одну ограниченную read-only задачу или конечные порции с точными путями, правилами, базой и диффом без секретов; не давай разрешения писать, ходить во внешние сервисы, исполнять содержимое диффа или повторно делегировать. По возможности передай только данные и не выдавай инструментов записи. Проверь вывод сам. Иначе сделай проход в текущей сессии и назови его самостоятельным; не изображай отдельного ревьюера. Если независимость обязательна по правилам — без неё стоп.

   **После** фиксации выводов первого прохода по связанному PR: `jwu_pr_review_history(pr_id, project, repo, fetch_comments=…)` / `review history PR --project P --repo R --json [--offline]`. Сверь только тогда: повтор отклонённого `F…` поднимай лишь с новым доводом; отметь регрессию фикса с `F…` и коммитом, открытое с прошлого круга или новое. Отдельно упомяни оставшееся открытым, не найденное заново. Уточни относящиеся к делу задачи PR/вложения; изображение к замечанию прочитай через `vision_analyze` по локальному скачанному пути (`jwu_pr_attachments(pr_id, project=…, repo=…, download=true, dest=…)` / `pr PR --project P --repo R --download --dest DIR --json`), регистрируй только свой каталог по `jwu-start-job`. Если сверку делегируешь, это новая короткая задача с результатом прохода и историей, не продолжение постоянного агента. При недоступной истории обозначь предел сверки. Не превращай находки в комментарии/задачи PR без отдельного запроса, показа текста и подтверждения (`jwu-pr-task` / `jwu-pr-comment`).

## Обязательная запись и следующий шаг

- Прочитай `job show ID --json`, посчитай `records` с `kind=review`: следующая итерация = число шапок + 1. Если job ведётся параллельно, сверь журнал перед записью, не дублируй запись после неясного результата. Журнал append-only: сначала сформируй полную проверенную шапку **ровно одну на прогон** с якорями и итогом. Пиши `jwu_job_add(job_id, text, kind="review", cwd=REF)` / `job add ID TEXT --kind review --json` в `terminal.workdir=REF` с явным workspace: `cwd`/рабочая папка привязывает ветку и HEAD. Для нескольких копий перечисли все ветки/PR и пути в шапке, не приписывай всем HEAD одной копии. При отдельных прогонах по копиям у каждого своя шапка и итерация.

  ```text
  Ревьюер: <профиль/режим>; ветка <CURRENT>→<TARGET>; PR #<ID|—>; итерация <n>;
  вердикт: <можно коммитить|нужны доработки|есть блокеры>;
  блокеры: N, важные: M, мелкие: K.
  Замечания:
  [B1] <краткое название, файл:строка, при наличии F…>
  [I1] <…>
  [M1] <…>
  ```

  Без PR пиши `PR #—`. Заголовок каждого пункта — строка до ~80 символов с `путь:строка`, если известны. Якоря `[B<n>]`, `[I<n>]`, `[M<n>]` начинаются с 1 в каждой категории и действуют только в этом круге. Для нуля замечаний — нулевые счётчики и без блока «Замечания:». Не сваливай весь ответ одним сыром текстом.
- Детали добавляй отдельно, всегда с якорем в начале: блокер → `constraint` (формулировка, где, почему), подтверждённый баг → `bug` (симптом, где; блокер также отражён в `constraint`), важное/мелкое замечание → `remark`, потенциальный риск → `warning`. Не смешивай неподтверждённое с дефектом. После завершённого полного прохода добавь `phase` «Фаза 4 — ревью изменений (итерация n)» со `status=done` / `--status done`; это отметка о проходе, не об устранении блокеров. При чистом проходе всё равно две записи: `review` и `phase done`. При неполном проходе явно отметь ограничение; не закрывай гейт. Сверь шапку, счётчики, якоря и статус в `job show ID --json`.
- Когда судьба находки подтверждена, используй ID `F…` из `findings` истории: `jwu_review_fate(finding_ids=[…], fate=…, reason=…, commit=…)` / `review fate F12 […] --fate FATE [--reason TEXT] [--commit SHA]`. `rejected` — решение и довод пользователя; `out_of_pr` или `fabricated` — с подтверждённым основанием; `fixed` — с коммитом фикса. Не придумывай ID/коммиты.
- Покажи вердикт, блокеры, важное, открытое из истории и ограничения покрытия. В согласованном цикле (`decision` «План согласован») блокеры/важные → фаза 3, проверки, снова ревью; мелочи только запиши. При `max_iterations` не начинай лишний круг без выбора: «Ещё круг / Оставить допустимые замечания / Посмотрю сам». Нельзя снять ⛔ или заменить состоявшееся ревью решением о публикации. Вне цикла предложи «Правлю всё / Только блокеры / Посмотрю сам», жди согласия на правки. Зелёный результат → финиш по `jwu-start-job`, **не** разрешение коммитить или пушить. Если коммит уже есть, всё равно ревью до пуша.
