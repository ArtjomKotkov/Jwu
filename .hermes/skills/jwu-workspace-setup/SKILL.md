# jwu: привязка проекта к воркспейсу

1. Уточни фактическую папку проекта, проверь абсолютный путь (`pwd -P`, при необходимости корень Git). В `terminal` задавай её явно как `workdir`. `jwu workspace current --json` запускай без `--workspace`; только `source: cwd` с ожидаемыми `cwd` и непустым `slug` подтверждает привязку. Если контур уже правильный — подтвердить и ничего не создавать. Если привязка конфликтует — сообщить, не перепривязывать. `active`, `only`, `env`, `explicit` или ошибка не подтверждают путь. При обычной проверке области **остановись**, если привязки нет; не превращай проверку в bootstrap и не пиши jobs в запасной контур.
2. Только на явный запрос подключения: предложи создать новый контур или привязать к существующему. Предпочитай CLI из проверенной папки: `jwu init <абсолютная-папка> --json` без `--yes` и `--attach`; ожидай `reason: confirm_required`. При доступном MCP `jwu_workspace_suggest(path=…)` — всегда с абсолютным путём; список существующих — `jwu workspace list --json`. Если предложение говорит `already_bound`/`already_initialized`, не выполняй init повторно: у CLI ветка уже привязанной папки может менять активный контур. Проверь найденные пути и теги, исключи чужие каталоги; не скрывай, что init добавляет **все** предложенные папки и меняет активный контур.
3. Покажи точный план (папки, теги, новый или существующий slug, имя, провайдер, Bitbucket, смена активного контура). Выбор — в чате, затем явное согласие на этот план. Один провайдер: `local` по умолчанию, `jira` (Bitbucket только по выбору) или `github`. Перепроверь предложение и конфликты перед записью. Создание: `jwu init <папка> --slug <slug> --name <имя> --provider <provider> --yes --json` (добавь `--bitbucket` только если одобрено). Присоединение: `jwu init <папка> --attach <slug> --json` — **пишет даже без `--yes`**. Если одобрены не все предложенные папки, не используй init; для точечных операций используй подтверждённый workspace и `jwu --workspace <slug> workspace add-path <путь> --tag <тег>`; для точечного создания сверяй `jwu_workspace_create(slug, name, provider, bitbucket, paths, tags, use)` с живой MCP-схемой и передавай только одобренные значения. Если недоступен безопасный точечный вариант, остановись.
4. Прочитай обратно: `jwu workspace current --json` без переопределения должен показать ожидаемый `slug`, `cwd`, `source: cwd`; `jwu --workspace <slug> workspace paths --json` должен подтвердить все пути и теги. Не продолжай работу при несовпадении. В дальнейшем используй явный `--workspace <slug>`. MCP пригоден для обычных действий только после того, как `jwu_workspace_current()` подтвердил те же `source`, `slug` и `cwd`; иначе CLI. Имена Hermes обычно `mcp_jwu_jwu_*` — проверь обнаруженную схему.
5. По запросу предложи теги (`workspace tag <путь> --add <тег>`) и стартовые правила (`rule add <заголовок> --kind <тип> --text <текст>` с необязательным `--tag`). Каждое изменение требует согласия на точный текст/значения; проверь через `workspace paths --json` / `rules --json`. Не меняй провайдера, не переноси папки и не настраивай учётные данные заодно. Настройку доступа делает пользователь локально, без передачи секретов Hermes. Загрузи **jwu-session-init**, прежде чем работать в новом контуре.
