# jwu: очередь ревью

Если нет подтверждённого проекта и правил, загрузи `skill_view(name="jwu-session-init")`. При `local` или `prs_enabled=false` не ходи за PR. Загрузи `jwu-review-pr` для транспорта, проверки target и точных команд записи, `jwu-voice-rewrite` для формы текста. Если `skill_view` не находит эти или другие зависимые скиллы в чате воркера, прочитай актуальные `SKILL.md` через `read_file` из проверенного каталога `.hermes/skills` репозитория Jwu по путям из брифа; архивные версии не используй. Ссылки на скиллы не меняют рабочую папку задачи. MCP только после сверки cwd, с `workspace=slug`; CLI — `jwu --workspace SLUG …`, явный `terminal(workdir=<проект>)`. Динамические значения через argv или отдельное shell-экранирование. PR идентифицируй тройкой проект/репо/номер; один PR — `jwu-review-pr`, свой diff — `jwu-job-review`.

Режим `light` (по умолчанию: блокеры и критичное) или `full`; предел параллельности N (по умолчанию 3); фильтры по номерам и репозиториям. `--include-approved` включает уже APPROVED мной; `--include-needs-work` — мои NEEDS_WORK без вопроса.

## A. Разбор и файл, без записей в PR

Разреши точные роли как в `jwu-review-pr`: доверенная Hermes-адаптация либо fallback для совпадающего штатного имени из `jwu-hermes-role-samples` (через `skill_view` или проверенный каталог Jwu/пакета). Если точной роли ревьювера или фильтра нет, отметь затронутый PR и дождись выбора роли, не подменяй её. Для каждого прохода передавай инструкции и проверенные входы отдельно. Для голоса примени `jwu-voice-rewrite`; без профиля оставь нейтральный текст.

1. `jwu_review_queue(include_approved=…, include_needs_work=…, prs=[…], repos=[…])` / `review queue --json` с повторяемыми `--pr ID`, `--repo R` и нужными флагами. Покажи таблицу PR со ссылкой, репо, задачей, ревьювером, пропуски с причинами. По `needs_work` до запуска — один множественный выбор (`clarify` если доступен, иначе список с номерами в чате): `repo#PR · КЛЮЧ · автор`, ссылка, `new_commits=N`, ноль или неизвестно. Названные явно PR и PR, уже включённые флагом, не переспрашивай. Выбранные добавь, остальные отметь «пропущено: мой NEEDS_WORK».
2. Ревьюер = `reviewer_agent` (иначе `reviewer-jwu-sample`), фильтр = `filter_agent` (иначе `review-filter-sample`). Настройки смотри `review agents --json`; имена — метки, не параметры Hermes. Прочитай подтверждённые инструкции ролей как в `jwu-review-pr`. Не перенастраивай роли в процессе.
3. Ограниченный `delegate_task` на один PR на ревьювера: самодостаточный контекст (подтверждённый slug/workdir и правила, точный PR, source → target, задача, режим). Он сам берёт `jwu_pr`, `jwu_task`, полный `jwu_pr_diff` (по файлам при необходимости) или CLI `pr ID --json`, `task KEY --json`, `pr ID --diff --numbered [--path FILE]`. Сверяет target в подтверждённом клоне без переключения веток/правок; разрешённый fetch и отсутствие клона — как в `jwu-review-pr`, fetch не делегируй роли. Не давай историю прошлых ревью. Роли возвращают текст, проверенные результаты сохраняет вызывающий скилл в разрешённые `review_file` и `facts_file` вне репо; проверь пути до записи (шаг 5). Не тащи весь diff в оркестратор при наличии делегации.
4. Пул не больше N и фактического лимита Hermes. Используй `delegate_task(tasks=[…])` небольшими пачками или, если есть фоновые результаты в этом интерфейсе, пополняй пул по завершению. Если делегация недоступна — последовательно. Как только результат отдельного ревью доступен, передай его фильтру с `review_file`, `facts_file`, PR, target, задачей и режимом. Фильтр сам читает `jwu_pr_review_history(pr_id, project, repo)` / `review history ID --project P --repo R --json`: отклонённое без нового довода — отбросить с `F<id>`, проверить регрессии исправлений с `F<id>` и незакрытые находки. Оставить подтверждённые `new`/`made-reachable`, сценарий, последствие, просьбу, точные `path:line` или `reply_to`; отметить предложенный статус и отброшенное с причинами. `pre-existing` — только в сводку. Не выдавай усечённый/упавший результат за пройденный PR.
5. Проверь `dir`, `review_file`, `facts_file` и `summary` из очереди: абсолютные пути в данных jwu вне репо, уникальны для обрабатываемых PR; при коллизии раздели файлы/прогоны. В CLI каталог может ещё не существовать; `write_file` создаёт родителей. Технические черновики из фактов перепиши отдельным проходом голоса одним заданием на PR: `channel=pr_comment` / `pr_reply` / `pr_review_body`, `audience=colleague`, numbered diff или цитата треда как контекст, 3–5 предложений на комментарий, та же нумерация. Голос не меняет факты и ничего не отправляет.
6. `write_file` сводки `<dir>/summary.md`: `PR | репо | задача | вердикт | главное` (PR ссылкой), раздел каждого PR с предлагаемым статусом, тяжестью, `file:line` и черновиками; отдельно pre-existing, в конце пропуски и причины. Отдай файл в текущем сеансе: Desktop — артефакт `write_file` в Artifacts; gateway с доставкой файлов — абсолютный путь без backticks в ответе для Deliverable Mode. Не отправляй в другой чат. Если доставка недоступна, прямо скажи и дай путь. В чате кратко — число PR и блокеры. В рамках запрошенного разбора сохрани локальную `context`-заметку на каждый разобранный PR о пути к черновикам (`jwu_note` / `note KEY TEXT --kind context --json`, проверь через `notes`).

## B. Предпросмотр и отправка: один PR за сообщение

Если запрошен только черновик, не начинай отправку. Для разрешённого этапа публикации веди по всей очереди список: PR, вердикт, уже подтверждённые записи, следующий выбор или явный пропуск и состояние работы. Одна запись или один выбор не завершают очередь.

По порядку сводки заново прочитай PR (head, коммиты, треды, сборка, ревьюверы) и задачу. Сравни с прошлым комментом/статусом пользователя; убери написанные им вручную черновики, ответы на вопросы автора идут первыми. При изменении head перепроверь находки/якоря, не отправляй устаревшее.

Покажи: (1) `N/M — repo#PR · КЛЮЧ · автор` и ссылку; (2) 2–3 простых предложения о задаче и изменении; (3) новые коммиты, ответы и замечания после прошлого ревью, статус сборки и какие дубли сняты; (4) блок для каждого комментария: номер, место (`path:line`, тред #id, общий), тяжесть, **Проблема** для пользователя в 3–5 предложениях из фактов (что было, что меняется, сценарий и риск), затем точный текст цитатой; (5) текущий и предлагаемый статус, полный текст отзыва, если есть. Ревьюер сам обосновывает, блокируют ли проверенные замечания мерж, и рекомендует статус; пользователь разрешает только внешнюю запись показанного варианта. В чате воркера напиши **«Жду твоего выбора»** и вызови `clarify`: отправить показанное (включая явно названный статус) / править / пропустить. Если кнопки недоступны или запрос не доставлен, покажи варианты номерами: «Ответь номером или напиши свой вариант. До ответа ничего не меняю». Молчание и тайм-аут — не согласие.

- «Отправить» на этот PR покрывает только показанные и явно принятые действия, включая статус лишь если он был в вопросе. Частичное «1 и 3, без статуса» — строго так. Сначала ответы в треды, затем inline, затем общий комментарий, в конце статус. Команды и `--yes` — см. `jwu-review-pr`. При `anchored:false` скажи; удаление своего комментария (`jwu_pr_comment_delete(pr_id, comment_id)` / `pr-comment-delete ID CID --yes --json`) и повторное размещение — только после нового согласия. Перечитай PR, сверь подтверждённые ids, якоря и статус; не повторяй неопределённую отправку вслепую.
- После отправки — закреплённая `status`-заметка с фактическим итогом. Только подтверждённые отправленные находки — `jwu_review_add(pr_id, findings, side="local", label=…, commit=<head>, full_pass=…)` с точным PR и `workspace`; `findings`: `level`, `text` в одну строку, `file`, `line` где есть. Для частичного списка или `light` не ставь `full_pass=True` (иначе исчезнут прежние находки); не дублируй записи `kind=review`, уже попавшие в историю работ. Проверь круг в `review history`. У `review add` нет CLI-эквивалента: без MCP не выдумывай его, явно скажи, что круг не записан.
- «Править» — перепиши только утверждённые факты и форму, покажи PR заново, отдельно предложи сохранить voice feedback. «Пропустить» / «дальше» — никакой отправки по этому PR, сразу следующий.
- После частичной публикации не повторяй опубликованные комментарии. Если рекомендуемый статус ещё не установлен и пользователь не отказался от него отдельно, это новый выбор: например, «Поставить APPROVED без новых комментариев» / «Оставить статус как есть». Покажи его через `clarify` или текстовый фолбэк. Согласие на комментарий не действует на статус, другие комментарии или другие PR.
- После каждого ответа проверь и запиши только согласованное, затем сам покажи следующий нерешённый выбор, не жди отдельного «дальше». Тайм-аут оставляет без изменения только затронутое действие; обозначь его и продолжай независимые шаги. В конце покажи итог по всей очереди и отдельный выбор закрытия, если есть связанные работы, либо укажи, почему они остались открытыми.

Интерактивный воркер после последнего решения отправляет итог по всему назначению в проверенный чат оркестратора из брифа; ответ в текущем чате и записи в jwu не заменяют отчёт. Если работы закрыты и решений не осталось, в том же сообщении явно попроси архивировать только свою сессию после завершения ответа. При оставшихся работах или решениях перечисли их и не проси архивировать. Если маршрут недоступен, явно сообщи об этом. Не отправляй черновики в другой чат: в служебном отчёте достаточно итогов, статусов и ссылки на сводку.
