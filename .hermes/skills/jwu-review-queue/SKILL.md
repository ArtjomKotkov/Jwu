# jwu: очередь ревью

## Вход по поручению

Для назначенной очереди сначала пройди «Вход по поручению с доски» в **jwu-start-job** в своей сессии. Сохрани соответствие `полный ключ PR → job_id` только по подтверждённым взятиям/передачам. Пересекай результат фильтров очереди с точными назначенными PR; не расширяй выборку совпадением номера или Jira-ключа. Одно ревью и решение о публикации — на один PR. Если несколько PR одной задачи и `todo_take` пропустил один по общей задаче, чужой `job_id` не относится ко второму PR. Сообщи пропуск, не обходи его через `job start` и не публикуй по этому PR; продолжай независимо взятые. Не теряй пропущенный PR: если мешает собственная работа той же очереди, после её согласованного закрытия заново прочитай доску и попробуй взять этот точный PR в своей сессии. Чужую работу не закрывай. В итоге различай завершённое, явно пропущенное пользователем и всё ещё занятое. При прямом `/jwu-review-queue` без назначения обычный отбор ниже остаётся доступен без предварительной брони.

Если нет подтверждённого проекта и правил, загрузи `skill_view(name="jwu-session-init")`. При `local` или `prs_enabled=false` не ходи за PR. Загрузи `jwu-review-pr` для транспорта, проверки target и точных команд записи, `jwu-voice-rewrite` только для чтения профиля и формы текста. Обычная правка не даёт повода спрашивать о записи в профиль; меняй его только по отдельной просьбе и согласию на формулировку. Если `skill_view` не находит эти или другие зависимые скиллы в чате воркера, прочитай актуальные `SKILL.md` через `read_file` из проверенного каталога `.hermes/skills` репозитория Jwu по путям из брифа; архивные версии не используй. Ссылки на скиллы не меняют рабочую папку задачи. MCP только после сверки cwd, с `workspace=slug`; CLI — `jwu --workspace SLUG …`, явный `terminal(workdir=<проект>)`. Динамические значения через argv или отдельное shell-экранирование. PR идентифицируй тройкой проект/репо/номер. Разовое ревью вне очереди — `jwu-review-pr`, свой diff — `jwu-job-review`; единственный PR из назначенной очереди остаётся в этом процессе.

Режим `light` (по умолчанию: блокеры и критичное) или `full`; предел параллельности N (по умолчанию 3); фильтры по номерам и репозиториям. `--include-approved` включает уже APPROVED мной; `--include-needs-work` — мои NEEDS_WORK без вопроса.

## A. Разбор и файл, без записей в PR

Разреши точные роли как в `jwu-review-pr`: доверенная Hermes-адаптация либо fallback для совпадающего штатного имени из `jwu-hermes-role-samples` (через `skill_view` или проверенный каталог Jwu/пакета). Если точной роли ревьювера или фильтра нет, отметь затронутый PR и дождись выбора роли, не подменяй её. Для каждого прохода передавай инструкции и проверенные входы отдельно. Для голоса примени `jwu-voice-rewrite`; без профиля оставь нейтральный текст.

1. `jwu_review_queue(include_approved=…, include_needs_work=…, prs=[…], repos=[…])` / `review queue --json` с повторяемыми `--pr ID`, `--repo R` и нужными флагами. Покажи таблицу PR со ссылкой, репо, задачей, ревьювером, пропуски с причинами. По `needs_work` до запуска — один множественный выбор (`clarify` если доступен, иначе список с номерами в чате): `repo#PR · КЛЮЧ · автор`, ссылка, `new_commits=N`, ноль или неизвестно. Названные явно PR и PR, уже включённые флагом, не переспрашивай. Выбранные добавь, остальные отметь «пропущено: мой NEEDS_WORK».
2. Ревьюер = `reviewer_agent` (иначе `reviewer-jwu-sample`), фильтр = `filter_agent` (иначе `review-filter-sample`). Настройки смотри `review agents --json`; имена — метки, не параметры Hermes. Прочитай подтверждённые инструкции ролей как в `jwu-review-pr`. Не перенастраивай роли в процессе.
3. Ограниченный `delegate_task` на один PR на ревьювера: самодостаточный контекст (подтверждённый slug/workdir и правила, точный PR, source → target, задача, режим). Он сам берёт `jwu_pr(pr_id, project=P, repo=R, workspace=slug)`, `jwu_task(key, workspace=slug)`, полный `jwu_pr_diff(pr_id, project=P, repo=R, workspace=slug)` (по файлам при необходимости) или CLI `pr ID --project P --repo R --json`, `task KEY --json`, `pr ID --project P --repo R --diff --numbered [--path FILE]`. Сверяет target в подтверждённом клоне без переключения веток/правок; разрешённый fetch и отсутствие клона — как в `jwu-review-pr`, fetch не делегируй роли. Не давай историю прошлых ревью. Роли возвращают текст, проверенные результаты сохраняет вызывающий скилл в разрешённые `review_file` и `facts_file` вне репо; проверь пути до записи (шаг 5). Не тащи весь diff в оркестратор при наличии делегации.
4. Пул не больше N и фактического лимита Hermes. Используй `delegate_task(tasks=[…])` небольшими пачками или, если есть фоновые результаты в этом интерфейсе, пополняй пул по завершению. Если делегация недоступна — последовательно. Как только результат отдельного ревью доступен, передай его фильтру с `review_file`, `facts_file`, PR, target, задачей и режимом. Фильтр сам читает `jwu_pr_review_history(pr_id, project=P, repo=R, workspace=slug)` / `review history ID --project P --repo R --json`: отклонённое без нового довода — отбросить с `F<id>`, проверить регрессии исправлений с `F<id>` и незакрытые находки. Оставить подтверждённые `new`/`made-reachable`, сценарий, последствие, просьбу, точные `path:line` или `reply_to`; отметить предложенный статус и отброшенное с причинами. `pre-existing` — только в сводку. Не выдавай усечённый/упавший результат за пройденный PR.
5. Проверь `dir`, `review_file`, `facts_file` и `summary` из очереди: абсолютные пути в данных jwu вне репо, уникальны для обрабатываемых PR; при коллизии раздели файлы/прогоны. В CLI каталог может ещё не существовать; `write_file` создаёт родителей. Технические черновики из фактов перепиши отдельным проходом голоса одним заданием на PR: `channel=pr_comment` / `pr_reply` / `pr_review_body`, `audience=colleague`, numbered diff или цитата треда как контекст, 3–5 предложений на комментарий, та же нумерация. Голос не меняет факты и ничего не отправляет.
6. `write_file` сводки `<dir>/summary.md`: `PR | репо | задача | вердикт | главное` (PR ссылкой), раздел каждого PR с предлагаемым статусом, тяжестью, `file:line` и черновиками; отдельно pre-existing, в конце пропуски и причины. Отдай файл в текущем сеансе: Desktop — артефакт `write_file` в Artifacts; gateway с доставкой файлов — абсолютный путь без backticks в ответе для Deliverable Mode. Не отправляй в другой чат. Если доставка недоступна, прямо скажи и дай путь. Сводка не заменяет показ первого готового PR по разделу B. В рамках запрошенного разбора сохрани локальную `context`-заметку на каждый разобранный PR о пути к черновикам (`jwu_note` / `note KEY TEXT --kind context --json`, проверь через `notes`).

## B. Предпросмотр и отправка: один PR за сообщение

Сначала закончи анализ выбранной очереди (фаза A); явно отдели недоступные PR. Затем сразу покажи первый нерешённый PR по порядку: готовые тексты комментариев, их места и рекомендуемый статус ревью (или «статус без изменений»). Не спрашивай, готовить ли тексты или переходить ли к первому PR. Если анализ уже готов, не запускай его заново: сверь HEAD, якоря и дубли, примени голос для формулировок и переходи к показу. Сводка — дополнение, а не отдельная остановка. Только при явном «только черновик» отдай готовые тексты без вопроса о публикации и ничего не отправляй. Отчёт без предложенной внешней записи не требует ответа: покажи итог и перейди к следующему PR. Веди по всей очереди список: PR, вердикт, уже подтверждённые записи, следующий выбор или явный пропуск и состояние работы. Одна запись или один выбор не завершают очередь.

По порядку сводки заново прочитай PR (head, коммиты, треды, сборка, ревьюверы) и задачу. Сравни с прошлым комментом/статусом пользователя; убери написанные им вручную черновики, ответы на вопросы автора идут первыми. При изменении head перепроверь находки/якоря, не отправляй устаревшее.

Покажи: (1) `N/M — project/repo#PR · КЛЮЧ · автор` и ссылку; (2) 2–3 простых предложения о задаче и изменении; (3) новые коммиты, ответы и замечания после прошлого ревью, статус сборки и какие дубли сняты; (4) блок для каждого комментария: номер, место (`path:line`, тред #id, общий), тяжесть, **Проблема** для пользователя в 3–5 предложениях из фактов (что было, что меняется, сценарий и риск), затем точный текст цитатой; (5) текущий и предлагаемый статус, полный текст отзыва, если есть. Ревьюер сам обосновывает, блокируют ли проверенные замечания мерж, и рекомендует статус; пользователь разрешает только внешнюю запись показанного варианта. Если есть предлагаемая запись и это не «только черновик», покажи один выбор в чате исполнения через `clarify`: например, «Отправить 2 комментария и поставить NEEDS_WORK» / «Отправить только 2 комментария» / «Пропустить PR». Показывай только применимые варианты и разреши ответить своими номерами или поправить текст. При одном действии не добавляй пустых вариантов. Не спрашивай ещё раз о точном неизменном результате, уже согласованном пользователем в этом чате. Если кнопки недоступны или запрос не доставлен, покажи варианты номерами: «Ответь номером или напиши свой вариант. До ответа ничего не меняю». Молчание и тайм-аут — не согласие.

- «Отправить» на этот PR покрывает только показанные и явно принятые действия, включая статус лишь если он был в вопросе. Частичное «1 и 3, без статуса» — строго так. Перед записью сверь HEAD, треды, якоря и текущий статус с превью; если результат изменился, обнови превью и согласуй изменённое. Сначала ответы в треды, затем inline, затем общий комментарий, в конце статус; если тело статуса в Bitbucket уйдёт общим комментарием, явно включи его в превью и не посылай повторно. Команды и `--yes` — см. `jwu-review-pr`. При `anchored:false` скажи; удаление своего комментария (`jwu_pr_comment_delete(pr_id, comment_id, project=P, repo=R, workspace=slug)` / `pr-comment-delete ID CID --project P --repo R --yes --json`) и повторное размещение — только после нового согласия. Перечитай PR, сверь подтверждённые ids, якоря и статус; не повторяй неопределённую отправку вслепую.
- После отправки — закреплённая `status`-заметка с фактическим итогом. Только подтверждённые отправленные находки — `jwu_review_add(pr_id, findings, side="local", label=…, commit=<head>, project=P, repo=R, workspace=slug, full_pass=…)`; `findings`: `level`, `text` в одну строку, `file`, `line` где есть. Для частичного списка или `light` передавай `full_pass=False` (иначе исчезнут прежние находки); не дублируй записи `kind=review`, уже попавшие в историю работ. Проверь круг в `review history`. У `review add` нет CLI-эквивалента: без MCP не выдумывай его, явно скажи, что круг не записан.
- «Править» — перепиши только утверждённые факты и форму, покажи исправленный текст по этому PR. Правка текста не меняет профиль стиля. «Пропустить» / «дальше» — никакой отправки по этому PR, сразу следующий.
- После частичной публикации не повторяй опубликованные комментарии и не предлагай отклонённое. Если пользователь оставил действительно нерешённый вопрос о статусе, предложи только его: например, «Поставить APPROVED без новых комментариев» / «Оставить статус как есть». Согласие на комментарий не действует на статус, другие комментарии или другие PR.
- После каждого ответа проверь и запиши только согласованное, затем сам покажи следующий нерешённый выбор, не жди отдельного «дальше». Тайм-аут оставляет без изменения только затронутое действие; обозначь его и продолжай независимые шаги. В конце покажи итог по всей очереди. Для связанных работ применяй **jwu-close-job**: спрашивай о закрытии только если решение ещё нужно. Воркер отправляет обычный итог Main пассивной почтой по **jwu-orchestrator**; почта не переносит согласие и не запускает архив. Архив чата — только вручную.

Интерактивный воркер после последнего решения отправляет итог по всему назначению в проверенный связанный чат Main через `session_mailbox`; ответ в текущем чате и записи в jwu не заменяют отчёт. Если работы закрыты и решений не осталось, спроси пользователя в чате воркера об архиве. Если он явно согласился, оставь чат открытым и предложи архивировать этот чат вручную в Hermes Desktop; не передавай согласие в другой чат. При оставшихся работах или решениях перечисли их и не проси архивировать. Если маршрут недоступен, явно сообщи об этом. Не отправляй черновики в другой чат: в служебном отчёте достаточно итогов, статусов и ссылки на сводку.
