# jwu: создать, поправить или связать задачи Jira

Загрузи `skill_view(name="jwu-session-init")`; без проверенной привязки и правил пройди его. Требуй `source="cwd"`, непустой `slug` и совпадающий `cwd` из `jwu workspace current --json` с явным `terminal.workdir` проекта. Соблюдай ⛔ и правила тега. Ниже CLI-команды идут после `jwu --workspace <slug>` с тем же `workdir`. MCP необязателен: только если `jwu_workspace_current` подтверждает тот же `source`, `slug`, `cwd`; передавай `workspace=<slug>` в поддерживаемые вызовы. Если чтения не хватает, уточни через `clarify`, если доступен, иначе спроси в чате.

Только `provider=jira`. Для Support явно предупреди, что задачу и текст увидит клиент, и получи согласие именно на это. Перед каждой внешней записью покажи точную цель и все поля payload, полные тексты в блоках кода, при изменении «было → стало». Дождись нового явного «да» на это превью. Правка поля или цели — новое превью. Перечитай точную цель после записи; при неопределённом исходе не повторяй запись вслепую.

1. Уточни проект и тип, не угадывай. В незнакомом проекте `jwu_issue_create_meta(project)` даёт типы и обязательные поля; отдельной CLI-команды нет. CLI dry-run ниже проверяет уже выбранный тип и поля (`check`); не выдумывай допустимые значения, если их не удалось узнать. Для подзадачи сверь ключ родителя и тип с метаданными.
2. Источники черновика — диалог, обращение, `jwu_job_handoff(job_id)` / `job handoff JOB_ID --json` (без `--save`). Русский текст и wiki-разметка Jira Server (`{code}`, `*жирный*`, `# `), без атрибуции ассистента. Баг: сценарий, воспроизведение, ожидание, факт, окружение, ссылки. Для формы используй «Голос пользователя» из `skill_view(name="jwu-pr-comment")`, канал `task`, аудитория `colleague`/`analyst`/`qa` по получателю. `from_job` / `--from-job JOB_ID` даёт черновик описания из журнала, не сочетай с явным описанием. Чтобы не публиковать необработанный или заново сгенерированный текст, финальный dry-run и запись делай с зафиксированным описанием без `from_job`.
3. Dry-run: `jwu_issue_create(project=…, summary=…, description=…, issuetype=…, priority=…, assignee=…, labels=…, components=…, fix_versions=…, parent=…, dry_run=True)` / `issue create --project PROJECT --summary TITLE --type TYPE --description-file FILE [--priority P --assignee LOGIN --label LABEL --component C --fix-version V --parent KEY] --dry-run --json` (флаги списков повторяются). Исправь `check.problems`, повтори; покажи `similar`, если есть дубли-кандидаты. По отдельному поиску: `jwu_issue_similar(project, summary, months=…)` / `issue similar --project PROJECT --summary TITLE --json`.
4. Покажи `fields` целиком, включая проект, тип, родителя и defaults, если они присутствуют. После «да» отправь тот же набор с `dry_run=False` / замени `--dry-run` на `--yes`. Перечитай созданный ключ `jwu_task(key)` / `task KEY --json`, сверь результат; верни ключ и ссылку из `issue`. Если есть связанная работа, локально `jwu_job_add(job_id, "Заведена KEY: SUMMARY", kind="phase")` / `job add JOB_ID "Заведена KEY: SUMMARY" --kind phase --no-git`.
5. Связь — отдельное превью типа, направления, обеих задач и отдельное «да». `issue link-types --key KEY --json` — фактические имена и направления связей на данном инстансе. Между Jira и Support связи нет. `jwu_issue_link(inward, outward, link_type=…)` / `issue link INWARD OUTWARD --type TYPE --yes --json`; перечитай `links` карточек и проверь пару и направление.
6. Правка: прочитай `jwu_task(key)` / `task KEY --json`; меняй только согласованные поля. `jwu_issue_update(key, summary=…, description=…, assignee=…, priority=…, labels=…)` / `issue edit KEY [--summary TITLE --description-file FILE --assignee LOGIN --priority P --label LABEL] --yes --json`. Снять исполнителя — `assignee=""` / `--assignee -`, метки передаются целым списком; для пустого списка используй MCP `labels=[]` (явного CLI-флага очистки нет). Сверь поля перечтением. Удаления задач в jwu нет; для закрытия загрузи `skill_view(name="jwu-task-status")`. Для вложений — `skill_view(name="jwu-task-attach")`, если доступен.
