# jwu: ревью чужого PR

## Вход по поручению

Воркер, которому назначен PR с доски, сначала проходит «Вход по поручению с доски» в **jwu-start-job** в своей сессии. Используй только подтверждённый ID работы по этому полному `project/repo#PR`; совпадения задачи недостаточно. Если очередь уже проверила бронь, повторно не бери. Прямое `/jwu-review-pr` без назначения не требует брифа или автоматического создания работы.

Свой diff — `jwu-job-review`, очередь — `jwu-review-queue`. Если проект или правила не подтверждены, загрузи `skill_view(name="jwu-session-init")`. `local`/`prs_enabled=false` — остановись. Далее MCP только при совпавшей привязке, с `workspace=slug`; CLI `jwu --workspace SLUG …` с явным `terminal(workdir=<проект>)`. Используй argv или `shlex.quote` для каждого динамического аргумента. В каждом PR-вызове фиксируй `project`, `repo`, `pr_id` (CLI `--project P --repo R`).

## Разбор, без отправки

После выбора имени ревьювера и фильтра найди доверенные Hermes-инструкции точных ролей. Для штатных имён без отдельной адаптации используй `skill_view(name="jwu-hermes-role-samples")` и соответствующие `references/`; если скилл не виден, прочитай их из проверенного каталога `.hermes/skills/jwu-hermes-role-samples/` в Jwu или из установленного пакета. Нет пользовательской роли — сообщи и дождись выбора, не подменяй её штатной. Передавай инструкции отдельным проходам в `context` `delegate_task`; при недоступной делегации применяй последовательно и скажи, что проходы не были независимыми.

1. Вход: `ID [роль ревьювера] [--project P --repo R]`. Номер без репозитория разреши из `jwu_prs(view="review")` / `prs --view review --json`; при неоднозначности спроси (`clarify` или чат). Роль: обязательная по правилам, затем совместимая явно названная, затем настроенная для репо (`jwu_job_reviewer(repo=…)` / `review agents --json`), затем `reviewer-jwu-sample`; спроси, лишь если нужная роль неясна. Имена ролей — метки, не типы Hermes. Загружай точную Hermes-адаптацию. Для пользовательской роли вне каталога нужна отдельно подтверждённая Hermes-совместимая инструкция; не подменяй роль.
2. `jwu_context("P/R#ID")` (CLI `notes 'P/R#ID' --json` даёт только заметки) и `jwu_pr(...)` / `pr ID --json`: описание, ветки, ревьюверы, head, треды/комменты и задачи, сборка. Если скриншоты нужны, `jwu_pr_attachments(pr_id, download=True, dest=…)` / `pr ID --download --dest DIR --json` в scratch; проверь путь, смотри картинки через `vision_analyze`. По `task_key` прочитай `jwu_task(key)` / `task KEY --json`. Нет задачи — явно ревью только по PR.
3. `jwu_pr_diff(pr_id, path=None, max_chars=60000, numbered=False)` / `pr ID --diff` — весь diff. При усечении разбей по `files`, `path=…` / `--path FILE`; каждый кусок тоже проверь на усечение. Не пропускай удаления, переименования или файлы, иначе потерю правок из target не проверить. При большом diff передай подтверждённые пути к частям в scratch либо поручение получить все части. Отметь непроверенное.
4. Один ограниченный `delegate_task(tasks=[{goal: …, context: …}])` ревьюверу: точный PR, требования, метаданные без тредов, задач на комментариях и истории прошлых кругов и полный diff или доступ к нему; «чужой PR, только разбор». Сверь с target из подтверждённого клона (`paths`, правила тега), `git show` по проверенному ref/пути. Если нужна свежая база — только разрешённый `git fetch origin <target>` в этом клоне, с явным `workdir`, проверенными ref и remote; после fetch проверь фактический ref/commit (`FETCH_HEAD` при необходимости). Не переключай ветки, не меняй рабочее дерево, не запускай код PR и не пиши наружу. Без клона — явно только diff. Если делегация недоступна, сделай проход сам.
5. Отдельный проход фильтра (`review agents --json` → `filter_agent`, по умолчанию `review-filter-sample`), ограниченный `delegate_task` или последовательно в сессии. Вход: находки, PR, target, задача и внешние замечания, включая историю прошлых кругов; выход: подтверждённые `new`/`made-reachable`, сценарий → последствие → просьба, точное `path:line` из `jwu_pr_diff(numbered=True)` / `pr ID --diff --numbered` или `reply_to`, предлагаемый статус. Убери дубли, натянутые находки и мелочи; `pre-existing` только в сводку. Покажи оставшееся, отброшенное по строке на пункт и отдельно pre-existing. Не апрувь по отсутствию находок.

## Согласование и отправка

Технические черновики → `skill_view(name="jwu-voice-rewrite")` только для чтения профиля и прохода формы, `audience=colleague`, `pr_reply`, `pr_comment` или `pr_review_body`; передай сценарий и контекст, не меняй факты. Покажи полные тексты в блоках `text`, места/адресатов и действия. «Только черновик» — покажи тексты без вопроса и без отправки. Иначе предложи одним выбором точный результат для этого PR; если пользователь уже согласовал то же превью и состояние не изменилось, не спрашивай повторно. Правка текста или цели — новое превью и согласие только на изменённое. Согласие на подготовку, молчание и письма Main не разрешают внешнюю запись. Если наружу нечего отправлять, дай итог без вопроса. Правку внеси только в черновик; профиль меняй только по просьбе запомнить правило и после согласования формулировки.

- **Комментарии** — только по явному «да» на выбранные тексты. Вопрос автора — первым ответом в тред. `jwu_pr_comment(pr_id, text, reply_to=…)` или `path=…, line=…` для inline, без полей — общий. CLI `pr-comment ID --text TEXT [--reply-to CID | --path FILE --line N] --yes --json`. Ориентируйся на numbered diff; для удаления при необходимости явно `side="FROM"` / `--side FROM`. `anchored: false` — сообщи, не отправляй повтор автоматически.
- **Задача на комменте** — только по отдельному «да», текст до 10 слов формулирует пользователь. `jwu_pr_task_add(pr_id, text, comment_id=…)` / `pr-task add ID TEXT --comment CID --yes --json` (Bitbucket, см. `jwu-pr-task`).
- **Статус** — явное «да» (можно в одной форме с комментариями, если эффект назван) именно на `APPROVED` или `NEEDS_WORK` и текст: `jwu_pr_review(pr_id, status, text)` / `pr-review ID approve|needs-work --text TEXT --yes --json` (выбери один статус). Не подменяй одним действием другое; на Bitbucket тело статуса может уйти отдельным комментарием, включи его в превью.

Перед отправкой проверь, что head/треды ещё совпадают; если изменились, обнови и согласуй затронутое заново. После перечитай PR и `jwu_pr_tasks` / `pr-task list ID --json` при задаче, сверь ids, якоря, статус и текст. При неопределённом ответе не повторяй вслепую. После проведённого ревью — локальная закреплённая `status`-заметка по `P/R#ID` (`jwu_note(..., kind="status", pin=True)` / `note KEY TEXT --kind status --pin --json`), по фактическому итогу, проверка через `notes`. Не помечай «отправлено», если остались черновики.
