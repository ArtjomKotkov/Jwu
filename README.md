# jwu

CLI для **Jira Server / Data Center + Bitbucket Server** и для **GitHub** с локальной
памятью (кэш задач/PR, дельты между синками, заметки) — и набор скиллов для Claude Code.

- **Воркспейсы** — независимые контуры (рабочий, личный): свои папки, свой **провайдер**
  задач и PR, свои данные. Определяется автоматически по текущей папке. Папки можно
  помечать тегами (`legacy-бэкенд`, `новая-версия`) — по ним понятно, где что лежит.
- **Провайдер контура** — `jira` (Jira + Bitbucket + Jenkins), `github` (Issues + PR +
  Actions) или `local` (только свои фичи). Один на проект, меняется в любой момент.
- Задачи по фильтрам: мои активные / упоминания / ждут моего ревью (PR).
- Живой TUI-дашборд с авто-обновлением.
- «Работы (jobs)» — журнал работы над задачей (фазы, баги, тесты, решения).
- **Локальные фичи** — мини-трекер для контуров без Jira: тот же журнал работ,
  ключи в формате `HOMEJWU-1` (годятся как префикс ветки и коммита).

---

## 1. Установка

Требуется **Python 3.10+**. Ставим как CLI-приложение через [pipx](https://pipx.pypa.io):

```bash
# из git
pipx install git+https://github.com/ArtjomKotkov/jwu.git

# или из локальной копии репозитория
cd jwu && pipx install .
```

Для разработки — poetry: `poetry install`, запуск `poetry run jwu …`.

## 2. Сделать доступным как `jwu`

pipx кладёт бинарь в `~/.local/bin`. Один раз добавь его в PATH и перезапусти шелл:

```bash
pipx ensurepath
```

Проверка:

```bash
jwu --help
```

Обновить после изменений — **два шага** (второй легко забыть):

```bash
pipx install --force .       # CLI и MCP-сервер
jwu install-claude-skills    # скиллы и субагенты в ~/.claude
```

MCP-сервер живёт процессом: новые инструменты `jwu_*` появятся только после перезапуска
сессии Claude Code. Для разработки удобнее `pipx install --force --editable .` — тогда
правки кода подхватываются без переустановки. Есть скилл `/jwu-update`, который делает
это и проверяет результат.

## 3. Воркспейсы и конфигурация

### Воркспейс

**Воркспейс** — контур работы: набор папок + провайдер задач и PR + свои локальные данные
(работы, фичи, заметки, анализы, снапшоты). Данные контуров не пересекаются.

Активный воркспейс определяется в таком порядке: флаг `-W/--workspace` → переменная
`JWU_WORKSPACE` → **текущая папка** (если она привязана; у вложенных выигрывает самая глубокая
привязка) → последний выбранный (`jwu workspace use`) → единственный. Не определился —
CLI объяснит, что делать, а `jwu dashboard` откроется на экране выбора.

```bash
jwu workspace list                 # все контуры
jwu workspace current              # что резолвится здесь и ПОЧЕМУ
jwu workspace create home-jwu --name "Личное" --path .
jwu workspace use work             # активный для команд вне привязанных папок
jwu workspace show                 # папки, провайдер, счётчики, настройки (секреты — ****)
jwu workspace provider             # какой провайдер сейчас и что даёт каждый
jwu workspace provider github      # сменить (локальные данные остаются на месте)
```

### Провайдер: откуда берутся задачи, PR и сборки

У проекта **один** источник правды — смешивать Jira с GitHub незачем и вредно:

| provider | задачи | PR | сборки | ключ задачи |
|---|---|---|---|---|
| `local` | локальные фичи jwu | — | — | `HOMEJWU-1` |
| `jira` | Jira (+SDESK) | Bitbucket | Jenkins | `PROJ-123` |
| `github` | GitHub Issues | GitHub PR | GitHub Actions | `dndeck#42` |

Провайдер объявляется при создании и меняется командой `jwu workspace provider <name>`:
работы, фичи, заметки и правила при этом остаются на месте — меняется только то, откуда
приезжают задачи и PR. У `jira`-контура Bitbucket остаётся отдельным флажком
(`--bitbucket/--no-bitbucket`): Jira без Bitbucket встречается, GitHub без своих PR — нет.

Что jwu умеет одинаково у обоих провайдеров: списки «мои»/«на ревью», карточка задачи
со связанными ветками и PR, комментарии PR с куском диффа, статусы и разбор упавших
сборок, привязка PR к работам. Чего у GitHub нет: **таймтрекера** — `jwu worklog`
там честно откажет (учитывай время записями работы).

### Папки и теги — «где что лежит»

Папки воркспейса отвечают на вопрос, **где находится код проекта**: скиллы ищут и правят
только в них. Теги объясняют, что есть что, когда репозиториев несколько.

```bash
jwu workspace add-path ~/dev/backend --tag legacy-бэкенд --tag django
jwu workspace add-path ~/dev/backend-v2 --tag новая-версия
jwu workspace tag ~/dev/front --add фронт          # пометить уже привязанную
jwu workspace paths                                # все папки с тегами
jwu workspace paths --tag legacy-бэкенд            # найти нужную
```

Теги видны и в дашборде (вкладка «Структура»), и агенту — через `jwu_workspace_paths(tag=…)`.

### Правила воркспейса

Папки и теги говорят, ГДЕ лежит код. Правила — то, что знает о проекте человек, но не знает
код: что нельзя делать, как поднять стенд, где что лежит. Они хранятся рядом с контуром и
**сами приезжают в контекст при работе над любой задачей**, так что пересказывать их каждую
сессию больше не нужно.

Пять типов: `constraint` (⛔ запрет), `howto` (🛠 как делать), `convention` (📐 соглашение),
`gotcha` (⚠ грабли), `info` (ℹ справка). Правило либо общее для контура, либо привязано
к тегу папки — тогда оно относится только к этому репозиторию.

```bash
jwu rule add "Не пушить в develop напрямую" --kind constraint
jwu rule add "Как поднять стенд" --kind howto --tag legacy-бэкенд --file -   # текст из stdin
jwu rules                      # всё
jwu rules --tag legacy-бэкенд  # правила этого репо И общие (общие действуют везде)
jwu rule show 2 · jwu rule edit 2 --kind info · jwu rule rm 2
```

Агент получает контекст проекта одним куском — и в `jwu_workspace_current()`, и в ответе
`jwu_job_start()` (то есть правила и структура доезжают до первой правки, даже если скилл
поленился): `paths` с тегами и `known_tags` — JSON, его фильтруют; `rules_md` — готовый
markdown, его читают и исполняют. Общие правила там целиком, у правил конкретных
репозиториев — только заголовки; полный текст берётся вторым вызовом `jwu_rules(tag=…)`,
когда уже понятно, где правим. Иначе инструкция по стендам уезжала бы в контекст каждого
скилла, включая те, что до кода не доходят. Записи `⛔ ЗАПРЕТ` скиллы обязаны соблюдать,
а не обходить молча.

В дашборде правила живут на вкладке **Правила** (нижний ряд, сразу за «Структурой»):
`enter` — карточка с полным текстом, `N` — добавить, `e` — править, `D` — удалить.
Так «поправь в legacy-бэкенде» перестаёт быть загадкой.

Провайдер объявляется **явно** при создании (`--provider local|jira|github`). В локальном
контуре команды задач не молчат, а отказывают с подсказкой; вкладки задач и PR в дашборде
скрываются, вместо них — «Фичи».

### Доступы

Визард спрашивает хосты, логин, токен/пароль и путь до БД, сохраняет в **активный воркспейс**
и проверяет связь:

```bash
jwu configure            # текущий воркспейс
jwu configure -W work    # конкретный
jwu auth check
```

Настройки и секреты воркспейса хранятся **в БД jwu** (`~/.local/share/jwu/state.db`).
Секреты лежат там **в открытом виде**; файл закрывается правами 600, каталог бэкапов — 700.

> ⚠️ Не держи БД в облачной папке (iCloud/Dropbox/Google Drive): туда уедут токены.
> jwu предупредит об этом сам. Нужен облачный синк — задавай токены переменными окружения.

Сеть мигает — jwu повторяет GET-запросы при таймауте, обрыве и 502/503/504 (два повтора с
паузой) и не роняет синк целиком из-за одного сервиса. Настройка: `JWU_HTTP_TIMEOUT`
(секунды, по умолчанию 30) и `JWU_HTTP_RETRIES` (по умолчанию 2; 0 — без повторов).

**Переменные окружения перекрывают БД** (удобно на серверах и в CI):
секреты — `JIRA_TOKEN`, `JIRA_PASSWORD`, `JIRA_GATE_PASSWORD`, `SDESK_TOKEN`, `SDESK_PASSWORD`,
`SDESK_GATE_PASSWORD`, `BITBUCKET_TOKEN`, `GITHUB_TOKEN`, `JENKINS_TOKEN`, `TELEGRAM_BOT_TOKEN`;
настройки — `JWU_JIRA_URL`, `JWU_JIRA_USER`, `JWU_JIRA_PROJECT`, `JWU_JIRA_GATE_USER`,
`JWU_SDESK_URL/PROJECT/USER/GATE_USER`, `JWU_BITBUCKET_URL/PROJECT/REPO`,
`JWU_GITHUB_API/WEB/OWNER/REPOS/USER`, `JWU_JENKINS_URL/USER`, `JWU_TELEGRAM_CHAT`.
Так контур поднимается «безголово» — без визарда и keyring: `jwu init . --provider jira
--bitbucket --yes` плюс переменные, и `jwu doctor` скажет, чего не хватает.

**`jwu doctor`** — одна команда про всё: БД (путь, облачная папка, права, схема), воркспейс
и его папки на диске, полнота конфига под провайдера, доступы к каждому сервису (с
`--offline` — без сети), Telegram, демон, MCP-сервер в `~/.claude.json`, актуальность
скиллов в `~/.claude/skills`, версия кода против установленной.

Неинтерактивно (CI/серверы):

```bash
jwu configure --non-interactive \
  --jira-host https://jira.acme.com --jira-user alice --jira-token "$JIRA_TOKEN" \
  --bitbucket-host https://git.acme.com --bitbucket-token "$BITBUCKET_TOKEN"
```

Если перед Jira стоит nginx Basic-гейт — `--gate-user/--gate-password`.

Для GitHub-контура нужен только PAT — classic со scope **`repo`** (для публичных
репозиториев хватит `public_repo`). Он покрывает всё, что jwu читает: Issues, PR,
комментарии, check-runs и логи Actions. Fine-grained-токен тоже подходит: права
`Metadata`, `Issues`, `Pull requests`, `Actions` — на чтение. Токен заводится тут:
<https://github.com/settings/tokens>.

```bash
jwu workspace provider github
jwu configure --non-interactive \
  --github-owner akotkov --github-repos dndeck,dndeck-ui --github-token "$GITHUB_TOKEN"
```

`owner` — организация или пользователь, чьи репозитории считаются своими; он же
ограничивает выборку. `--github-repos` сужает её ещё точнее, до перечисленных
репозиториев; без него берутся все репозитории owner'а. **Без owner'а область поиска
пуста, и `assignee:@me` уедет искать по всему GitHub** — задачи из чужих проектов
попадут в список. GitHub Enterprise задаётся через `--github-api https://ghe.example.com/api/v3`
и `--github-web https://ghe.example.com`.

> Флаг `-W` — глобальный и идёт **до** подкоманды: `jwu -W dndeck configure …`,
> а не `jwu configure -W dndeck …`.

**Если задач не видно, а токен валиден** — почти всегда дело в области видимости токена,
а не в jwu. Проверяется так:

```bash
jwu auth check                       # ✓ github (Имя) — токен рабочий
jwu workspace show                   # тот ли owner и репозитории
```

Репозитории **организации** видны не любому токену:

- **fine-grained** — при создании выбирается *Resource owner*, и поменять его потом нельзя.
  Если там личный аккаунт, репозитории организации токену недоступны в принципе: в списке
  «Only select repositories» их попросту нет. Нужен новый токен с Resource owner =
  организация; если она требует одобрения, владелец подтверждает его в
  *Organization settings → Personal access tokens*.
- **classic** — про Resource owner ничего не знает и работает с репозиториями организации
  сразу; при SAML SSO нужно нажать *Configure SSO → Authorize* рядом с токеном.

Resource owner решает только, **куда токену разрешено смотреть**, а не «чьи задачи
показывать»: токен действует от твоего имени и больше твоих прав не получает, а вкладка
«Мои задачи» фильтрует по `assignee:@me` в любом случае.

### Переезд со старой версии

Ничего делать не нужно: при первом запуске старый `~/.config/jwu/config.toml` и секреты из
системного keyring переносятся в воркспейс **«Работа»** (`work`), все накопленные работы и
снапшоты достаются ему же. Перед структурной миграцией снимается копия БД
(`~/.local/share/jwu/backups/state.db.pre-v<N>-<дата>`). Keyring **не чистится** и остаётся
фолбэком на чтение, поэтому откат на прежнюю версию jwu ничего не ломает.
Перенести вручную: `jwu workspace migrate`.

**Путь до БД** остаётся глобальным (`[storage].db_path` в config.toml, `jwu configure --db-path …`
или env `JWU_DB_PATH`) — её надо найти до того, как известен воркспейс. jwu раз в день делает
локальный бэкап и проверяет целостность. Не запускай jwu на двух устройствах одновременно
поверх одной БД в облаке (риск конфликта файла).

### Размер БД и чистка снапшотов

Снапшоты задач и PR нужны только для сравнения соседних синков, но копятся вечно — на
рабочей базе это десятки тысяч строк и гигабайты файла, которые вдобавок каждый день
копирует бэкап. Поэтому jwu **раз в день сносит снапшоты старше 30 дней** — но только если
файл БД перевалил за 256 МБ и только **после** сегодняшнего бэкапа (чистка необратима).

Сохраняется всё, на чём держится расчёт дельт: свежайший снапшот каждой задачи и PR,
свежайший снапшот с достоверной dev-панелью и последние надёжные прогоны каждой вкладки.
Иначе следующий синк объявил бы половину задач новыми, а половину — ушедшими.

`VACUUM` (пересборка файла, десятки секунд на гигабайте) делается только когда после
чистки освободилось больше 25% файла.

```bash
jwu db stats                 # сколько занимает и из чего состоит
jwu db prune                 # сухой прогон: что удалилось бы (по умолчанию)
jwu db prune --apply         # собственно удалить
jwu db prune --apply --vacuum
jwu db vacuum                # вернуть освободившееся место ОС
```

## 4. Дашборд и авто-синк

```bash
jwu dashboard            # TUI из памяти (быстро, без сети)
jwu dashboard --sync     # сначала синхронизировать всё, потом открыть
jwu dashboard -a         # авто-обновление (см. ниже)
```

Режим `-a` (`--auto-update`):
- локальные вкладки (Работы/Фичи) — из памяти каждые **5с** (`--fast-interval`);
- сетевые таблицы (задачи/PR) — фоновый синк каждые **10 мин** (`--slow-interval`);
- открытый детальный экран — раз в **60с** (`--detail-interval`).

Дашборд открывается на том воркспейсе, где ты его закрыл: его держат одним окном и
переключают руками (`W`), поэтому папка запуска для него не указ. Всем остальным командам,
скиллам и MCP папка по-прежнему важнее — они работают в контексте проекта, из которого их
позвали. Перебить и то и другое можно флагом `-W`.

Вкладки идут **двумя рядами**. Наверху — **Workspace**, выбор контура: это единственное,
что не зависит от того, какой воркспейс активен. Внизу — всё его содержимое: **Структура**
(дерево папок) и **Правила** (что агент обязан знать о проекте) идут первыми — с них
начинают в незнакомом контуре, — дальше **Мои задачи**/**Упоминания** (при провайдере
Jira или GitHub), **PR: мои**/**PR: на ревью** (когда есть откуда их брать), **Фичи**
(наоборот, только в локальном контуре) и **Работы** (всегда). Ряд, которому активная вкладка не принадлежит, приглушён.
`[` и `]` листают все видимые вкладки подряд, обоими рядами.

Панель **Изменения** (`b`) показывает изменения только активной вкладки и группирует их
по сущностям: заголовок «ключ: название» и под ним список того, что в ней случилось
(новые комментарии, смена статуса, апрувы, конфликт). `c` — очистить активную вкладку,
`C` — все.

**Упоминания** — это сами упоминания, а не задачи: каждое найденное `[~логин]` в комментарии
становится отдельной записью один раз и дальше не меняется, за задачей никто не следит.
Непрочитанные помечены точкой, счётчик на вкладке — это их число; карточка задачи тянется
из сети только при заходе внутрь (`enter`), и он же снимает пометку.

На вкладке **Работы** строки разбиты по дням: заголовок дня — черта во всю таблицу с
подписью «Сегодня — 30.07.2026» (сначала словами, потом дата; свежесть видна цветом),
а закончившийся день отбит от следующего пустой строкой. Разбивка работает при сортировке
по времени (по умолчанию); отсортируешь по другой колонке — черты пропадут.

На вкладке **Структура** папки показаны деревом: `→`/`←` (или мышь) раскрывают и сворачивают,
у каталогов-репозиториев виден маркер `имя/ветка`, рядом — теги папки. Структура
переиндексируется в фоне, интервал — `--index-interval` (по умолчанию 120 с).

Экран по умолчанию занят только данными: панель **Изменения** скрыта (`b` — показать/убрать),
поиск задачи — модалка по `/`, а легенда клавиш — модалка по `?`. Легенда собирается под то
окно, где ты стоишь: сверху клавиши текущей вкладки или карточки, ниже общие. Внизу остаётся
одна строка состояния — синк, память, кто ты.

Клавиши: `?` — легенда, `/` — поиск задачи, `b` — панель изменений, `enter` — детали,
`o` — открыть (браузер или файловый менеджер), `y` — скопировать ключ, `Y` — меню копирования,
`R` — синк всего, `c` — очистить изменения вкладки, `W` — быстрый выбор воркспейса,
`N` — создать (воркспейс, фичу или правило — по вкладке), `a` — добавить папку,
`D` — удалить/отвязать выбранное, `q` — выход.

**Буфер обмена (`y` / `Y`):** `y` — сразу ключ Jira (или ключ задачи у работы); `Y` — модалка с
атрибутами (URL, markdown-ссылка, заголовок и др. — набор зависит от контекста). Навигация ↑↓ /
`j` `k`, копирование — `enter`, клик или горячая клавиша пункта. jwu использует
[pyperclip](https://pypi.org/project/pyperclip/)
— он уже ставится вместе с пакетом. На **macOS** и **Windows** дополнительно ничего не нужно. На
**Linux** нужна утилита для работы с clipboard в вашей сессии:

| Среда | Пакет |
|---|---|
| X11 | `xclip` или `xsel` |
| Wayland | `wl-clipboard` (команда `wl-copy`) |

Примеры: `sudo apt install xclip` (Debian/Ubuntu, X11), `sudo apt install wl-clipboard` (Wayland).
Без этих утилит копирование покажет ошибку в уведомлении TUI.

Без TUI: `jwu sync` — разовый полный синк.

### Бэкап и переезд

```bash
jwu backup --out ~/Desktop            # jwu-backup-<дата>.tar.gz: БД (VACUUM INTO), config.toml,
                                      # проектные субагенты/скиллы из ~/.claude, RESTORE.md, SHA256SUMS
jwu backup --no-secrets               # копия БД без токенов
jwu restore ~/Desktop/jwu-backup-2026-09-11.tar.gz [--force] [--db-only] [--dry-run]
```

`restore` проверяет контрольные суммы и целостность базы, существующую БД не трогает без
`--force` (и тогда оставляет копию рядом), путь до БД в `config.toml` переписывает под эту
машину. Слить две базы без потерь — не `restore`, а `jwu memory import`.

### Память отдельно от кэша

В `state.db` лежат две разные вещи: **кэш** (снапшоты задач и PR — сотни мегабайт,
восстановимы одним синком) и **память** (работы с записями, заметки, правила, фичи,
воркспейсы с папками и тегами — мало и заново не соберёшь). Память выгружается в каталог
обычных JSON-файлов и сливается обратно по естественным ключам — повторный импорт ничего
не задваивает, ничего не удаляет. Секреты и снапшоты туда не попадают никогда.

```bash
jwu memory export --dir ~/jwu-memory          # JSON по воркспейсам
jwu memory import ~/jwu-memory --dry-run      # что изменится; без --dry-run — слить в БД
jwu memory sync --repo ~/jwu-memory           # pull → импорт → экспорт → commit → push
```

`sync` рассчитан на **свой приватный** git-репозиторий памяти (не на репозитории проектов):
две машины сходятся к одному состоянию без ручного разбора JSON. Каталог запоминается,
дальше хватает `jwu memory sync`.

### Фоновый синк (демон)

Дашборд синкает только пока открыт. Чтобы дельты копились и уведомления уходили без
открытого окна, есть демон: раз в `--interval` секунд проходит по всем контурам с внешним
провайдером (Jira/GitHub), синкает каждый и запускает хуки после синка (уведомления —
см. ниже). Один экземпляр на машину (файловый лок в каталоге данных), ошибка одного
контура не мешает остальным, лог — `~/.local/share/jwu/daemon.log`.

```bash
jwu daemon run --once            # один проход руками — проверить, что всё синкается
jwu daemon install --interval 600   # службой: launchd (macOS) / systemd --user (Linux)
jwu daemon status                # установлена ли служба, жив ли процесс, последний проход
jwu daemon uninstall
```

Служба стартует при входе и перезапускается сама. `JWU_DB_PATH`, если задан в окружении
при установке, прописывается в службу явно — вне шелла переменных пользователя у неё нет.

### Задачи на комментах PR

В Bitbucket Server под комментом PR можно повесить **задачу** — строку с чекбоксом.
jwu делает из них чек-лист правок по PR: `jwu pr <id>` показывает задачи под своими
комментами, `jwu prs` и дневной анализ считают состояние `открытые задачи: N`, синк даёт
дельты `new_pr_task` / `pr_task_resolved`. В работы задачи не зеркалятся — список один,
и он в PR: его видят и ревьювер, и Claude.

```bash
jwu pr-task list 893 --project WEBIM --repo django-chat
jwu pr-task add 893 "Убрать лишний запрос в цикле" --comment 41512 --yes   # на чужой коммент
jwu pr-task add 893 "Добавить тест на пустой фильтр" --file src/x.py --line 12 --yes  # свой inline-коммент + задача
jwu pr-task done 77 78 --yes                                              # закрыть пачкой
```

Текст задачи — не длиннее 10 слов (лимит стоит в инструменте, а не в скилле), без `--yes`
команды только показывают превью. Скилл `/jwu-pr-task` спрашивает текст у пользователя и
ничего не создаёт без явного «да». Только Bitbucket: у GitHub такого механизма нет.

### Уведомления в Telegram

После **каждого** сетевого синка (руками, из дашборда, из демона, из day-analyze) jwu
отбирает из дельт то, что требует действия, и шлёт одним сообщением в Telegram:
конфликт, красный билд, `needs work` от ревьювера, новая задача на комменте PR, возврат
задачи с тестов, комментарий тестировщика и новые упоминания. Апрувы чужих PR и
исчезновения из выборки не шлются — они подождут дашборда. Сообщение либо уходит сразу,
либо теряется: очереди и повторов нет, чтобы не задваивать.

Нужен бот (@BotFather → токен) и `chat_id` личного чата с ним или группы:

```bash
jwu configure --non-interactive --telegram-chat 123456789 --telegram-token "$TELEGRAM_BOT_TOKEN"
jwu notify status      # включены ли, какие события уходят
jwu notify test        # тестовое сообщение — проверка токена и чата
```

Токен — секрет воркспейса (слот `telegram.token`, переменная `TELEGRAM_BOT_TOKEN`
перекрывает), `chat_id` — обычная настройка. Пустой `chat_id` выключает уведомления.

## 5. Скиллы и субагенты для Claude

В репозитории шипуются и **скиллы** (`src/jwu/skills/<имя>/SKILL.md`), и **дефолтные субагенты**
(`src/jwu/agents/<имя>.md`) — можно взять прямо из git.

**Claude Code** — установить одной командой (копирует скиллы в `~/.claude/skills` и субагентов
в `~/.claude/agents`, обновляя существующие):

```bash
jwu install-claude-skills                   # каталог скиллов — флагом --dest
                                            # каталог агентов — флагом --agents-dest
                                            # пропустить агентов — флагом --skip-agents
```

**Другой агент / не Claude** — скорми содержимое нужного `SKILL.md` из `src/jwu/skills/`
своему инструменту (это обычные markdown-инструкции, без привязки к Claude).

### Вызов скиллов в Claude Code

Подхватываются **автоматически по фразам-триггерам**, либо явно слэш-командой:

| Скилл | Когда / как |
|---|---|
| `/jwu-workspace-setup` | «подключи jwu к этому проекту», «jwu не видит мою папку» — завести/подключить воркспейс (`jwu init`), привязать репозитории, расставить теги |
| `/jwu-update` | «обнови jwu», «нет инструмента jwu_*», «скилл не подхватился» — переустановка пакета + скиллов и диагностика старого MCP-сервера |
| `/jwu-start-job` | «начни работу по ABC-123», «проанализируй задачу» — анализ + план + создание работы (последняя фаза = ревью) |
| `/jwu-resume-job` | «на чём остановились», после очистки контекста — восстановить состояние работы |
| `/jwu-track-job` | «запиши баг/решение/прогон тестов», «отметь фазу done» — лог прогресса |
| `/jwu-job-review <reviewer-subagent>` | «прогони ревью», «code review этого PR» — запуск явно указанного субагента-ревьювера с контекстом задачи+PR+диффа; результат пишется в работу записями `--kind review` (шапка с якорями `[B*]/[I*]/[M*]`) + детальные `remark`/`bug`/`warning`/`constraint` |
| `/jwu-commit-message` | «напиши коммит», «коммит-месседж» — генерирует текст из текущих изменений (staged + unstaged); префикс `EXAMPLE-1111:` подставляется из имени ветки, нет префикса → без него; печатает текст, `git commit` делает пользователь |
| `/jwu-task-create` | «заведи задачу», «оформи баг задачей» — собрать текст, проверить поля по `createmeta` и дубли, показать пользователю и завести только после явного «да»; `--from-job` берёт описание из лога работы |
| `/jwu-task-comment` | «напиши комментарий в задачу», «ответь клиенту в SDESK» — показать текст целиком и отправить после «да»; для SDESK (его читает клиент) подтверждение строже |
| `/jwu-task-status` | «переведи в In Progress», «какие статусы доступны» — сначала доступные из текущего статуса переходы, потом выбранный |
| `/jwu-task-attach` | «приложи har к задаче» — показать файлы и предупредить о содержимом, загрузить после «да» |
| `/jwu-context` | «что я знаю по задаче», «почему висит PR», «запиши, что по задаче …» — контекст сущности без разбора работ: `jwu_context(key)` читает заметки, закреплённый статус, последнюю работу и снапшот; `jwu_note` пишет |
| `/jwu-pr-comment` | «ответь в PR», «напиши под замечанием, что поправил», «апрувни / поставь needs work» — ответ ревьюверу в тред, коммент на строку, свой статус ревью; дифф без клона через `jwu_pr_diff`; текст показывается целиком, отправка только после «да» |
| `/jwu-pr-task` | «повесь задачу на коммент», «заведи таску в PR» — задача-чекбокс под комментом PR в Bitbucket: текст формулирует пользователь (до 10 слов), создание и закрытие только после «да»; открытые задачи — чек-лист правок, который видят и ревьювер, и Claude |
| `/duty-support` | «посмотри дежурку», «разбери тред» — обращения техподдержки из мессенджера: обзор новых вопросов либо разбор треда по коду с вердиктом и черновиком ответа. Ничего не постит |
| `/jwu-prompt-refine` | «подготовь промпт», «перепиши задание для новой сессии» — из черновика собрать самодостаточный промпт: заземлить в коде, задать только решающие вопросы, отдать файлом. Код не правит |
| `/jwu-task-branches` | «есть ли фикс в версии клиента», «в какие ветки доехала задача» — только чтение, по dev-панели и локальным клонам |
| `/jwu-analyze-day` | «разбери мой день» — план по задачам и PR на сегодня |
| `/jwu-post-analyze-day` | «что я сделал сегодня» — итоги для трекинга времени |

### Дефолтные субагенты

| Субагент | Когда |
|---|---|
| `reviewer-jwu-sample` | Универсальный код-ревьювер по 10-пунктовому чек-листу (баги, безопасность, нейминг, миграции, потеря правок из target, и пр.). Используется `/jwu-job-review` как дефолт, если для проекта нет более специфичного ревьювера. |
| `duty-support-sample` | Аналитик дежурства: разбирает обращение техподдержки из мессенджера — читает тред, скачивает вложения (скрины, har, логи), сверяет гипотезы с кодом нужной версии и отдаёт вердикт, черновик ответа в тред и ответ клиенту. Наружу ничего не постит. Используется `/duty-support` как дефолт. |

Свой проектный ревьювер (напр. `reviewer-myproject-django`) или свой субагент дежурства
добавляется как обычный субагент Claude Code в `~/.claude/agents/` и вызывается тем же скиллом:
`/jwu-job-review reviewer-myproject-django`. Проектный субагент главнее образца из поставки —
образец знает методику, но не знает названий твоих комнат, аккаунтов и репозиториев.

## Команды

Глобальный флаг `-W/--workspace <slug>` (или env `JWU_WORKSPACE`) выбирает воркспейс
для любой команды; без него он определяется по текущей папке.

| Команда | Что делает |
|---|---|
| `jwu workspace …` | воркспейсы: `list`/`create`/`use`/`current`/`show`/`provider`/`add-path`/`remove-path`/`tag`/`paths`/`rename`/`delete`/`migrate` |
| `jwu feature …` | локальные фичи: `add`/`list`/`show`/`status`/`edit`/`rm` (алиас `jwu features`) |
| `jwu rule …` | правила воркспейса: `add`/`list`/`show`/`edit`/`rm` (алиас `jwu rules`) |
| `jwu changes` | дельты с прошлого синка |
| `jwu configure` | настройка хостов/логинов/секретов воркспейса (`-W`), путь до БД |
| `jwu db …` | файл БД: `stats` / `prune` (по умолчанию сухой прогон) / `vacuum` |
| `jwu dashboard` | живой TUI (`--sync`, `-a`) |
| `jwu auth check` | проверка доступов контура (Jira/Bitbucket либо GitHub). 401 «ключ протух»: сессию Jira клиент переустанавливает сам, а сменившиеся креды долгоживущий MCP-сервер подхватывает инструментом `jwu_auth_refresh` |
| `jwu sync` | разовый синк вью + PR, снапшот в память, расчёт дельт |
| `jwu action day-analyze [--brief]` | контекст + промпт для дневного анализа; `--brief` — только требующее действия (без `gone`/`pr_gone`, без чужих апрувов на PR, где я ревьювер, только ждущие меня PR и свежие непрочитанные упоминания) |
| `jwu mentions list\|read\|archive` | упоминания меня без дашборда: список (`--unseen`), пометить прочитанными, убрать старше N дней |
| `jwu workspace thresholds [--stale-pr N] [--approval-wait N] [--review-wait N] [--testing N] [--mention-days N]` | пороги «давно» для дневного анализа — раздел «Застряло» называет каждый застрявший PR и задачу явно |
| `jwu doctor [--offline]` | диагностика окружения и доступов одной командой (`--json` для агентов) |
| `jwu backup [--out] [--no-secrets]` / `jwu restore <архив> [--force]` | переезд между машинами: архив с БД, конфигом, проектными субагентами/скиллами и RESTORE.md; восстановление с проверкой сумм |
| `jwu memory export\|import\|sync` | память (работы, заметки, правила, фичи, воркспейсы) как JSON без секретов и снапшотов; `sync` — через свой приватный git |
| `jwu daemon run\|install\|status\|uninstall` | фоновый синк всех контуров без дашборда; `install` ставит службу launchd/systemd |
| `jwu notify status\|test` | уведомления в Telegram после синка: настроены ли, тестовое сообщение |
| `jwu pr <id> --diff [--path f]` | unified diff PR без клона (Bitbucket и GitHub); большой PR — по файлам |
| `jwu pr-comment <id> -m … [--reply-to CID \| --path f --line N]` | комментарий в PR: общий, ответ в тред замечания, на строку; только после подтверждения / `--yes` |
| `jwu pr-review <id> approve\|needs-work\|unapprove [-m …]` | мой статус ревью на PR (`unapprove` — только Bitbucket; у GitHub `needs-work` требует текст); только с `--yes` |
| `jwu pr-task list\|add\|done\|reopen` | задачи на комментах PR (Bitbucket tasks) — чек-лист правок; `add`/`done` пишут в Bitbucket только с `--yes`, текст задачи до 10 слов |
| `jwu tasks --view mine\|mentions` | список задач (есть `--jql`) |
| `jwu task ABC-123` | полная карточка: описание, комменты, связанные ветки и PR (у GitHub ключ — `repo#42`) |
| `jwu attachments ABC-123 [--download]` | вложения задачи; у каждого `referenced_by` — в каком комментарии / описании оно вставлено (`!name.png!`), у комментария — `images` |
| `jwu prs --view mine\|review` / `jwu pr <id>` | PR с ревьюерами, статусом конфликта и сводным статусом CI-сборки (`build_state`); красный билд — состояние PR и дельта `build_failed` / `build_fixed`. `jwu pr <id> --download` качает скриншоты из описания PR и комментов ревью (у каждого — `comment_id` якоря) |
| `jwu note <ключ> "…" [--kind status\|decision\|gotcha\|todo\|context]` / `jwu notes <ключ>` | заметки-контекст по задаче, PR (`PROJ/repo#42`) или ветке; `status` — одна закреплённая строка «почему висит», видна в `jwu prs`, дневном анализе и карточках. `jwu job done` сам пишет выжимку работы в контекст |
| `jwu issue create -p PROJ -s "…" -F ./task.md` | завести задачу: поля сверяются с `createmeta` проекта, показываются похожие задачи, `--dry-run` печатает payload, без `--yes` ничего не создаётся; `--from-job <ID>` собирает описание из лога работы |
| `jwu issue link KEY1 KEY2 --type Relates` | связать задачи (`jwu issue link-types` — какие типы знает инстанс) |
| `jwu issue similar -p PROJ -s "…"` | похожие по тексту задачи проекта — проверка на дубль до создания |
| `jwu issue transitions KEY` / `jwu issue transition KEY "In Progress"` | доступные сейчас переходы по процессу и перевод по выбранному |
| `jwu issue attach KEY ./log.har` | приложить файлы к задаче (обратное к `jwu attachments --download`) |
| `jwu comment KEY -F ./answer.md` | комментарий в задачу; для SDESK (его читает клиент) обязателен `--to-client` |
| `jwu task KEY --branches` | в какие релизные ветки доехал фикс задачи, а в какие нет (по локальным клонам) |
| `jwu worklogs --on 2026-08-31` | что затрекано за день; без ключей задачи находятся сами |
| `jwu job …` | работы: `start`/`add`/`show`/`done` и т.д.; якорь — задача Jira, локальная фича (`--feature`) либо ничего. `add` запоминает ветку и коммит HEAD текущей папки (читает `.git`, в git не пишет) |
| `jwu job handoff <id>` | передача работы другой сессии: самодостаточный markdown — задача, где стоять в git, сделано/осталось, PR с блокерами и открытыми задачами, правила; `--offline` без сети |
| `jwu install-claude-skills` | развернуть скиллы в `~/.claude/skills` и дефолтных субагентов в `~/.claude/agents` |

У большинства команд есть `--json` (для интеграции с агентами).
