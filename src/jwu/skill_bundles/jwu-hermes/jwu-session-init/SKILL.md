# jwu: контекст сессии Hermes

Зависимости этого комплекта загружай через `skill_view` по точному пути `jwu-hermes/<имя>`, не из старой категории `jwu`. Рабочую папку задачи не меняй ради загрузки скиллов.

## Вход по поручению

Каждый запущенный воркер проходит этот инит сам, из папки назначения: контекст оркестратора не подтверждает его собственный контур. Сам инит ничего не берёт. Итог и рабочие вопросы передавай связанному оркестратору по `jwu-hermes/jwu-orchestrator`; уведомление от агента может запустить обработку, но не заменяет согласие пользователя. После проверки папки и правил переходи к действию из брифа без общего меню «что взять»: для назначения с доски — **jwu-start-job**, раздел «Вход по поручению с доски» (своё имя сессии, свой показ, точные ключи); для подтверждённой передачи конкретной работы — **jwu-continue-job** по ID. При запросе только на инициализацию или осмотр остановись после сводки. Если ты оркестратор, передавай поручение через **jwu-orchestrator**: работу берёт и ведёт сам воркер.

Перед действиями через jwu установи реальную папку проекта Hermes. Для `terminal` передавай её явно как `workdir`; не используй cwd из предыдущего проекта. Запроси `jwu workspace current --json` в этой папке и проверь `source == "cwd"`, непустой `slug`, отсутствие ошибки. Если CLI падает при импорте `pydantic_core` из несовместимого окружения Hermes, повтори вызов как `env -u PYTHONPATH jwu workspace current --json` в той же папке; не меняй окружение всей сессии. При несовпадении остановись: активный, единственный или заданный через окружение контур не подтверждает привязку папки. Не выполняй `jwu init` автоматически.

Если доступен MCP `jwu`, вызови `jwu_workspace_current` (обычно `mcp_jwu_jwu_workspace_current`). Используй его только если `source`, `slug` и `cwd` совпадают с проверенным контуром и папкой проекта. MCP-процесс может работать из другой папки даже после смены проекта в Desktop; тогда оставайся на CLI для этой сессии. Для последующих MCP-вызовов передавай `workspace=<проверенный slug>`, если параметр поддерживается. Для CLI — `jwu --workspace <slug> …` с тем же `workdir`.

1. Прочитай общие правила из `rules_md` или `jwu --workspace <slug> rules --json`. Когда известен тег репозитория, дотяни `jwu_rules(tag=…)` / `rules --tag <tag> --json`. Если правило ссылается на инструкцию, открой её по имени, а не угадывай процедуру.
2. Проверь активные работы (`jwu_jobs(status="active")` / `jobs --status active --json`) и планы (`jwu_plan_now` / `plan now --json`). Для `provider=local` посмотри `jwu_features` / `feature list --status open --json` и `--status in_progress`; задачи и PR из внешних трекеров не запрашивай. Сам инит не обновляет доску и не ходит во внешние сервисы. На «покажи доску» или «обнови доску» перейди к **jwu-todo**: оркестратор тоже показывает доску без взятия работ.
3. Коротко сообщи контур, провайдер, существенные запреты, активные работы и планы. Не создавай jobs, не меняй статусы и не запускай воркеров. Повтори проверку при смене проекта или если подтверждённые правила выпали из контекста.

## Как говорить с пользователем

Пиши простым русским, как коллеге. Это касается всего чата: объяснений, коротких обновлений, итогов и кнопок. Начни с того, что произошло и что это значит для работы. Если нужен ответ, сразу скажи, что именно нужно решить, что ты рекомендуешь и что изменится после выбора. Если ничего не нужно, не заставляй пользователя угадывать, ждёшь ли ты его.

Используй обычные глаголы и короткие предложения. Не переноси в ответ слова из журнала, ключи инструментов и цепочки сокращений. Номера задач, ссылки, точные ошибки и команды оставляй, когда они помогают проверить результат. Если термин нужен, объясни его через последствие, а не через другой термин. Кнопка должна называть действие или результат, а не внутренний этап. Не упрощай за счёт точности: «не повторилось» не значит «исправили», а «ветка отправлена» не значит «PR открыт».

- Вместо «CI запущен, job в done»: «Сборка запущена. Работу в Jwu закрыл, результат тестов пока неизвестен».
- Вместо «нужно исключение на публикацию»: «Проверка миграций падает и без наших правок. Отправить исправление и открыть PR, не меняя миграции?» Кнопка: «Отправить исправление и открыть PR». Такой выбор уместен только если правила разрешают продолжить при этом сбое.
- Вместо «ожидаю дальнейшего решения»: «Проверки прошли. Предлагаю отправить ветку и открыть PR» — и покажи кнопки, если это ещё не согласовано.

**Один вопрос — одно решение.** Перед вопросом проверь запрос и предыдущий выбор. Если пользователь уже согласовал точное действие и условия не изменились, продолжай без нового «да». Для нескольких готовых, связанных шагов предложи один понятный результат с перечислением действий. Независимые решения можно спросить в одной форме; зависимое уточнение задавай только если оно действительно меняет результат. Превью внешней записи, обязательные проверки и отдельный допуск Git остаются обязательными. Не спрашивай по итогам простого просмотра, если от пользователя ничего не нужно.

Перед отправкой проверь: понятно ли с первого прочтения, что случилось и нужно ли что-то делать? Не добавляй служебный отчёт вторым слоем. Это правило про речь, а не про разрешения или формат сообщений между ботами.

Эталоны формулировок для `clarify`: [references/clarify-menu-russian.md](references/clarify-menu-russian.md).

## Проверка перед завершением каждого хода

После обсуждения, патча, тестов, ревью или фонового результата определи ближайший безопасный шаг. Если он уже согласован — продолжай без повторного вопроса. Если нужно новое согласие, решение или действие пользователя — в этом же чате и ходе коротко скажи, что сделано, что мешает и что рекомендуешь, затем вызови нативный `clarify` с `questions` и `choices`. Первой кнопкой — рекомендуемый шаг, второй — безопасная альтернатива или пауза. Карточка уведомляет пользователя: отчёт, запись `waiting` и `[SILENT]` её не заменяют. При недоступной форме покажи варианты текстом и жди ответа. Не дублируй живую карточку и не переоткрывай явную паузу без новой причины. Если ждёшь только внешний результат, назови его без фиктивного запроса согласия.

Это не замена git-хуку jwu: наличие MCP и скила не означает, что shell Hermes автоматически блокирует пишущие git-команды.
