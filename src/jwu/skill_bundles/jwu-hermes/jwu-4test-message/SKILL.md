# 4test: что и как проверить

Это черновик для копирования, не публикация. Сценарий из аддона `webim-work`, но для чтения работы, задачи и диффа достаточно основного jwu и локального git. Для персонализации нужен профиль голоса jwu и доступный проход редактора; отсутствие аддона не мешает собрать техническую инструкцию.

## Контур и источники

Сначала загрузи `jwu-session-init` через `skill_view`, если контур и правила этой папки ещё не подтверждены. Проверь `jwu workspace current --json` с явным `terminal.workdir` папки проекта: `source=cwd`, непустой `slug`, без ошибки. CLI: `jwu --workspace <slug> …` с тем же `workdir`; MCP используй только при совпадении `source`, `slug`, `cwd`, передавай `workspace=<slug>` там, где он поддерживается. Для чтения git используй явный `workdir` только из подтверждённых путей воркспейса и загрузи правила его тега. При неподтверждённом контуре или отсутствии правил остановись.

1. Определи точную задачу/фичу и работу из запроса, ветки или активных работ (`jobs --status active --json`). При нескольких кандидатах уточни через `clarify`, если доступен, иначе в чате. Выбери подходящую активную/последнюю работу: `jwu_jobs(task=<KEY>, workspace=…)` или `jwu_jobs(feature=<REF>, workspace=…)`; CLI — `jobs --task <KEY> --json` / `jobs --feature <REF> --json`. Затем `job show <ID> --json`: возьми суть фикса и предупреждения, решения и запреты, из-за которых проверка может дать ложный результат.
2. Сверь ожидаемое поведение с карточкой `jwu_task(key, workspace)` / `task <KEY> --json` для внешнего провайдера в рамках запроса. Для `provider=local` используй `feature show <REF> --json`, не вызывай инструменты трекера. Отметь недоступный источник, не заменяй его догадкой.
3. Прочитай `git diff <target>...HEAD` при известной цели, отдельно `git diff HEAD` для незакоммиченных правок; если цель неизвестна, не угадывай её, проверь локальную историю (`git log --oneline -15`). Найди затронутый интерфейс и точные строки логов. Не переключай ветки, не делай fetch, не меняй git. Вводные пользователя определяют условия проверки в рамках правил: настройки, роли, стенд, ветка, устройства, ловушки. Без них используй «стенд тестирования, сборка с правками задачи» и роли/данные по смыслу; не добавляй адреса, логины, инструкции деплоя или плейсхолдеры. Никогда не включай секреты.

## Текст для QA

Покажи одним блоком `text`: **4TEST — ключ: что проверяем**; **ЧТО ТЕСТИРУЕМ** — наблюдаемый результат в 1–3 предложениях; **ВАЖНО ПЕРЕД СТАРТОМ** — только при ловушках; **ПОДГОТОВКА**, **ОСНОВНОЙ СЦЕНАРИЙ**, **КОНТРОЛЬ РЕГРЕССА БАГА** (только для фикса: без правки воспроизводится, с ней — нет), **РЕГРЕСС СОСЕДНЕЙ ФУНКЦИОНАЛЬНОСТИ**. Сквозная нумерация; каждый проверочный шаг — конкретное действие и `ОЖИДАНИЕ:`. Для UI укажи экран, действие и видимый эффект. Для невидимого поведения — дословная строка из источника и где искать; если существенная проверка не подтверждена, пометь текст как неполный и явно назови недостающее. Не раскрывай классы, таблицы, эндпоинты или другие детали реализации.

Загрузи через `skill_view` скил `jwu-voice-rewrite` и выполни только его чтение существующего профиля без создания. Если профиль и `delegate_task` доступны, отдай технический черновик редактору, при необходимости с `jwu_voice_examples(channel="qa_note", audience="qa", workspace=…)`. Поле `agent` — ориентир, не идентификатор запуска Hermes. Передай только нужный стиль и факты: править форму, не шаги, ожидания и дословные логи. Если редактор или профиль недоступен, явно пометь результат как технический черновик. На «не похоже на меня» повтори проход с замечанием и предыдущей версией; обратную связь в профиль не записывай без отдельного согласия.

## Сохранение копии отдельно

Если пользователь отредактировал или отклонил стиль, предложи отдельно записать правку в профиль. Только после согласия — `jwu_voice_feedback(channel="qa_note", audience="qa", verdict="edited" или "rejected", before=…, after=…, reason=…, workspace=…)`; перечитай профиль и проверь новую запись. Не записывай чувствительные данные в примеры.

Ничего не записывай по умолчанию. Только после показа полного текста и явного согласия сохранить его в конкретную работу: `jwu_job_add(job_id=…, text=…, kind="note", cwd=<проверенная папка>, workspace=…)` или `job add <ID> <текст> --kind note --no-git --json` с безопасным экранированием. Повторно прочитай `job show <ID> --json` и сверь запись по ID и тексту. Если не удалось подтвердить, не дублируй запись вслепую. Этот скилл никогда не публикует в Jira и не пишет в git.
