# jwu: начать работу в Hermes

## Вход по поручению с доски

Оркестратор передаёт цель и точные ключи выбранных пунктов, но не создаёт и не резервирует работы. Бриф — не подтверждение владения. Просьба только посмотреть или объяснить не требует взятия. Для поручения «взять в работу» действуй в чате воркера:

1. Пройди **jwu-session-init** в своей папке; сверь `source=cwd`, slug и правила. Выбери постоянное уникальное имя `S` для этой сессии доски (например, `worker-<ID этого чата>`, не ID оркестратора). Передавай его явно и при показе, и при взятии: MCP может быть общим для нескольких чатов.
2. Прочитай `jwu_todo(workspace=slug, session=S, refresh=False)`; CLI для чтения — `jwu --workspace SLUG todo --session S --no-refresh --json`. По `items` найди **точное** равенство `item.key` ключу брифа и сверь группу/цель. Используй **номер этой строки у себя**, не номер у оркестратора. Для PR ключ — из доски целиком, не `issue_key` и не голый номер. Если ключ отсутствует, неоднозначен или цель изменилась — сообщи расхождение; соседний пункт, всю группу или ручной старт не подставляй.
3. Сверь работы по задаче и по полной ссылке PR, включая `paused`, `done`, `cancelled` (не только `active`); прочитай журнал совпавшей цели. Своя уже взятая работа или явно переданная существующая работа с подтверждённой передачей и без параллельного владельца → **jwu-continue-job** по точному ID, без повторного take. Чужая/неясная бронь → сообщи ID и владельца, остановись по этому пункту. Для паузы или закрытого цикла покажи остаток и запроси решение о возобновлении именно этой работы; не создавай дубль и не переоткрывай по одному факту назначения. Для завершённой цели без остатка достаточно итога.
4. Только для свободных выбранных строк вызови `jwu_todo_take(workspace=slug, session=S, numbers=[n], keys=[item.key])` без `for_worker`. Это атомарная проверка и создание для штатных групп. Если MCP недоступен, CLI `jwu --workspace SLUG todo N --session S --no-refresh --json` использует сохранённый показ **этой** сессии, но не принимает `keys`: используй его только если снимок проверен и никто другой не может его перезаписать; иначе остановись. Для групп аддонов сначала проверь контракт обработчика: без подтверждённой защиты от двойного взятия остановись.
5. Разбери `taken` и `skipped` по каждому ключу. При гонке, исчезновении или иной причине пропуска не вызывай `jwu_job_start`: он всегда создаёт новую запись, даже если нашёл `existing_jobs`. После ошибки с неизвестным результатом сначала перечитай доску и работы. Для каждого успеха сначала сверь ключ и раздел в `taken`; при расхождении не приступай к работе. Затем проверь точный `job_id` через `jwu --workspace SLUG job show ID --json`: статус, якорь/PR и запись «Взято сессией» с твоим именем и ключом. Только теперь переходи к анализу/плану или ревью по назначенному скиллу. Решения о правках и публикации остаются в чате воркера.

**Прямой вызов без доски.** Ручной старт новой цели, локальной фичи или работы без якоря описан ниже. Это отдельный сценарий, не запасной способ обойти пропуск на доске.

## От анализа до первой правки

Для новой задачи, бага, конфликта, возврата QA, исправления сборки или замечаний к PR порядок один. Простое ревью чужого PR без правок идёт по своему процессу. Если после ревью попросили исправлять — это уже работа над изменением.

1. **Анализ.** Прочитай поручение, журнал и прошлые решения, карточку и комментарии, относящиеся к делу вложения, PR, замечания и результаты проверок. Сверь с текущим диффом, кодом и ближайшими тестами. Объясни пользователю, что должно работать, что сейчас не так, что подтверждено и что пока гипотеза. Для конфликта назови поведение, которое нужно сохранить с каждой стороны. Недоступный контекст обозначь явно.
2. **План.** Разбей изменение на участки с проверяемым результатом. Назови границы и порядок: что меняем, чего не трогаем. Для каждого нужного прогона укажи что проверяем, где (копия, сервисы или CI), когда и какой результат достаточен. Объедини дорогие проверки на итоговой версии; ранний узкий тест оставь только для конкретной гипотезы или обязательного RED/GREEN. Не отменяй обязательные проверки проекта.
3. **Решение в чате воркера.** Покажи в чате воркера весь план с проверками, дай утвердить или поправить. В Hermes помести сам план в вопрос `clarify` над кнопками: пользователь должен видеть, на что соглашается. Назначение работы и бриф — не согласие. Если этот точный план ещё не согласован, дождись решения. До согласия не применяй патч, не начинай мерж, не создавай стенд или рабочую копию и не запускай тесты. После согласования запиши именно выбранный план и расписание проверок как `decision` в журнал этой работы; перечитай запись. Если правила требуют короткой сверки перед правками, проведи её.
4. **Исполнение.** Иди по записанному плану. При продолжении не согласовывай неизменный план заново. Если изменились цель, объём, порядок работ или условия проверки, остановись до исполнения изменённого плана. Объясни причину и покажи обновлённый план целиком: что уже сделано, какие участки остаются, что добавилось или отпало, где и когда пройдут проверки. Согласуй с пользователем всю новую версию, а не только разницу. Запиши её в журнал как актуальный план и только затем продолжай. План сам по себе не разрешает публикацию.

**Сначала контур.** Загрузи `jwu-session-init` через `skill_view`, если папка и правила ещё не подтверждены. `source=cwd`, непустой `slug`, без ошибки; при смене проекта или потере контекста проверь снова. Бери `paths` и теги из контура, прочитай общие `rules_md` и полные правила нужных репозиториев (`jwu_rules(tag=…)` / `rules --tag TAG --json`). Соблюдай ⛔. Если запрет мешает плану — остановись. Никакого автоматического `init` или смены контура.

Ниже MCP — только если `jwu-session-init` подтвердил совпадение папки и контура; указывай `workspace=<slug>`, где поддерживается. CLI-команды ниже дополняй префиксом `jwu --workspace <slug>` и запускай `terminal` с проверенным `workdir`; для операций над копией используй только её подтверждённый `ref` по указанным ниже правилам. Экранируй тексты, ключи и пути отдельно. Вопросы — `clarify`, если он доступен и подходит, иначе пронумерованные варианты в чате и ожидание ответа. Не считай молчание согласием. Hermes не устанавливает и не гарантирует git-хук.

## Найти или начать

1. Определи **одну цель** цикла («конфликт PR #1092», «красная сборка», «правки по ревью»). Принимай точный ключ Jira `PROJ-399` или GitHub `dndeck#42`; у неоднозначного номера спроси ключ/PR, не подставляй префикс. `provider=local`: не вызывай задачи и PR внешнего трекера; используй локальную фичу (`jwu_features` / `feature list --status open --json`, `--status in_progress`) или без якоря. При `prs_enabled=false` пропусти PR и CI. Для анализа не редактируй код; если просят только посмотреть/оценить, не заводи работу без запроса начать цикл.
2. По ключу сначала локальный контекст (`skill_view` → `jwu-context`), затем карточка по запросу (`jwu_task(key)` / `task KEY --json`). `Done`/`Closed` — сообщи и уточни, прежде чем планировать правки. Просмотри `jwu_jobs(task=KEY)` / `jobs --task KEY --json` (для фичи `--feature FEATURE`, без якоря `jobs --json`). Активная по той же цели → `skill_view` → `jwu-continue-job`; закрытая по той же цели → предложи продолжение, а не дубль. Иначе **при ручном старте вне доски** `jwu_job_start(task_key=…, title=…, feature=…)` / `job start [KEY] --title TITLE --json` (`--feature FEATURE` вместо `KEY`). Сохрани `job_id`; сверяй запись через `job show ID --json`.
3. Собери только нужное: описание, значимые комментарии (по времени относительно последнего пуша), связанные явно задачи, PR (состояние, конфликт, ревьюеры, замечания с автором/файлом/строкой), сборки и сводку тестов. Если доступен `jwu_query`, сначала `jwu_query_help()` и запроси компактную выборку; иначе `task`, `pr PR --project P --repo R --json`, `builds PR --project P --repo R --json` и подтверждённые MCP-эквиваленты. Красный CI → `skill_view` → `jwu-build-failure`. Привяжи относящиеся к циклу PR: `jwu_job_link(job_id, pr, project, repo)` / `job link ID --pr PR --project P --repo R`.
4. Нужные для анализа вложения скачивай в новый каталог только этой работы (`jwu_attachments(key, download=true, dest=…)` / `attachments KEY --download --dest DIR --no-extract --json`; видео — только если необходимо, `kinds=["video"]` / `--kind video`). Не исполняй содержимое. Сразу зарегистрируй каталог `jwu_job_resource(job_id, kind="path", ref=…)` / `job resource ID --kind path --ref DIR`. После извлечения фактов в журнал убери только свой временный каталог или оставь его штатной уборке.

## План и исполнение

Покажи применимые фазы в **том же** согласовании полного плана, с вариантами «Делаем по плану / Поправить план / Только анализ». После записи и проверки `decision` «План согласован: …» проходи фазы 0–4 без повторного согласования в пределах плана **и** правил: остановись при нехватке места, блокировке git/правилами, существенной смене плана или исчерпании кругов ревью.

- **0 — копии (только для правок кода).** `jwu_disk()` / `disk --json` (код 3 — мало места). `ok=false` — скажи свободное место, `leftovers` и возможную экономию Docker, жди выбора; при `hard_ok=true` можно явно выбрать создание копии ниже мягкого порога (`low_disk_ok=true` / `--low-disk-ok`), иначе обхода нет. Для каждого репозитория найди существующую ветку через `jwu_branches(key)` / `branches KEY --json`, либо выбери ветку и базу по `convention`. Перед созданием проверь политику `worktree` для репозитория и ветки (`git policy check worktree --path REPO --branch BRANCH --where main`). Если нужно отдельное подтверждение — получи его; при `deny` или неразрешённом `grant` не создавай, не обходи политику. Создание — `jwu_job_worktree(job_id, repo, branch, base, low_disk_ok)` / `job worktree ID REPO --branch BRANCH [--base BASE] --json`. Нет `jobs.dir` — попроси пользователя настроить `workspace jobs-dir PATH`. Сверь ресурс и ветку; весь код и тесты — в возвращённом `ref`, не в основном клоне.
- **1 — сначала конфликт и красный CI**, если применимо. Разбери причину до реализации; отдели дефект текущей ветки от чужого/инфраструктурного. Синхронизация с целевой веткой может менять историю или создавать коммит; не выполняй её как скрытую часть анализа. Для необходимого sync отдельно покажи ветку, цель и режим, получи разрешение и используй только доступный `jwu_git_sync(path=…, target=…, mode=…, user_approved=true)` под политикой; без безопасного эквивалента остановись.
- **2 — анализ реализации и уточнение правок.** Проверь предложения ревьюеров; изменения объёма согласуй заново.
- **3 — правки и проверки.** Держи журнал. Для прогона дольше минуты — `terminal` в фоне с общим таймаутом раннера/обёртки и выводом в файл; наблюдай через `process_manage`, если доступен, либо запускай управляемым ограниченным прогоном. Пять минут без вывода или общий таймаут — останови процесс и только его контейнеры; запиши `test-fail`, последний шаг, команду и длительность; исследуй конкретный сбой, не перезапускай всё вслепую. Для успешного прогона — `test-pass` с командой и временем.
- **4 — ревью до коммита.** Загрузи `jwu-job-review` через `skill_view`; `jwu_job_reviewer(repo=…)` возвращает профиль и `max_iterations`. CLI: `review agents --json` и `workspace setting job.review.max_iterations` (по умолчанию 3). Используй настройки без отдельного вопроса, если профиль доступен; иначе действуй по скилу ревью. Блокеры/важные → собрать правки пакетом, затем новый проход. Тесты и стенд — по разделу «Один финальный прогон, один стенд работы». Мелочи не запускают круг. При лимите — «Ещё круг / Явно оставить допустимые замечания и идти к коммиту / Посмотрю сам» с остатком; запреты и блокировки не снимаются этим выбором, без состоявшегося ревью не пушь.

### Один финальный прогон, один стенд работы

1. Собери согласованную логику и изменения тестов целиком → отдай код на предварительное ревью → собери и исправь замечания пакетом → запусти согласованные тесты на итоговой версии. Не запускай широкие наборы, Playwright, сборку фронта или стенд после каждой мелкой правки и между проходами ревью. До финала используй чтение диффа и дешёвые проверки без сервисов. Ранний целевой тест — только если нужен для воспроизведения, проверки рискованного допущения или обязательного RED/GREEN. Назови, что именно такой прогон должен выяснить; не поднимай ради него весь стек, если хватит меньшего.
2. Если нужны сервисы, сначала проверь ресурсы этой работы. Подними один изолированный стенд с её метками и используй его повторно. Для нового прогона обнови только изменившийся код, компонент или бандл; сбрось только нужные тестовые данные, схему либо кеш своей работы и проверь, что загружена актуальная версия. Не переиспользуй грязное состояние как доказательство. Полное пересоздание — только если частичный сброс не даёт корректной изоляции, стенд повреждён или несовместим с новой конфигурацией. Назови причину. Не трогай чужие ресурсы; штатная уборка — при закрытии, не между тестами. Сразу записывай точные пути прогонов и кэшей, Compose-проект, тестовые тома и ID собственных образов, чтобы `jwu-close-job` мог убрать их без угадывания.
3. Повторяй только проверки, результат которых мог измениться после правки или чей предыдущий прогон не дошёл до тестов. Перед повтором назови причину и самый узкий достаточный набор. Привяжи результат к версии кода и условиям прогона. Если правила публикации требуют независимое ревью **после** тестов на том же снимке, соблюди этот порядок: раннее ревью экономит прогоны, но не заменяет обязательное финальное. Не урезай согласованную проверку и не обходи ограничения по диску, стенду или разрешениям.

### Стенд

Только свой стенд по `testenv` с тегом репозитория. Открой полную инструкцию (`jwu_guide(name)` / `guide show NAME`). Нет инструкции — спроси; предложи сохранить текст и короткое правило со ссылкой, оба только после «да» на формулировки (`jwu_guide_save(..., user_approved=true)` / `guide add NAME --title TITLE --file FILE [--tag TAG]`). Удалённые стенды — отдельный доступ по правилам (`jwu_ssh_servers()` / `ssh list --json`), по умолчанию только чтение.

До запуска и сборки образов проверь место; при нехватке стоп. Используй ровно `compose_project` и docker `label` от jwu (из старта или `jwu_job_resources(job_id)` / `job resources ID --json`), а не собранные из ID. `docker compose -p PROJECT …` и метка jwu на создаваемых Docker-ресурсах; порты через `jwu_job_ports(job_id, names=[…])` / `job ports ID db redis web --json`, подставь в конфиг. Регистрируй созданные ресурсы, не покрытые меткой, через `job resource` / MCP, с проверенной принадлежностью. Не трогай общий стенд; запиши способ запуска, адрес и порты, не секреты.

## 5 — финиш и публикация

**Спроси про результат, а не про очередную команду.** Если нужен новый PR, после показа ветки, сообщения коммита, результатов проверок и параметров PR предложи одним `clarify` весь применимый путь: сделать коммит, отправить ветку и открыть PR. Если коммит уже готов, не спрашивай про него заново: предложи отправить готовый коммит и открыть PR, если его параметры готовы. Для существующего PR назови его номер и предложи отправить изменения в него. Отдельные вопросы или пункты в той же форме нужны только для реально независимых решений; не подразумевай Jira, ручной CI или закрытие работы. Пуш не равен созданию PR, если оно явно не названо.

Не оставляй голое «принять исключение»: объясни, какая именно проверка падает и что проверено без нашей правки. Если это подтверждённый старый сбой и политика допускает исключение, согласуй одним выбором допустимость этого сбоя и весь указанный путь публикации. При новой проблеме, изменении согласованного объёма или обязательном `grant` остановись на реальной границе, а не задавай лишний вопрос между уже согласованными шагами.

**Не запрашивай локальный коммит дважды.** Если пользователь уже явно разрешил коммит этого набора изменений в этой ветке либо выбрал цепочку публикации, которая включает коммит, выполняй его после обязательных проверок без отдельной карточки «разрешить локальный коммит?». Не превращай локальный коммит в обязательную паузу. Если точного согласия ещё нет, получи его один раз в меню на весь следующий результат. Согласие на правки или тесты само по себе не разрешает коммит, согласие только на коммит не разрешает пуш. Новый вопрос нужен при изменении согласованного объёма, невыполненной проверке или обязательном допуске Git, а не потому, что коммит локальный.

1. Покажи что сделано, тесты и круги ревью; сразу подготовь одним сообщением полный коммит-месседж (`skill_view` → `jwu-commit-message`), заголовок/описание нового или обновляемого PR и тексты применимых активных аддонов (`jwu_addons()` → `after` для `jwu-start-job`). `addons list --json` показывает состояние, но не `after`; без MCP бери подсказки только из подтверждённой документации активного аддона, иначе явно пропусти этот шаг. Если доступен перенос профиля `voice_agent` из `jwu_job_reviewer`, возьми его как инструкции к стилю, не как имя исполняемого агента; иначе готовь черновики в текущей сессии и не приписывай им неподтверждённый голос. Ничего не публикуй на этапе черновика.
2. Покажи точные репо, ветки, файлы будущего коммита и превью того, что уйдёт. По умолчанию собери явно помеченное локальное превью по `git --no-optional-locks status`, `git diff` и `git log` относительно проверенной upstream-ссылки; если удалённое состояние нельзя подтвердить, так и скажи. `jwu_git_push(job_id=…, repo=…, dry_run=true)` не пушит, но требует чистого дерева и делает `fetch` (сеть и запись refs): только если отдельно разрешены обновление refs и доступ по политике. Он показывает существующие коммиты, не будущий коммит. У CLI `job push` **нет** `--dry-run`; не запускай для превью. Для создания PR `jwu_pr_people()` даёт `usual` (до 4 вариантов с числом PR); `jwu_pr_people(names=[…])` разрешает имена, совпадения уточняй, неизвестных не подставляй. CLI-аналога для рекомендаций нет — используй явно названные подтверждённые логины либо согласуй PR без ревьюверов. Перед переводом задачи прочитай актуальные переходы `jwu_issue_transitions(key)` / `issue transitions KEY --json`, если провайдер поддерживает. Покажи один вариант на связанный результат (коммит, отправка ветки и новый PR либо обновление существующего). Показанный текст аддона и точный переход Jira — отдельные решения, но их можно согласовать в той же форме, если они нужны. Изменил текст, назначение или объём — покажи и получи согласие заново.
3. Выполняй только выбранное, в порядке **коммит → пуш → PR → комментарий → переход**. Коммит: `jwu_git_commit(message=…, path=REF, files=[…], user_approved=true)` (перечисли одобренные файлы; без `files` инструмент добавляет всё, а даже с `files` коммит включает уже staged-содержимое: сначала проверь индекс и остановись при чужих/неодобренных правках). CLI-эквивалента нет: не подменяй shell-коммитом, попроси пользователя выполнить защищённый шаг и проверь результат. Пуш: только `jwu_git_push(job_id=…, repo=…, force=false, dry_run=false, user_approved=true)` или `job push ID [--repo REPO] --yes` **без интерактивной выдачи допусков**. При `blocked`: `grant` — передай `ask_user`, только пользователь выдаёт допуск; если доступен `jwu_git_grant_wait(grant_id, timeout=…)`, жди ограниченно, иначе возобнови после подтверждённого допуска. `deny` — стоп. Не меняй политику, не используй голый пишущий git, force или другой транспорт в обход отказа.
4. PR — только из подтверждённой запушенной ветки: `jwu_pr_create(target=…, title=…, description=…, source=…, reviewers=[…], from_job=…, project=…, repo=…)` / `pr-create --from SOURCE --to TARGET --title TITLE --text BODY --from-job ID [--reviewer LOGIN] --project P --repo R --yes --json`. Для своего существующего PR покажи «было → станет»: `jwu_pr_update` / `pr-edit PR --title TITLE --text BODY --project P --repo R --yes --json`; новый PR привяжи к job. Комментарий: `jwu_comment(key, text, dry_run=false)` / `comment KEY --text TEXT --yes --json`; для Support отдельно согласуй видимость клиенту (`client_facing=true` / `--to-client`). Статус: `jwu_issue_transition(key, target)` / `issue transition KEY TARGET --yes --json`. Не запускай CI и не делай дополнительные записи по умолчанию.
5. После каждого внешнего шага перечитай точный объект (удалённый ref/хеш, PR, комментарий, статус). При ошибке остановись, сообщи что уже подтверждено и чего не сделано; не повторяй запись вслепую. По достижении цели — `skill_view` → `jwu-close-job`, отдельный выбор закрытия, не следствие согласия на публикацию.

## Журнал

`jwu_job_add(job_id, text, kind, status, cwd=…)` / `job add ID TEXT --kind KIND [--status STATUS] --json`. Для привязки ветки/HEAD MCP укажи `cwd=REF`; CLI запускай из проверенной копии с явным `--workspace`. Проверяй значимые записи через `job show ID --json`. Пиши по ходу, не в конце:

- `phase` — этап, `pending`/`done`; `decision` — выбор, причина, отвергнутые альтернативы; `note` — факт; `constraint` — нельзя; `warning` — риск; `remark` — замечание ревьюера.
- `bug` — симптом и подтверждение; отдельный `bug-resolved` — что исправлено, исходную запись не меняй. `test-pass`/`test-fail` — каждый значимый прогон; дефект по тестам отдельно как `bug`.
- `todo` — только в этом цикле (`done` по факту); на следующий цикл — предложи заметку на задаче через `jwu-context`. Перед паузой запиши фазу и следующий шаг. `summary` — итог завершённого шага одной простой строкой без хешей, путей и номеров сборок; минимум одна итоговая запись за сессию на работу, в которой был результат. `review` — ровно одна самодостаточная шапка на прогон, якоря повторяются в деталях (см. `jwu-job-review`).
- Разовый запрет — в журнал. Для постоянного правила покажи `title`, `text`, `kind`, `tag`; создавать/править/удалять только после явного «да» на точный текст и охват (`jwu_rule_add(..., user_approved=true)` / `rule add TITLE --text TEXT --kind KIND [--tag TAG] --json` для добавления). Не превращай свои догадки или грабли одной задачи в правило проекта.
