# jwu: очередь ревью

## Вход по поручению

Для назначенной очереди сначала пройди «Вход по поручению с доски» в **jwu-start-job** в своей сессии. Сохрани соответствие `полный ключ PR → job_id` только по подтверждённым взятиям/передачам. Пересекай результат фильтров очереди с точными назначенными PR; не расширяй выборку совпадением номера или Jira-ключа. Одно ревью и решение о публикации — на один PR. Если несколько PR одной задачи и `todo_take` пропустил один по общей задаче, чужой `job_id` не относится ко второму PR. Сообщи пропуск, не обходи его через `job start` и не публикуй по этому PR; продолжай независимо взятые. Не теряй пропущенный PR: если мешает собственная работа той же очереди, после её согласованного закрытия заново прочитай доску и попробуй взять этот точный PR в своей сессии. Чужую работу не закрывай. В итоге различай завершённое, явно пропущенное пользователем и всё ещё занятое. При прямом `/jwu-review-queue` без назначения обычный отбор ниже остаётся доступен без предварительной брони.

> **Сначала правила воркспейса.** Ответа `jwu_workspace_current()` с `rules_md` нет в контексте
> этой сессии (новая сессия, `/clear`, компакт) — сначала пройди **jwu-session-init**. Без правил
> воркспейса не действуй: запреты (⛔) в них обязательны.

## Overview

Пакетное ревью чужих PR в два захода:

- **Фаза A — разбор, наружу НИЧЕГО.** Отбор PR → ревьюеры-субагенты пулом → фильтр
  замечаний → черновики комментов голосом пользователя → сводный md файлом пользователю.
- **Фаза B — отправка по одному PR.** PR целиком (о чём задача, что изменилось, по каждому
  комменту — проблема и текст, статус) → один вопрос → отправить комменты и статус →
  status-заметка → следующий PR.

Разовое ревью вне очереди — **jwu-review-pr**; свой дифф до коммита — **jwu-job-review**. Единственный PR из назначенной очереди остаётся в этом процессе.

> **MCP-first.** `jwu_review_queue(include_approved, prs, repos)` — очередь и пути;
> `jwu_pr`, `jwu_task`, `jwu_pr_diff` — контекст (их зовут
> сами субагенты); запись — `jwu_pr_comment`, `jwu_pr_review`, `jwu_note`.
> Bash-фолбэк: `jwu review queue --json`, `jwu --workspace <slug> pr <id> --project <P> --repo <R> --diff --numbered`.

## Аргументы

- глубина: `light` (по умолчанию — только блокеры и критичное) | `full`;
- параллельность: `N` (по умолчанию 3) — сколько ревьюеров одновременно;
- фильтр: номера PR и/или репозитории;
- `--include-approved` — ревьюить и PR, где мой статус уже APPROVED;
- `--include-needs-work` — PR с моим NEEDS_WORK брать без вопроса.

## Фаза A — разбор (ничего не отправляется)

1. **Очередь.** `jwu_review_queue(include_approved, include_needs_work, prs, repos)`.
   Покажи одной таблицей: что ревьюим (PR со ссылкой, репо, задача, ревьювер) и что
   пропущено с причиной. Каталог сводки — `dir` (данные jwu, вне репозиториев проекта).
2. **PR с моим NEEDS_WORK — отдельный вопрос, до запуска ревьюеров.** Если `needs_work`
   не пуст, спроси пользователя одним вопросом с множественным выбором, какие из них
   проверить заново. По каждому варианту: `repo#PR · КЛЮЧ · автор`, ссылка и что было
   после его needs work — «новых коммитов: N» / «новых коммитов нет — автор ещё не
   правил» / «не знаю, были ли правки» (`new_commits` пуст). Выбранные добавь в очередь
   (поля те же), остальные — в «пропущено: мой NEEDS_WORK, решил не смотреть». Явно
   названные номера и `--include-needs-work` не спрашивай — они уже в очереди.
3. **Ревьюеры пулом по N.** Для каждого PR — `Agent` с `subagent_type = reviewer_agent`
   (ревьювер репозитория из настроек, иначе `reviewer-jwu-sample`; задать —
   `jwu review agents --repo R --reviewer X`). Одновременно не больше N; как только один
   закончил — запускай следующий. Промпт каждому — самодостаточный:
   - полный адрес из строки очереди (`pr_id` = `pr`, `P` = `project`, `R` = `repo`), проверенный воркспейс `slug`, source → target, ключ задачи и режим `light|full`;
   - «это ЧУЖОЙ PR, ревью для комментариев автору»;
   - «сам возьми `jwu_pr(pr_id, project=P, repo=R, workspace=slug)`, `jwu_task(key, workspace=slug)`, `jwu_pr_diff(pr_id, path=path, numbered=True, project=P, repo=R, workspace=slug)` —
     дифф не приходит через оркестратора»;
   - «код сверяй с проверенным target через `git show` в подтверждённом клоне из `jwu_workspace_paths`. Если требуется fetch, вызывающая сессия проверяет допуск, remote и ref как в `jwu-review-pr`; не поручай fetch ревьюверу. Без клона — только дифф».
     Ветки НЕ переключай, рабочее дерево не трогай, ничего не коммить. Клона нет — пиши,
     что вывод только по диффу»;
   - «запиши свой раздел в `review_file` и верни его».
4. **Фильтр — сразу за ревьювером** этого PR (не жди остальных): `Agent` с
   `subagent_type = filter_agent` (по умолчанию `review-filter-sample`). Передай PR,
   target, задачу, путь к `review_file`, режим и путь `facts_file`. Выход — факты для
   комментов (куда, происхождение new/made-reachable, сценарий, следствие, просьба),
   предлагаемый статус и отброшенное с причинами. `pre-existing` автору не пишется.
   **История ревью PR — фильтру, не ревьюверу.** Ревьювер делает независимый проход без
   прошлых кругов (иначе заякорится на старом). Фильтру скажи сам взять
   `jwu_pr_review_history(pr_id, project=P, repo=R, workspace=slug)` и сверить: что уже отклонено с доводом
   (повтор без нового довода — в отброшенное «повтор отклонённого F<id>»), что исправлено
   на прошлых кругах (сломано снова или фикс задел соседний сценарий — «регрессия фикса
   F<id>», это важно), что открыто с прошлых кругов и не закрыто автором.
5. **Черновики голосом.** По каждому PR с оставшимися фактами — агент голоса
   (`jwu_voice_profile()` → `agent`): `channel = pr_comment` (ответ в тред автора —
   `pr_reply`), `audience = colleague`, `draft` — «Черновик» каждого пункта из `facts_file`
   (голос только переписывает форму, факты и имена не трогает), `context` — кусок
   numbered-диффа или цитата треда, `limits` — «3–5 предложений на коммент». Одним вызовом
   на PR, тексты пронумерованы так же, как пункты.
6. **Сводка** → `summary` (`<dir>/summary.md`):
   - сверху таблица `PR | репо | задача | вердикт | главное`, номер PR — ссылкой на него;
   - раздел на каждый PR: предлагаемый статус, блокеры / критичное / важное с `file:line`,
     под каждым — черновик коммента; «Для сводки» (pre-existing) отдельной строкой;
   - в конце — пропущенные PR и причины.
7. **Отдай файл — всегда `SendUserFile`.** `summary.md` отправляй пользователю файлом в
   любой сессии, не только удалённой: путь в тексте он не видит и открыть не может. Нет
   `SendUserFile` — скажи об этом прямо и дай путь. Сводка не заменяет показ первого готового PR по фазе B.
8. `jwu_note("PROJ/repo#ID", "ревью: черновики в <summary>", kind="context")` по каждому
   PR — чтобы следующая сессия нашла сводку.

## Фаза B — отправка, по одному PR

Строго **один PR за сообщение**, по порядку очереди. Сначала закончи анализ выбранной очереди (фаза A); явно отдели недоступные PR. Затем сразу покажи первый нерешённый PR по порядку: готовые тексты комментариев, их места и рекомендуемый статус ревью (или «статус без изменений»). Не спрашивай, готовить ли тексты или переходить ли к первому PR. Если анализ уже готов, не запускай его заново: сверь HEAD, якоря и дубли, примени голос для формулировок и переходи к показу. Сводка — дополнение, а не отдельная остановка. Только при явном «только черновик» отдай готовые тексты без вопроса о публикации и ничего не отправляй. Отчёт без предложенной внешней записи не требует ответа: покажи итог и перейди к следующему PR.

**Подготовка (молча):**

- `jwu_pr(pr_id, project=P, repo=R, workspace=slug)` — свежее состояние: коммиты, комменты и треды, сборка, ревьюеры. Сравни с моментом
  прошлого ревью пользователя (его последний коммент или статус в этом PR): что появилось
  после — новые коммиты, ответы автора в тредах, комменты других ревьюеров.
- Если HEAD изменился, перепроверь относящиеся к нему находки и якоря. Черновики, которые пользователь уже написал руками, — выкинь (совпадение по смыслу).
- Автор задал пользователю вопрос в треде — **первым идёт ответ в его тред** (`reply_to`).
- Задача — `jwu_task(KEY)`: что за баг или фича.

**Показ — ровно в таком порядке:**

1. **Шапка:** `N/M — project/repo#PR · КЛЮЧ-ЗАДАЧИ · автор` и под ней ссылка на PR (`url` из
   `jwu_review_queue` / `jwu_pr`) — кликабельно, чтобы открыть PR в один тап.
2. **О чём задача** — 2–3 предложения простым языком: какой баг или фича (из карточки
   Jira) и что автор в PR сделал. Без деталей реализации.
3. **Состояние PR** — одна-две строки: что изменилось с прошлого ревью пользователя
   (новые коммиты, ответы автора в тредах, новые комменты других ревьюеров), статус
   сборки, какие прежние черновики выкинуты, потому что уже написаны руками.
4. **По каждому комменту — отдельный блок:**
   - заголовок: номер, куда уйдёт (новый inline `path:line` / ответ в тред #id / общий
     коммент), важность (блокер / критично / важно);
   - **Проблема** — для ПОЛЬЗОВАТЕЛЯ, не для автора PR: почему этот коммент вообще есть —
     что было до PR, что PR изменил, какой реальный сценарий ломается и чем это грозит
     (500, регрессия, нарушение правила проекта, повтор незакрытого треда, на который
     автор ответил формально). 3–5 предложений простым языком — чтобы пользователь решил,
     отправлять ли, не открывая код. Берётся из фактов фильтра (`facts_file`), не из
     текста коммента;
   - сам текст коммента цитатой (`> …`) — ровно то, что уйдёт в PR.
5. **Статус** — текущий и рекомендуемый (`APPROVED` / `NEEDS_WORK` / оставить без изменений). Если отзыв включает текст, покажи его целиком.
6. **Один выбор по этому PR**, если есть предлагаемая запись и это не «только черновик»: например, «Отправить 2 комментария и поставить NEEDS_WORK» / «Отправить только 2 комментария» / «Пропустить PR». Показывай только применимые варианты; пользователь может назвать номера, оставить статус без изменений или поправить текст. Если точное неизменное превью уже согласовано, не спрашивай повторно. Молчание не разрешает запись.

**Ответ пользователя:**

- **«Отправить»** — перед записью сверь HEAD, треды, якоря и статус с согласованным превью. Если результат изменился — обнови превью и согласуй изменённое; иначе без второго «да». Выполни только выбранное по этому PR: ответы в треды, inline, затем общий комментарий. Для inline — `jwu_pr_comment(pr_id, text, path=path, line=line, project=P, repo=R, workspace=slug)`, для ответа вместо пути и строки — `reply_to`. Сверь текст и якорь; при `anchored: false` остановись. Удаление своего комментария и повторная отправка — только с новым согласием.
  Затем, только если явно выбран статус, — `jwu_pr_review(pr_id, status, project=P, repo=R, workspace=slug)`; `text` передавай только если показан и согласован текст отзыва. В Bitbucket согласованный текст статуса может уйти отдельным общим комментарием: включи этот эффект в превью и не посылай текст повторно. Перечитай этот PR, проверь выбранные записи и статус. Не повторяй неопределённую отправку вслепую.
  Фактический результат — в `jwu_note("PROJ/repo#ID", "ревью сделано, ждём …", kind="status", pin=True, workspace=slug)`. Круг в историю — `jwu_review_add(pr_id, findings, side="local", label=reviewer, commit=head, project=P, repo=R, workspace=slug, full_pass=full_pass)`: только подтверждённые отправленные находки (`level`, `text`, `file`, `line`). Для `light` или частичного списка передай `full_pass=False`, чтобы не снять прежние находки; `True` — только для полного прохода и полного набора.
- **«Править»** — текст правит агент голоса по фактам и правке; покажи PR заново в том же
  формате и снова один вопрос.
- **«Пропустить» / «дальше»** — в этот PR ничего не уходит; следующий PR.
- После выбора или явного пропуска сразу покажи следующий нерешённый PR — не жди команды «дальше». Не предлагай повторно уже опубликованное или явно отклонённое. По окончании — итог по всей очереди; закрытие связанных работ по `jwu-close-job`, только если ещё нужен выбор.

## Текст от имени пользователя (голос)

Содержание текста, который уйдёт наружу от имени пользователя или отдаётся ему «для
копирования», пишешь **ты** (или субагент, который разбирался), а **форму** — агент голоса:

1. Напиши **технический черновик** — полный и точный ответ по существу: что сказать
   (сценарий → следствие → просьба; или что сделано), на что отвечаем, имена из кода,
   цифры, выводы. Стиль не важен, важно, чтобы по содержанию его можно было отправить.
2. `jwu_voice_profile()` → поле `agent` (дефолт `voice-writer-sample`, проектный задаётся
   `jwu voice agent <имя>`). Запусти его через Agent (`subagent_type` = `agent`) и передай
   `channel`, `audience`, `draft` (черновик), `context`, `limits`. Голос **только переписывает
   форму** под пользователя — длину, тон, обращения, привычные выражения, — факты, имена и
   выводы не трогает. Наружу ничего не шлёт.
3. Покажи пользователю текст целиком **в блоке кода** (```` ```text ````, чтобы копировался
   как есть; «что ушло при сжатии», если не пусто, — под ним обычным текстом) → правки →
   явное «да» → отправка этим скиллом.
4. «Не похоже на меня» — запусти агента ещё раз с `recheck` (прежний текст в `previous`,
   слова пользователя в `remark`): он сверит черновик с реальными текстами из корпуса и
   перепишет. Предложит правило для профиля — покажи его пользователю.
5. Обычную правку внеси в черновик, не спрашивая о настройках стиля. Если пользователь просит запомнить правило на будущее, покажи точную формулировку; запись в профиль — только по его согласию (`jwu_voice_feedback`).

Каналы: `pr_comment`, `pr_reply`, `pr_review_body`; аудитория `colleague`.

## Чего делать НЕ надо

- Отправлять что-либо в фазе A, или в фазе B без ответа «отправить» по конкретному PR.
- Показывать несколько PR в одном сообщении или переписывать «Проблему» текстом коммента.
- Писать автору `pre-existing` и натянутое: мелочи, стиль, «проверь якорь», «уточни
  формулировку», вне скоупа задачи.
- Держать дифф в контексте оркестратора — его берут субагенты сами.
- Класть сводку в репозиторий проекта.
- Запускать больше N ревьюеров одновременно.
- Апрувить «раз замечаний нет» без явного «да» пользователя на статус.
