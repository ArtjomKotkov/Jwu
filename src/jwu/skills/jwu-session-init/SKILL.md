# jwu: инит сессии в воркспейсе

## Overview

Новая сессия ничего не знает о проекте: в каком он контуре jwu, какие у него правила,
что уже в работе. Без этого работа идёт мимо jwu — записи не логируются, правила
нарушаются, пользователю приходится напоминать. Этот скилл — **первый шаг любой сессии**:
за пару вызовов поднять контекст и дальше вести всё через jwu.

Скилл только читает (локальная БД, без сети) и ничего не пишет.

## Когда

- Начало сессии, до первого чтения/правки кода.
- После `/clear` или компакта контекста — состояние jwu ушло вместе с ним.
- Пользователь напоминает «работай через jwu» — значит, этот шаг пропустили.
- **Не нужен**, если `jwu_workspace_current()` уже вызывался в этой сессии и его ответ в контексте.

## Шаги

1. **Воркспейс.** `jwu_workspace_current()` (bash: `jwu workspace current --json`).
   - `source` = `cwd` — папка привязана, продолжай.
   - `source` другой (`active`, `only`, `env`) или ошибка «не понял, в каком воркспейсе» —
     папка **не привязана**: записи уедут в чужой контур. Остановись и предложи скилл
     **jwu-workspace-setup**. Дальше не иди.
   - Есть `version_warning` — скажи пользователю одной строкой (MCP-сервер на другой версии,
     чем установлена; лечится перезапуском сессии или скиллом **jwu-update**).

2. **Правила.** Общие правила приходят готовым текстом в `rules_md` — прочитай и **соблюдай**
   (`⛔ ЗАПРЕТ` обязательны). У папок воркспейса есть теги (`paths[].tags`): как только
   понятно, в каком репозитории работа, дотяни его правила — `jwu_rules(tag="<тег>")`.
   Если папка одна — дотяни сразу.

3. **Что уже в работе.** `jwu_jobs(status="active")`.
   - Есть активные — покажи списком (`id`, якорь `anchor`, дата обновления, последняя запись).
     Если просьба пользователя про одну из них — дальше **jwu-continue-job**.
   - Нет — ок.

4. **Очередь.** `jwu_queue()` (bash: `jwu queue --json`). Есть пункты `queued`/`running` —
   покажи их построчно и считай режим очереди включённым: дальше по скиллу **jwu-queue**
   (хвосты `running` прошлой сессии — закрыть или вернуть в очередь). Пусто — молчи.

5. **Откуда задачи** — по `provider`:
   - `local` — задач Jira/GitHub нет, якорь работы — локальная фича:
     `jwu_features(status="open")` и `in_progress`. Инструменты задач/PR **не вызывай**.
   - `jira` / `github` — задачи и PR внешние; сводку дня даёт **jwu-analyze-day**
     (сам не запускай — сетевой и длинный, предложи).

6. **Стенды.** `jwu_ssh_servers()` — есть SSH-стенды контура? Если да, проверь, что в
   сессии есть инструменты с префиксом `tools_prefix`; нет — одной строкой подскажи
   `jwu ssh install` и перезапуск сессии. Стендов нет — молчи.

7. **Сводка пользователю** — 3–6 строк: воркспейс и провайдер, ключевые запреты,
   активные работы, очередь (если не пуста), открытые фичи (для `local`), стенды, если есть. Без пересказа всех правил.

## Дальше в сессии

- Новая задача или фича → **jwu-start-job** (для `local` сначала `jwu_feature_add`,
  если подходящей фичи нет, потом `jwu_job_start(feature=KEY)`).
- Продолжение или переоткрытие → **jwu-continue-job**. Журнал ведётся по ходу (раздел «Журнал работы» в jwu-start-job).
- Цель работы достигнута → **jwu-close-job** (итог для трекинга времени, уборка стенда и копий).
- Работа без якоря — только если пользователь явно не хочет фичу: `jwu_job_start(title=…)`.

## Частые ошибки

- Начать читать и править код, не вызвав `jwu_workspace_current()`: правила и активные
  работы остаются неизвестны.
- Логировать работу, когда `source` не `cwd`.
- Для `provider=local` звать `jwu_tasks` / `jwu_prs` — они откажут.
- Заводить новую работу, когда по той же фиче/задаче уже есть активная.
