# jwu: продолжить или переоткрыть работу (job)

## Вход по поручению

Бриф с ключом строки, но без подтверждённой работы → **jwu-start-job**, раздел «Вход по поручению с доски». С точным ID после проверки папки и правил через **jwu-session-init** прочитай `job show ID --json`: сверь контур, цель, полный PR и владение. Продолжай свою работу либо явно переданную без параллельного владельца; при чужом или неясном владельце остановись, не присваивай работу. `paused`, `done`, `cancelled` не дают права создать дубль или молча вернуть статус `active`. Восстанови журнал и остаток; возобновляй только по явному решению об этом цикле, затем перечитай статус. Запрос состояния — только чтение. При прямом вызове без брифа выбирай работу по правилам ниже.

При продолжении работы с изменениями, в том числе после возврата QA, сначала сверь весь согласованный план и проверки с журналом, новыми замечаниями и фактическим состоянием ресурсов. Нет плана или изменились цель, объём, порядок или условия проверки — примени «От анализа до первой правки» из **jwu-start-job**: согласуй и запиши весь актуальный план, не только разницу. Неизменный план заново не согласовывай. Только затем, если это нужно для очередного согласованного шага, восстанавливай копию или стенд.

## Overview

Контекст ушёл, а работа осталась: её журнал, ветки, копии, стенд. Прежде чем трогать код,
**восстанови состояние из jwu** (локальная БД, без сети) и коротко синхронизируйся с
пользователем. Если пользователь просит возобновить закрытую работу по той же цели — **переоткрой**, а не заводи новую: у неё
уже есть журнал, ветка и история решений.

В конце каждой фазы выполни проверку «перед завершением каждого хода» из `jwu-session-init` § «Меню в Hermes Desktop». Если следующий шаг понятен, но требует отдельного согласия (например, тесты после согласования только диффа), открой нативный `clarify` сразу, в этом же чате и ходе. Не оставляй открытый выбор в отчёте без карточки.

> **MCP-first.** `jwu_jobs(task, status)`, `jwu_job_handoff(job_id)`, `jwu_job_reopen(job_id)`,
> `jwu_job_resources(job_id)`, `jwu_job_worktree(job_id, repo, branch)`, `jwu_job_add(…)`,
> `jwu_disk()`, `jwu_pr`, `jwu_builds`, `jwu_pr_tasks`. Bash `jwu …` — фолбэк.
> **Воркспейс = где лежит код.** jwu работает в контексте *воркспейса*: он определяется
> автоматически по текущей папке, проверить — `jwu_workspace_current()`
> (bash: `jwu workspace current --json`).
>
> **Код проекта лежит ИМЕННО в папках воркспейса.** Их список с тегами приходит сразу
> в `jwu_workspace_current()` и в ответе `jwu_job_start()` (поля `paths` и `known_tags`),
> отдельный вызов нужен только чтобы отфильтровать по тегу — `jwu_workspace_paths(tag=…)`
> (bash: `jwu workspace paths`). Ищи и правь только в этих папках;
> остальное на диске к задаче отношения не имеет. У папок есть **теги** («legacy-бэкенд»,
> «новая-версия», «фронт») — по ним понятно, что где: `jwu_workspace_paths(tag="legacy-бэкенд")`.
> Не угадывай по имени каталога — спроси теги. Пользователь просит пометить папку —
> `jwu_workspace_tag(path, add=[...])` (bash: `jwu workspace tag <DIR> --add <тег>`).
>
> **У воркспейса есть ПРАВИЛА** — то, что знает о проекте человек, но не знает код:
> запреты (⛔ `constraint`), инструкции (`howto`), тестовое окружение (🧪 `testenv` — как
> работе поднять СВОЙ стенд и снести его),
> соглашения (`convention` — ветки, формат коммита), грабли (`gotcha`), справка (`info`).
> Правила приходят готовым текстом в поле `rules_md` — оно есть и в `jwu_workspace_current()`,
> и в ответе `jwu_job_start()`. Общие правила там целиком, у правил конкретных
> репозиториев — только заголовки. Как только понял, в какой папке правишь, возьми её
> правила целиком: `jwu_rules(tag="legacy-бэкенд")` (bash: `jwu rules --tag legacy-бэкенд`).
> **Записи `⛔ ЗАПРЕТ` обязательны к исполнению** и важнее твоего удобства: если правило
> мешает выполнить просьбу — не обходи его молча, скажи об этом пользователю.
> Пользователь формулирует правило уровня проекта («не пушь в develop», «стенд поднимается
> так-то») — **предложи** сохранить и покажи формулировку; ⛔ записывай только после его «да»:
> `jwu_rule_add(title, text, kind, tag, user_approved=True)`
> (bash: `jwu rule add "…" --kind constraint`).
>
> **Провайдер контура** (`provider` в ответе `jwu_workspace_current()`) говорит, откуда
> берутся задачи и PR: `jira` (Jira + Bitbucket + Jenkins), `github` (Issues + PR + Actions)
> или `local`. Инструменты одни и те же — меняется только формат ключа задачи: `PROJ-123`
> у Jira, `dndeck#42` у GitHub. Если `provider=local` — инструменты задач **не вызывай**:
> якорь работы там либо локальная фича (`jwu_features` / `jwu feature list`), либо ничего
> (`jwu job start --title "…"`). У GitHub нет таймтрекера — `jwu_worklog` там откажет. Если папка не привязана ни к одному воркспейсу — скажи
> об этом пользователю и предложи подключить проект.
> Если папка не привязана ни к одному воркспейсу (`source` не `cwd`) — **не логируй работу**:
> записи уедут в чужой контур. Сначала подключи проект — скилл **jwu-workspace-setup**
> (`jwu init`).

## Шаги

> **Сначала правила.** Ответа `jwu_workspace_current()` с `rules_md` нет в контексте этой
> сессии (новая сессия, `/clear`, компакт) — пройди **jwu-session-init**. Без правил
> воркспейса не начинай, не правь и не закрывай.

1. **Найти работу.** `jwu_workspace_current()` (работы скоупятся по воркспейсу).
   - Дан ключ — `jwu_jobs(task=KEY)`; дан `#id` — она; ничего — `jwu_jobs(status="active")`.
   - Несколько подходящих — список (`id · цель · статус · обновлена`) и **спроси**, какую.
   - Закрыта или на паузе — сначала восстанови состояние и остаток. Новая цель → **jwu-start-job**. Для того же цикла после явного решения о возобновлении: `done`/`cancelled` → `jwu_job_reopen(job_id)`; `paused` → `jwu_job_status(job_id, status="active")`. Перечитай статус. При запросе состояния ничего не меняй.

2. **Где мы.** `jwu_job_handoff(job_id, offline=True, save=False)` → `markdown`: цель, ветка и коммит по последней
   записи, что сделано / осталось, запреты и решения, состояние PR и правила. Мало —
   `jwu job show <id>`: последняя `phase`, `todo` без done, `bug` без парного `bug-resolved`,
   `constraint` (⛔ не нарушай), `decision` (не пересматривай без причины), последний тест.
   Сверь живое: сборка PR (`jwu_builds`), открытые задачи PR (`jwu_pr_tasks`), новые комменты.
   **«⚠️ По задаче есть ещё PR»** в handoff — правки по задаче лежат в нескольких ветках, а
   работа знает не обо всех. Для продолжения уточни состав цикла и только тогда привяжи выбранные PR (`jwu_job_link`); при запросе состояния не привязывай. Проверь, нужны ли правки в каждой ветке.

3. **Сверь весь план.** Коротко назови цель, фазу, что сделано, что осталось (включая открытые задачи PR), запреты и статус проверок. По `jwu_job_resources(job_id)` проверь наличие копий и стенда, пока ничего не восстанавливая.
   - `decision` «План согласован» по-прежнему охватывает работу и проверки — продолжай с первого невыполненного шага без повторного согласования.
   - Плана нет или он изменился — покажи целиком актуальный план с проверками по **jwu-start-job**. Дай выбрать «Делаем / Поправить план / Только анализ»; после согласия запиши план целиком в `decision` и перечитай запись.

4. **Восстанови рабочее место в пределах согласованного плана.** `jwu_job_resources(job_id)`:
   - копии (`worktree`) на месте — работай в них, не в основной папке;
   - копий нет (работу закрывали — уборка их сняла), а будут правки кода — `jwu_disk()`
     (мало места → стоп и вопрос; при `hard_ok=True` в меню есть «создать при малом
     месте» → `low_disk_ok=True`). Проверь точную ветку по ресурсам и журналу, затем её наличие локально или по подтверждённой `refs/remotes/origin/…`; если обе отсутствуют, не создавай копию от случайного HEAD. Проверь политику `worktree` и обязательные допуски по **jwu-start-job** до вызова `jwu_job_worktree(job_id, repo, branch=…)`;
   - стенд нужен и не поднят — как в **jwu-start-job**, раздел «Стенд работы»: по правилу
     `testenv`, всё с меткой и compose-проектом из `jwu_job_resources(job_id)` (`label`,
     `compose_project`), свободное место — до подъёма.

5. **Работай и веди журнал** — по правилам **jwu-start-job**, включая «Один финальный прогон, один стенд работы» и «Журнал работы»:
   закончил шаг — запись (`phase`, `decision`, `bug`/`bug-resolved`, `test-pass`/`test-fail`,
   `constraint`, `warning`, `todo`). Сессия кончается, а работа нет — запиши последнюю фазу
   и `todo` «что дальше»: следующая сессия начнёт с handoff.

6. **Цель достигнута** — финиш по `jwu-start-job`, закрытие по `jwu-close-job`. Продолжай уже согласованное; карточка нужна только для оставшегося решения. Стандартная уборка входит в согласованное закрытие после проверок безопасности; архив чата — отдельное решение.

## Частые ошибки

- Завести новую работу, хотя по той же цели есть открытая или закрытая.
- Править в основной папке, когда у работы есть своя копия.
- Поднять второй стенд, не проверив, что старый ещё жив (`docker ps --filter label=<label из jwu_job_resources>`).
- Продолжать по памяти, не перечитав handoff.

## Подтверждение

Чтение — без подтверждения. Для переоткрытия нужен запрос возобновить именно эту работу; простой осмотр, как и бриф с ключом, его не заменяет. Правки кода — после «да» на план
(в этой или прошлой сессии, запись в журнале). Коммит, пуш, PR и комментарий — только в явно согласованном объёме. Если решение уже есть и ничего не изменилось, не спрашивай заново. Нехватка места — всегда стоп и вопрос.
