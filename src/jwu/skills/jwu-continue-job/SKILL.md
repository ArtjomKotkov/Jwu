name: jwu-continue-job
description: Use when continuing an existing jwu «работа (job)» — an open one whose state is not in the current context (new session, after /clear or compaction, returning later) or REOPENING a closed one (вернули с тестов, ревьюер снова написал, сборка опять красная): «продолжим работу по …», «на чём остановились», «что по PROJ-124», «переоткрой работу», «вернули задачу — продолжаем», «/jwu-continue-job [KEY|#id]». Restores state from the job log and handoff, re-creates the job's worktrees and stand if they were cleaned up, syncs with the user, then keeps logging the journal while working. New goal → jwu-start-job; goal done → jwu-close-job.

# jwu: продолжить или переоткрыть работу (job)

## Overview

Контекст ушёл, а работа осталась: её журнал, ветки, копии, стенд. Прежде чем трогать код,
**восстанови состояние из jwu** (локальная БД, без сети) и коротко синхронизируйся с
пользователем. Закрытую работу по той же цели — **переоткрой**, а не заводи новую: у неё
уже есть журнал, ветка и история решений.

> **MCP-first.** `jwu_jobs(task, status)`, `jwu_job_handoff(job_id)`, `jwu_job_reopen(job_id)`,
> `jwu_job_resources(job_id)`, `jwu_job_worktree(job_id, repo, branch)`, `jwu_job_add(…)`,
> `jwu_disk()`, `jwu_pr`, `jwu_builds`, `jwu_pr_tasks`. Bash `jwu …` — фолбэк.
> **Воркспейс = где лежит код.** jwu работает в контексте *воркспейса*: он определяется
> автоматически по текущей папке, проверить — `jwu_workspace_current()`
> (bash: `jwu workspace current --json`).
>
> **Код проекта лежит ИМЕННО в папках воркспейса.** Их список с тегами приходит сразу
> в `jwu_workspace_current()` и в ответе `jwu_job_start()` (поля `paths` и `known_tags`),
> отдельный вызов нужен только чтобы отфильтровать по тегу — `jwu_workspace_paths(tag=…)`
> (bash: `jwu workspace paths`). Ищи и правь только в этих папках;
> остальное на диске к задаче отношения не имеет. У папок есть **теги** («legacy-бэкенд»,
> «новая-версия», «фронт») — по ним понятно, что где: `jwu_workspace_paths(tag="legacy-бэкенд")`.
> Не угадывай по имени каталога — спроси теги. Пользователь просит пометить папку —
> `jwu_workspace_tag(path, add=[...])` (bash: `jwu workspace tag <DIR> --add <тег>`).
>
> **У воркспейса есть ПРАВИЛА** — то, что знает о проекте человек, но не знает код:
> запреты (⛔ `constraint`), инструкции (`howto`), тестовое окружение (🧪 `testenv` — как
> работе поднять СВОЙ стенд и снести его),
> соглашения (`convention` — ветки, формат коммита), грабли (`gotcha`), справка (`info`).
> Правила приходят готовым текстом в поле `rules_md` — оно есть и в `jwu_workspace_current()`,
> и в ответе `jwu_job_start()`. Общие правила там целиком, у правил конкретных
> репозиториев — только заголовки. Как только понял, в какой папке правишь, возьми её
> правила целиком: `jwu_rules(tag="legacy-бэкенд")` (bash: `jwu rules --tag legacy-бэкенд`).
> **Записи `⛔ ЗАПРЕТ` обязательны к исполнению** и важнее твоего удобства: если правило
> мешает выполнить просьбу — не обходи его молча, скажи об этом пользователю.
> Пользователь формулирует правило уровня проекта («не пушь в develop», «стенд поднимается
> так-то») — предложи сохранить: `jwu_rule_add(title, text, kind, tag)`
> (bash: `jwu rule add "…" --kind constraint`).
>
> **Провайдер контура** (`provider` в ответе `jwu_workspace_current()`) говорит, откуда
> берутся задачи и PR: `jira` (Jira + Bitbucket + Jenkins), `github` (Issues + PR + Actions)
> или `local`. Инструменты одни и те же — меняется только формат ключа задачи: `PROJ-123`
> у Jira, `dndeck#42` у GitHub. Если `provider=local` — инструменты задач **не вызывай**:
> якорь работы там либо локальная фича (`jwu_features` / `jwu feature list`), либо ничего
> (`jwu job start --title "…"`). У GitHub нет таймтрекера — `jwu_worklog` там откажет. Если папка не привязана ни к одному воркспейсу — скажи
> об этом пользователю и предложи подключить проект.
> Если папка не привязана ни к одному воркспейсу (`source` не `cwd`) — **не логируй работу**:
> записи уедут в чужой контур. Сначала подключи проект — скилл **jwu-workspace-setup**
> (`jwu init`).

## Шаги

1. **Найти работу.** `jwu_workspace_current()` (работы скоупятся по воркспейсу).
   - Дан ключ — `jwu_jobs(task=KEY)`; дан `#id` — она; ничего — `jwu_jobs(status="active")`.
   - Несколько подходящих — список (`id · цель · статус · обновлена`) и **спроси**, какую.
   - Нашлась только **закрытая** (`done`/`cancelled`): цель та же (вернули с тестов, новые
     замечания по тем же правкам, сборка снова красная) — **переоткрой**
     `jwu_job_reopen(job_id)`; цель новая — это **jwu-start-job**.

2. **Где мы.** `jwu_job_handoff(job_id)` → `markdown`: цель, ветка и коммит по последней
   записи, что сделано / осталось, запреты и решения, состояние PR и правила. Мало —
   `jwu job show <id>`: последняя `phase`, `todo` без done, `bug` без парного `bug-resolved`,
   `constraint` (⛔ не нарушай), `decision` (не пересматривай без причины), последний тест.
   Сверь живое: сборка PR (`jwu_builds`), открытые задачи PR (`jwu_pr_tasks`), новые комменты.

3. **Рабочее место.** `jwu_job_resources(job_id)`:
   - копии (`worktree`) на месте — работай в них, не в основной папке;
   - копий нет (работу закрывали — уборка их сняла), а будут правки кода — `jwu_disk()`
     (мало места → стоп и вопрос), потом `jwu_job_worktree(job_id, repo, branch="<ветка
     работы из журнала>")` на каждый нужный репозиторий: ветка запушена, копия соберётся из неё;
   - стенд нужен и не поднят — как в **jwu-start-job**, раздел «Стенд работы»: по правилу
     `testenv`, всё с меткой `jwu.job=<id>` / `-p jwu-job<id>`, свободное место — до подъёма.

4. **Сводка пользователю** (4–6 строк): цель работы, фаза, что сделано, что осталось
   (включая открытые задачи PR), запреты, статус сборки. **Подтверди следующий шаг**, прежде
   чем писать код.

5. **Работай и веди журнал** — по правилам **jwu-start-job**, раздел «Журнал работы»:
   закончил шаг — запись (`phase`, `decision`, `bug`/`bug-resolved`, `test-pass`/`test-fail`,
   `constraint`, `warning`, `todo`). Сессия кончается, а работа нет — запиши последнюю фазу
   и `todo` «что дальше»: следующая сессия начнёт с handoff.

6. **Цель достигнута** — предложи **jwu-close-job**.

## Частые ошибки

- Завести новую работу, хотя по той же цели есть открытая или закрытая.
- Править в основной папке, когда у работы есть своя копия.
- Поднять второй стенд, не проверив, что старый ещё жив (`docker ps --filter label=jwu.job=<id>`).
- Продолжать по памяти, не перечитав handoff.

## Подтверждение

Чтение, переоткрытие, копия, журнал — без подтверждения. Правки кода, коммит, пуш — только
после явного «да». Нехватка места — всегда стоп и вопрос.
