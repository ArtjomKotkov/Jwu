# jwu: коммит-сообщение из текущих изменений

> **Воркспейс = где лежит код.** jwu работает в контексте *воркспейса*: он определяется
> автоматически по текущей папке, проверить — `jwu_workspace_current()`
> (bash: `jwu workspace current --json`).
>
> **Код проекта лежит ИМЕННО в папках воркспейса.** Их список с тегами приходит сразу
> в `jwu_workspace_current()` и в ответе `jwu_job_start()` (поля `paths` и `known_tags`),
> отдельный вызов нужен только чтобы отфильтровать по тегу — `jwu_workspace_paths(tag=…)`
> (bash: `jwu workspace paths`). Ищи и правь только в этих папках;
> остальное на диске к задаче отношения не имеет. У папок есть **теги** («legacy-бэкенд»,
> «новая-версия», «фронт») — по ним понятно, что где: `jwu_workspace_paths(tag="legacy-бэкенд")`.
> Не угадывай по имени каталога — спроси теги. Пользователь просит пометить папку —
> `jwu_workspace_tag(path, add=[...])` (bash: `jwu workspace tag <DIR> --add <тег>`).
>
> **У воркспейса есть ПРАВИЛА** — то, что знает о проекте человек, но не знает код:
> запреты (⛔ `constraint`), инструкции (`howto` — как поднять стенд, прогнать тесты),
> соглашения (`convention` — ветки, формат коммита), грабли (`gotcha`), справка (`info`).
> Правила приходят готовым текстом в поле `rules_md` — оно есть и в `jwu_workspace_current()`,
> и в ответе `jwu_job_start()`. Общие правила там целиком, у правил конкретных
> репозиториев — только заголовки. Как только понял, в какой папке правишь, возьми её
> правила целиком: `jwu_rules(tag="legacy-бэкенд")` (bash: `jwu rules --tag legacy-бэкенд`).
> **Записи `⛔ ЗАПРЕТ` обязательны к исполнению** и важнее твоего удобства: если правило
> мешает выполнить просьбу — не обходи его молча, скажи об этом пользователю.
> Пользователь формулирует правило уровня проекта («не пушь в develop», «стенд поднимается
> так-то») — предложи сохранить: `jwu_rule_add(title, text, kind, tag)`
> (bash: `jwu rule add "…" --kind constraint`).
>
> Если `jira_enabled=false` — Jira-команды и инструменты **не вызывай**: якорь работы там
> либо локальная фича (`jwu_features` / `jwu feature list`), либо ничего
> (`jwu job start --title "…"`). Если папка не привязана ни к одному воркспейсу — скажи
> об этом пользователю и предложи подключить проект.
> Если папка не привязана ни к одному воркспейсу (`source` не `cwd`) — **не логируй работу**:
> записи уедут в чужой контур. Сначала подключи проект — скилл **jwu-workspace-setup**
> (`jwu init`).

> **Префикс в воркспейсе без Jira.** Правило то же — префикс берётся из имени ветки той же
> регуляркой. Ключи локальных фич специально сделаны в формате ключей Jira (`HOMEJWU-12`),
> поэтому ветка `HOMEJWU-12-dark-theme` даёт префикс без каких-либо особых действий. Если в ветке
> префикса нет, а работа привязана к фиче — **предложи** префикс из `feature_key` и спроси
> подтверждение, сам не подставляй.

> **Где брать изменения.** `git diff` делается в папке воркспейса
> (`jwu_workspace_paths()`), а не в произвольном каталоге. Несколько папок с правками —
> уточни у пользователя, для какой нужен коммит.

## Когда

Во время цикла работы (job) после правок — нужен текст коммита по тому, что сейчас
накопилось в рабочем дереве. Скилл **показывает текст**, `git add`/`git commit`/`git push`
делает пользователь сам (правило проекта).

## Что считается «изменениями»

Все текущие изменения относительно `HEAD` — staged + unstaged + новые отслеживаемые
файлы. Не имеет значения, что застейджено, а что нет: формируем сообщение по всей
сумме правок.

Команда для сбора: `git diff HEAD` (покажет и staged, и unstaged; для статуса
по файлам — `git diff HEAD --stat`). Новые untracked файлы тоже учитываем:
`git status --short`.

## Формат

**Сначала проверь правила воркспейса.** Если в контуре есть правило с типом `convention`
про формат коммита — оно главнее канона ниже (`jwu_rules` / `jwu rules`). Правила
`constraint` про ветки («не пушить в develop напрямую») действуют и здесь: сообщение
составить можно, а пуш в запрещённую ветку — нет.

С префиксом задачи (если он есть в имени ветки):

```
<НОМЕР_ЗАДАЧИ>: Краткое описание

- что было сделано (10–15 слов)
- ещё пункт
```

Без префикса (ветка `main`/`develop`/без префикса в имени):

```
Краткое описание

- …
```

## Алгоритм

1. **Ветка:** `git rev-parse --abbrev-ref HEAD`.
2. **Префикс задачи** — извлечь из имени ветки регуляркой `^[A-Z][A-Z0-9]+-[0-9]+`
   (напр. `EXAMPLE-1111-foo-bar` → `EXAMPLE-1111`, `PROJ-2222-x` → `PROJ-2222`).
   - Не нашли? **НЕ выдумывать.** Печатать сообщение без префикса и предупредить пользователя.
3. **Что менялось** — собрать всё:
   - `git diff HEAD --stat` — обзор по файлам.
   - `git diff HEAD` — содержимое правок.
   - `git status --short` — добавит новые untracked файлы (строки `??`).
   - Изменений нет вообще (всё чисто) — сообщи «нет изменений», ничего не печатай.
4. **Язык тела** — определить по `git log -10 --pretty=%s` и писать на этом языке
   (в большинстве jwu-репозиториев — русский).
5. **Заголовок** — одна строка, суть изменений:
   - С префиксом: `<НОМЕР>: <краткое описание>`.
   - Без префикса: просто `<краткое описание>`.
6. **Список** — `- ` пунктами по 10–15 слов: что конкретно сделано (только из реального
   diff/status, не из памяти разговора). Один пункт = одно изменение или группа.
7. **Вывести готовый текст в код-блоке.** Никаких `git add`/`git commit`.

## Пример

Ветка `EXAMPLE-1111-fix-cookie-name`, в дереве (staged + unstaged) — правка cookie-имени:

```
EXAMPLE-1111: Имя токена авторизации вынесено в .env

- Добавлена переменная окружения для имени cookie авторизации
- Поправлено форматирование URL на странице логина
```

Ветка `main`, в дереве — мелкая правка README:

```
Уточнение в README по установке скиллов

- Добавлено пояснение про флаг --skip-agents
```

(+ предупреждение: «Префикс задачи не найден в ветке `main`, пишу без префикса».)

## Частые ошибки

| Ошибка | Правильно |
|---|---|
| Смотрим только staged или только unstaged | Брать всё через `git diff HEAD` + `git status --short` |
| Выдумываем номер задачи | Только из ветки регуляркой; нет — без префикса + предупреждение |
| Пишем пункты «по памяти разговора» | Только из реального `git diff HEAD` |
| Сами вызываем `git add`/`git commit` | Только печатаем текст; коммитит пользователь |
| Добавляем `Co-Authored-By` / упоминание AI | НИКОГДА, никакой атрибуции |

## Порядок фаз — важно

Коммит/пуш — это **Фаза 5** в каноническом флоу `jwu-start-job`. **Перед** коммитом
обязательно должна быть пройдена **Фаза 4 — ревью изменений** через `jwu-job-review`
(по локальному диффу относительно целевой ветки, ДО коммита). Если ревью ещё не было
или ревьювер вернул блокеры — **не печатай коммит-сообщение**, скажи пользователю
сначала прогнать ревью.

## Связанные скиллы

- **jwu-job-review** — Фаза 4 (ревью), запускается ДО этого скилла. Без её успешного
  прогона коммит/пуш считается невалидным циклом.
- **jwu-track-job** — после коммита запиши `--kind phase "Фаза 5 — коммит и пуш" --status done`.
