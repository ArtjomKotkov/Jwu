# jwu: оркестратор воркеров

Сначала **jwu-session-init** в фактической папке проекта: сверь `source=cwd`, ожидаемые `cwd`/`slug` и правила. Папка поручения — абсолютный путь нужного репозитория; воркер сверяет привязку сам. Не считай cwd дочернего процесса или MCP наследуемым. Используй обнаруженные схемы MCP только при совпадении `jwu_workspace_current()` с CLI по папке, источнику и контуру. Иначе используй документированные операции `jwu --workspace <slug> …` с явно заданным `workdir` в shell; не подменяй защищённую запись непроверенной командой.

## Основной чат: выбрать и передать

Основной чат раздаёт поручения, но не берёт, не резервирует, не создаёт и не закрывает работы за воркера и не пишет в их журналы. Воркер получает ключ, а не уже занятую за него работу.

Запускай ровно столько воркеров, сколько попросил пользователь. «Одному» — один список по порядку; «каждую своему» — отдельные сессии. Независимые поручения можно передать параллельно, пересекающиеся — последовательно. Без явного поручения не запускай и не перезапускай воркеров.

На «покажи доску» покажи её через **jwu-todo**, на «обнови доску» — обнови и покажи. Технический снимок номеров — часть показа, не бронь и не отдельное решение. Номер сверяй только со снимком, который видел пользователь. Снимка нет — попроси точный ключ/полный PR или покажи новую доску для нового выбора. Не разрешай старый номер по новой доске. Для известного ключа вне доски не выдумывай раздел.

Передай коротко: действие, точный ключ задачи или полный PR (`проект/репозиторий#номер`), раздел доски, если пункт оттуда, и ограничения пользователя дословно. Например: «Разбери P/r#42 из раздела review. Только черновик, не публикуй». Не вкладывай план, тесты, ветку, секреты или согласие от имени пользователя. Если ключ, раздел выбранного пункта или число воркеров неясны, уточни, не угадывай. Ключ Jira, ID работы и ID чата — разные вещи. Не включай ID работы в обычный бриф. «Не продолжать №N» не значит «без Jira»: сохрани исходный ключ и исключение.

## Воркер: сверить, взять и вести работу

Пройди **jwu-session-init** в своей папке. В собственной сессии доски найди точный ключ в том же разделе, используя свой снимок, не номера Main. Для поручения «взять» сначала проверь существующие работы и владельца; затем атомарно возьми только свободный пункт по своему номеру и ключу, без `for_worker`, через **jwu-todo** / «Вход по поручению с доски» в **jwu-start-job**. Проверь `taken`/`skipped`, ключ, раздел и владельца работы. При чужой или неясной брони, исчезновении пункта или смене раздела сообщи причину. Не бери соседний пункт и не заводи работу вручную вместо пропущенной. Просьба только посмотреть или объяснить не требует взятия. Свою подходящую работу продолжай без дубля; вне доски ищи по ключу и цели и только при необходимости начинай по **jwu-start-job**. Не возобновляй паузу или закрытый цикл без проверки остатка и нужного решения.

Сам сверяй требования, последние комментарии, PR и прежний итог. Ревью веди по **jwu-review-queue**, красную сборку — по **jwu-build-failure**, остальные пункты — по их разделу **jwu-todo**. Для правок пройди «От анализа до первой правки» в **jwu-start-job**: согласуй и запиши план до исполнения. Для простого ревью план правок не нужен. Сверь исходный ключ перед коммитом, PR или 4TEST; противоречие уточни до публикации.

Решения о плане, публикации, статусе и закрытии принимает пользователь в сессии воркера. Скажи простым русским, что случилось и какой следующий шаг рекомендуешь; открой выбор через инструмент своего клиента, а если формы нет — перечисли варианты и дождись ответа. Не дублируй меню в основном чате и не передавай согласие от имени пользователя. Сам продолжи очередь после решения; неизменное согласованное действие не переспрашивай. Обязательные проверки и допуск Git сохраняются.

## Если работаешь в Claude Code

Для отдельного воркера Claude используй штатный **Remote Control**, а не Hermes. Если пользователь попросил включить роль, возьми точное имя этой сессии из `ListAgents` и выполни `jwu worker orchestrator --name NAME` (сессия из `CLAUDE_CODE_SESSION_ID`). Для снятия роли — `jwu worker orchestrator --off`; воркеров это не останавливает. Регистрация роли сама ничего не запускает.

По явной команде запусти `jwu_worker_start(name=…, task=…, cwd=…, user_approved=True, workspace=slug)` или `jwu --workspace SLUG worker start NAME --task-file FILE --cwd DIR --json` с проверенной абсолютной папкой. Не передавай `jobs`/`--job`: не бронируй за воркера и не пиши задание в журнал работы. Jwu добавит служебную шапку. Покажи подтверждённую ссылку из результата или `jwu_worker_list` / `jwu worker list --json`, не угадывай её.

Состояния и ссылки читай через `jwu_worker_list`; воркер сам связывает взятые работы через `jwu_worker_report(state, note, jobs=[…])` / `jwu worker report`. Для фактов и итогов используй `SendMessage` по проверенному адресату (`ListAgents`), если инструменты доступны; для решения — `AskUserQuestion` в сессии воркера, не в основном чате. По завершении сверяй итог и закрытие заявленных работ, прежде чем штатно остановить завершённый воркер. При явной остановке с открытыми работами отдельно покажи, какие работы уйдут на паузу; `force=True` / `--force` только после согласия именно на паузу. Остановка: `jwu_worker_stop(name=…, force=False, user_approved=True, workspace=slug)` / `jwu worker stop NAME --yes` (с подтверждённым `--workspace` и папкой); перечитай состояние. Не перезапускай упавший процесс без нового поручения.

## Если работаешь в Codex

Для отдельной интерактивной сессии используй штатный чат Codex с проверенной папкой, только если можешь создать и проверить его в текущем клиенте. Иначе дай точный короткий бриф для отдельного чата и назови ограничение. Встроенный подагент Codex, если он доступен и его явно попросили, — не отдельный чат с пользователем. Не запускай через него работу, которой понадобится решение в собственном чате. Для решений используй `request_user_input`, если он доступен в текущем режиме, иначе спроси в чате и дождись ответа. Не используй `ListAgents`/`SendMessage`, Claude Remote Control или Hermes gateway вместо возможностей Codex.

## Только в Hermes Desktop

Main читает работы и брони Jwu, но не регистрирует роль, не берёт, не резервирует, не создаёт, не освобождает и не закрывает работу, не пишет в её журнал. Включение роли не запускает воркера. Создание чата и передача поручения — операции Desktop, не Jwu.

Воркер по умолчанию — **отдельный интерактивный чат Hermes в нужном проекте**, видимый в боковом меню. Явное поручение с понятным объёмом и числом воркеров не требует повторного согласия на запуск. `delegate_task` используй только по явной просьбе о фоновом подагенте: он не создаёт отдельный чат. Это не запрещает интерактивному воркеру использовать ограниченный поданализ, если его рабочий процесс это допускает. Не подменяй запуск Codex, Claude или фоновым подагентом, если проектный чат создать не удалось. Пустой чат — только по явной просьбе.

Загрузи `jwu-hermes-orchestrator`. До создания проверь совместимость локального шлюза и Python payload по `jwu-hermes-orchestrator`. При неизвестной совместимости остановись. Из проверенного родительского чата (`HERMES_SESSION_ID`) запусти `scripts/run_with_gateway.sh scripts/worker_launch.py --create-only --title …` с уникальным заголовком. Это первый этап одного поручения, не пустой тестовый чат. Проверь связанный с Main точный ID и `session.info` созданного чата. Только после сверки проекта, папки и модели отправь короткий бриф в этот же чат: `scripts/run_with_gateway.sh scripts/worker_relay.py send --target ID --title TITLE --project PROJECT_ID --message-file FILE`. Не создавай второй чат для доставки. Если маршрут не подтверждён, сообщи причину без отправки. При неопределённом результате допустим только точный повтор того же брифа по тому же маршруту; не отправляй вручную.

Main сверяет по точному ID созданного чата проект, workdir и его фактические `model`/`provider` с запрошенными (иначе — с родительскими). При расхождении не отправляет бриф. Отдельно проверяет точный текст в транскрипте. `queued` не означает доставку; доставка не означает взятие. Сообщи ключ, ссылку и подтверждённое состояние: «Поручение доставлено, воркер ещё не подтвердил, что взял работу» либо «Воркер взял работу» после подтверждения воркера или чтения соответствующей активной работы с его владельцем. Частичный сбой не повод создавать второй чат или брать пункт из Main.

Решения по работе — в чате воркера, не через Main. Если нужен новый выбор, сразу предложи ближайший безопасный шаг простым русским и вызови `clarify` в том же чате с непустым `questions` и `choices`. Если форма не появилась, проверь `outcome`, `notice` и `error`; если она недоступна, напиши «Жду твоего выбора», варианты по номерам и что останется без изменений. Не дублируй карточку в Main и не пересылай «да» от имени пользователя. Уже согласованный шаг не требует нового вопроса; обязательные проверки и допуск Git сохраняются. После решения воркер сам продолжает очередь.

**Обратный отчёт обязателен.** Обычный итог по PR/работам и нерешённые вопросы воркер отправляет в проверенный родительский чат через встроенный `session_mailbox`. Main и воркер используют ту же пассивную почту для рабочих вопросов и ответов в обе стороны. ID чатов и сообщений передавай полями инструмента, не вставляй их в текст. Почта не запускает ход и не заменяет решение пользователя в `clarify`. При недоступном маршруте или отказе инструмента сообщи блокер в своём чате и не подменяй почту отправкой промпта, CLI, записью в БД или наблюдателем. Запись в Jwu и ответ в своём чате не означают доставки.

**Автоматического маршрута нет: архив чата — только вручную в Hermes Desktop.** После итога оставь чат открытым, сам не запрашивай архив и не включай его в меню закрытия работы. Если пользователь сам спросил, укажи «Архивировать» в меню именно нужного чата. Не используй скрипт и не передавай запрос на архив письмом или промптом. Отчёт — не поручение архивировать.
