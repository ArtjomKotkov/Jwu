# jwu: задачи на комментах PR (Bitbucket tasks)

## Overview

В Bitbucket Server под комментом PR можно повесить **задачу** — короткую строку с
чекбоксом. Ревьювер видит чек-лист у себя в PR, а сессия Claude — список «что сделано,
что нет» в `jwu pr <id>` / `jwu_pr()` (поле `open_tasks`) и в `jwu pr-task list`.
Это **единственный** список прогресса по PR: в работы (jobs) задачи не зеркалятся.

> **MCP-first.** `jwu_pr_tasks(pr_id, project, repo)` — список; `jwu_pr_task_add(...)` —
> создать; `jwu_pr_task_done(task_ids, reopen=False)` — закрыть / открыть заново.
> Bash-фолбэк: `jwu pr-task list|add|done|reopen` (запись — только с `--yes`).
>
> **Только Bitbucket.** У GitHub-контура задач на комментах нет — инструмент откажет;
> там чек-лист живёт в теле PR.

## Три правила, которые нельзя обойти

1. **Текст задачи пишет пользователь.** Никогда не придумывай формулировку сам и не
   бери её из коммента ревьювера «как есть». Покажи коммент, **спроси** текст задачи.
   Если пользователь сказал «заведи таску по этому замечанию» без текста — предложи
   свой вариант ОДНОЙ строкой и дождись подтверждения или правки.
2. **До 10 слов.** Это чек-лист, а не описание. Инструмент отказывает на длинном
   тексте — переформулируй вместе с пользователем, а не режь молча.
3. **Создание — ВНЕШНЯЯ запись, только после явного «да».** Покажи превью:
   PR, коммент-якорь (кто и что написал, либо «свой коммент»), текст задачи. Слово
   «ок/да/давай» — создаёшь; всё остальное — не создаёшь.

## Шаги: создать

1. **Найди PR и коммент.** `jwu_pr(pr_id, project, repo)` → `comments[]` с `id`,
   автором, `file:line` и текстом. Якорем может быть **любой** коммент, включая свой.
2. **Если коммента-якоря нет** (пользователь сам придумал, что доделать) — задача
   вешается на **свой новый коммент**: общий (`comment_id=None`) либо на строку файла
   (`path=…, line=…`; `line` — строка новой версии, правый номер в
   `jwu_pr_diff(pr_id, path, numbered=True)`; тип строки jwu берёт из диффа, строка вне
   диффа — ошибка до отправки). Текст коммента — `comment_text`, по умолчанию совпадает
   с текстом задачи; спроси, если хочется другой.
3. **Спроси текст задачи** (правило 1), проверь длину (правило 2).
4. **Покажи превью и дождись «да»** (правило 3).
5. **Создай**: `jwu_pr_task_add(pr_id, text, comment_id=…, project=…, repo=…)`.
   Ответ — задача с `id`, `state=OPEN`, `comment_id`. Сообщи id пользователю.

## Шаги: закрыть

Закрывать задачи — по мере правок, когда сделано. Собери пачку за раз:

1. `jwu_pr_tasks(pr_id)` → открытые (`state=OPEN`).
2. Покажи, какие закрываешь и почему (коротко, что именно поправлено).
3. После «да» — `jwu_pr_task_done(task_ids=[...])`. Одно подтверждение на всю пачку.
4. Ошибся — `jwu_pr_task_done(task_ids=[...], reopen=True)`.

## Где это всплывает само

- **jwu-resume-job**: при подхвате работы открытые задачи PR — это «что осталось».
- **jwu-job-review**: замечания ревьювера-субагента можно превратить в задачи PR —
  но только этим скиллом, с текстом от пользователя.
- **jwu-analyze-day**: состояние PR `открытые задачи: N` — PR ещё не готов к мержу.
- Дельты `new_pr_task` / `pr_task_resolved` и уведомление в Telegram о новой задаче.

## Текст от имени пользователя (голос)

Итоговую формулировку любого текста, который уйдёт наружу от имени пользователя или
отдаётся ему «для копирования», пишет **агент голоса**, а не этот скилл:

1. Собери **факты** — что сказать (сценарий → следствие → просьба; или что сделано),
   на что отвечаем (цитата), нужные имена из кода. Формулировать не надо.
2. `jwu_voice_profile()` → поле `agent` (дефолт `voice-writer-sample`, проектный задаётся
   `jwu voice agent <имя>`). Запусти его через Agent (`subagent_type` = `agent`) и передай
   `channel`, `audience`, `facts`, `context`, `limits`. Агент только пишет, наружу ничего не шлёт.
3. Покажи пользователю текст целиком (и «что я предположил», если не пусто) → правки →
   явное «да» → отправка этим скиллом.
4. Пользователь поправил или отклонил текст — спроси одной строкой «Записать правку в
   профиль голоса?»; «да» → `jwu_voice_feedback(channel, verdict, before, after, reason)`.

Каналы: `pr_comment` для текста коммента-якоря; аудитория `colleague`. **Текст самой задачи по-прежнему формулирует пользователь** (правило 1) — голос его только выравнивает под 10 слов, если пользователь попросил.

## Частые ошибки

- Создать задачу с текстом из коммента ревьювера, не спросив пользователя.
- Заводить задачу на GitHub-PR — там инструмент откажет, не пытайся обойти.
- Дублировать задачи записями `jwu job add --kind todo` — список один, он в PR.
