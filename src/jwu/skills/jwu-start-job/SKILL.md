# jwu: старт и трекинг работы (job)

## Overview

Каждый **цикл работы** над задачей трекается отдельным объектом **работа (job)** в `jwu`: прогресс
по фазам, записи и замечания, связь с задачей (1) и PR (N). Новый раунд правок (напр. после ревью)
= новая работа. Пока просят «проанализировать» — **только анализ и план, никаких правок кода**.
Аргумент — ключ задачи (напр. `PROJ-399`); голый номер без префикса — спроси полный ключ.

> **MCP-first.** Read-операции доступны как MCP-инструменты jwu — **предпочитай их**,
> bash `jwu …` ниже это фолбэк (если MCP-сервер не подключён). Аргументы совпадают с флагами CLI:
> `jwu task <KEY>` → `jwu_task(key)` · `jwu tasks --view mine` → `jwu_tasks(view, jql)` ·
> `jwu changes` → `jwu_changes()` · `jwu jobs …` → `jwu_jobs(task, pr, status)` ·
> `jwu pr <id> …` → `jwu_pr(pr_id, project, repo)` · `jwu builds <id>` → `jwu_builds(pr_id, project, repo)` ·
> `jwu build <id>` → `jwu_build(pr_id, project, repo, url)` · `jwu attachments <KEY> [--download]` → `jwu_attachments(key, download, kinds, dest)`.
> Ключ SDESK-* автоматически уходит в инстанс SDESK. Запись — тоже MCP-first:
> `jwu job start` → `jwu_job_start(task_key, title)` · `jwu job add` → `jwu_job_add(job_id, text, kind, status)` ·
> `jwu job link` → `jwu_job_link(job_id, pr, project, repo)` · `jwu job done/cancel` → `jwu_job_status(job_id, status)` ·
> `jwu note` → `jwu_note(key, text)`. Bash-эквиваленты — фолбэк.
> **Воркспейс = где лежит код.** jwu работает в контексте *воркспейса*: он определяется
> автоматически по текущей папке, проверить — `jwu_workspace_current()`
> (bash: `jwu workspace current --json`).
>
> **Код проекта лежит ИМЕННО в папках воркспейса.** Их список с тегами приходит сразу
> в `jwu_workspace_current()` и в ответе `jwu_job_start()` (поля `paths` и `known_tags`),
> отдельный вызов нужен только чтобы отфильтровать по тегу — `jwu_workspace_paths(tag=…)`
> (bash: `jwu workspace paths`). Ищи и правь только в этих папках;
> остальное на диске к задаче отношения не имеет. У папок есть **теги** («legacy-бэкенд»,
> «новая-версия», «фронт») — по ним понятно, что где: `jwu_workspace_paths(tag="legacy-бэкенд")`.
> Не угадывай по имени каталога — спроси теги. Пользователь просит пометить папку —
> `jwu_workspace_tag(path, add=[...])` (bash: `jwu workspace tag <DIR> --add <тег>`).
>
> **У воркспейса есть ПРАВИЛА** — то, что знает о проекте человек, но не знает код:
> запреты (⛔ `constraint`), инструкции (`howto` — как поднять стенд, прогнать тесты),
> соглашения (`convention` — ветки, формат коммита), грабли (`gotcha`), справка (`info`).
> Правила приходят готовым текстом в поле `rules_md` — оно есть и в `jwu_workspace_current()`,
> и в ответе `jwu_job_start()`. Общие правила там целиком, у правил конкретных
> репозиториев — только заголовки. Как только понял, в какой папке правишь, возьми её
> правила целиком: `jwu_rules(tag="legacy-бэкенд")` (bash: `jwu rules --tag legacy-бэкенд`).
> **Записи `⛔ ЗАПРЕТ` обязательны к исполнению** и важнее твоего удобства: если правило
> мешает выполнить просьбу — не обходи его молча, скажи об этом пользователю.
> Пользователь формулирует правило уровня проекта («не пушь в develop», «стенд поднимается
> так-то») — предложи сохранить: `jwu_rule_add(title, text, kind, tag)`
> (bash: `jwu rule add "…" --kind constraint`).
>
> **Провайдер контура** (`provider` в ответе `jwu_workspace_current()`) говорит, откуда
> берутся задачи и PR: `jira` (Jira + Bitbucket + Jenkins), `github` (Issues + PR + Actions)
> или `local`. Инструменты одни и те же — меняется только формат ключа задачи: `PROJ-123`
> у Jira, `dndeck#42` у GitHub. Если `provider=local` — инструменты задач **не вызывай**:
> якорь работы там либо локальная фича (`jwu_features` / `jwu feature list`), либо ничего
> (`jwu job start --title "…"`). У GitHub нет таймтрекера — `jwu_worklog` там откажет. Если папка не привязана ни к одному воркспейсу — скажи
> об этом пользователю и предложи подключить проект.
> Если папка не привязана ни к одному воркспейсу (`source` не `cwd`) — **не логируй работу**:
> записи уедут в чужой контур. Сначала подключи проект — скилл **jwu-workspace-setup**
> (`jwu init`).


## Шаги

0. **Определи воркспейс, где лежит код и по каким правилам тут работают:**
   `jwu_workspace_current()`, затем `jwu_workspace_paths()` — это единственные папки,
   в которых стоит искать и править. Теги подсказывают, куда именно идти («legacy-бэкенд»
   vs «новая-версия»); если папок несколько и неясно, в какой из них задача — **спроси**,
   а не перебирай все.
   **Определив папку — сразу возьми её правила целиком:** `jwu_rules(tag="<тег папки>")`.
   Общие правила уже приехали в `jwu_workspace_current()`, а по тегам там только индекс
   без текста. Запреты (⛔) и соглашения из правил действуют на весь цикл: план, который
   их нарушает, показывать нельзя.
   Дальше две ветки:
   - **есть внешний трекер** (`provider` = `jira` или `github`) — всё как ниже, якорь
     работы это ключ задачи: `PROJ-123` у Jira, `dndeck#42` у GitHub;
   - **`provider=local`** — вместо `jwu task <KEY>` смотри карточку локальной фичи
     (`jwu feature show <KEY>` / `jwu_features()`), работу заводи как
     `jwu job start --feature <KEY> --title "<суть цикла>"`, а если фичи нет —
     `jwu job start --title "<суть>"` (работа без якоря). **Ключ задачи не выдумывай.**
     Фаза 1 там сводится к прогону локальных тестов — конфликт и CI смотреть негде.

1. **Карточка задачи целиком:** `jwu task <KEY>` (поля: `status`, `description`, `comments`, `links`,
   `pull_requests`, `branches`, `commits`, `notes`, плюс секция «Работы»; `--json` если нужна структура).
   **Сначала смотри `status`.** Done / Closed / Resolved → не планируй правки, сообщи и спроси.

2. **Создай работу (всегда новую):**
   - `jwu jobs --task <KEY>` — **обязательно** проверь существующие работы. Если они есть —
     **предупреди пользователя** (перечисли id/заголовки/статусы), но **всегда начинай новую**:
     `jwu job start <KEY> --title "<суть цикла>"`. Существующие работы НЕ продолжай.
   - Запиши id новой работы — он нужен для всех `jwu job add/link`.

3. **Контекст — экономно, без фанатизма** (не дампь весь JSON, бери суть):
   - **Комменты** — вычитай все, выдели требования/договорённости/решения. **Сверяй время коммента
     с последними правками ветки:** коммент ПОСЛЕ последнего пуша — актуален и в ветке ещё НЕ учтён;
     предложенные ревьюером варианты надо попробовать, а не отмахнуться.
   - **PR** — из `pull_requests`/секции «Работы»; детали/конфликт нужного: `jwu pr <id> --project <KEY> --repo <slug>`. **Замечания ревью берутся отсюда** — в выводе (и в `--json` поле `comments`) идут все комментарии PR: верхний уровень и ответы (`depth`), inline с `file:line`, свежие треды первыми. Если `NEEDS_WORK`, а `comments` пуст — проверь `--project/--repo` (без них берутся дефолтные из конфига). Привяжи к работе: `jwu job link <JOB_ID> --pr <id> --project <KEY> --repo <slug>`.
   - **Статус CI-сборок PR** — в выводе `jwu pr` есть секция «Сборки» (и поле `builds` в `--json`): состояние сборок по head-коммиту (✅/❌/🔄). Быстрый список — `jwu builds <id> --json`. **Если сборка красная (FAILED)** — разбери причину скиллом **build-failure** (субагент `jenkins-build-analyst`, ходит в `jwu build <id> --json`): что упало и почему, наш баг или регресс из целевой ветки. Красный билд лечи в **Фазе 1** наравне с конфликтом. (Команды `builds`/`build` не зависят от Jira.)
   - **Связанные задачи** — открывай `jwu task <KEY>` по `links` только если на них **явно** ссылаются. Не уходи рекурсивно вглубь.
   - **Вложения (скриншоты багов, логи, файлы, документы)** — список и счётчики по видам даёт `jwu attachments <KEY>` (он же в `jwu task` секцией «Вложения» и в поле `attachments` у `--json`; видео — только в списке, не качаются).
     **Если вложения есть — спроси пользователя ПЕРЕД анализом** (вопросом вида «Нашёл N изображений, M логов и K документов — проанализировать их?») и **дождись ответа**. Не качай молча.
     После согласия скачай: `jwu attachments <KEY> --download` (по умолчанию image/log/doc/archive в `<tmp>/jwu/<KEY>/`; сузить — `--kind image --kind log`). Команда печатает локальные пути — открывай их через **Read** (изображения читаются визуально, логи/JSON/pdf — как текст; архивы распаковываются рядом в `*.extracted/`). Связывай увиденное (текст бага на скрине, стек в логе) с требованиями из комментов.

4. **Определи:** что сделать и **в каком проекте/репо** (по dev-панели / `branches` / `pull_requests` / префиксу ключа).

5. **План по КАНОНИЧЕСКИМ ФАЗАМ** (фазы процесса, не «список задач»; пункты раскладываются ВНУТРИ фаз).
   Порядок фиксированный, фиксируй фазы записями работы `jwu job add <JOB_ID> --kind phase`:
   - **Фаза 1 — мердж/устранение конфликта + красный CI. ВСЕГДА первой.** PR/ветка в конфликте → сначала смердить целевую ветку и разрулить (`can_merge`). Красная сборка (см. секцию «Сборки» / `jwu builds`) — разобрать через **build-failure** и устранить здесь же (часто это регресс из целевой ветки, лечится её влитием). Остальное — после.
   - **Фаза 2 — анализ текущей реализации + план правок** (учесть и **попробовать** актуальные предложения ревьюеров).
   - **Фаза 3 — правки и фиксы** по согласованному плану. Сверяйся с правилами воркспейса:
     `constraint` — чего нельзя делать вообще, `convention` — как принято (нейминг, стиль),
     `howto` — как здесь поднимают стенд и гоняют тесты, `gotcha` — на чём тут спотыкаются.
   - **Фаза 4 — ревью изменений. ВСЕГДА ДО коммита/пуша.** Запускается через скилл **jwu-job-review** субагентом-ревьювером **по локальным изменениям** (рабочее дерево + ещё не запушенные коммиты vs. целевая ветка), чтобы поймать проблемы пока ничего не зафиксировано в истории. Имя субагента **не хардкодится** — его передаёт пользователь аргументом скилла (`/jwu-job-review <reviewer-subagent>`). Если из контекста (стек, репо, прошлые ревью) очевидно подходит конкретный субагент — **предложи** его как кандидата, но **всегда уточни у пользователя** и запускай только после подтверждения. Если кандидата нет — используется дефолтный `reviewer-jwu-sample`. Замечания фиксируй в работу через **jwu-track-job** (шапка `--kind review`, детали `remark`/`bug`/`warning`/`constraint`). Если ревьювер вернул блокеры или важные доработки — **возвращайся в фазу 3** (новая итерация правок), потом снова Фаза 4. На Фазу 5 переходим, **только когда ревьювер сказал «можно мержить»** или остались только мелкие замечания, которые пользователь явно решил оставить.
   - **Фаза 5 — коммит и пуш/обновление PR.** **ВСЕГДА последней.** Делается только после успешного прохождения Фазы 4. Коммит/пуш — по правилу проекта, после явного подтверждения пользователя. Перед пушем перечитай правила про ветки и формат коммита (`constraint` / `convention`): «не пушить в develop напрямую» — это запрет, а не пожелание.
   Большую задачу веди постепенно: начни с фазы 1, дальше по одной.
   Замечания ревьюеров фиксируй как `jwu job add <JOB_ID> --kind remark "<...>"`; явные запреты («не трогать X», «гонять без Y», «не пушить в Z») — `--kind constraint` (⛔ ЗАПРЕТ).

   **Канонический порядок ВСЕГДА: правки → ревью → коммит.** Не наоборот. Если коммит уже случился без ревью — всё равно прогоняй Фазу 4 до пуша; пушить «грязный» коммит без ревью **запрещено**.

   **Как вести записи по ходу работы** — это отдельная дисциплина: типы `phase` (со статусами), `bug` / `bug-resolved` (история «нашли → исправили»), `test-pass` / `test-fail` (прогоны тестов), `warning`, плюс фразовые триггеры. Полная таксономия и правила — в скилле **jwu-track-job**; обращайся к нему всякий раз, когда нужно что-то записать в работу во время исполнения.

6. **Покажи план пользователю.** По завершении цикла — `jwu job done <JOB_ID>`.

## КРИТИЧНО — подтверждение правок

- Пока просят анализ — **не редактируй код, не коммить, не пушь**.
- Любые правки/изменения — **только после явного подтверждения** пользователя (план/диф).
  Правило проекта (нельзя коммитить и пушить без подтверждения) распространяется и на правки.

## Заметки

- Read-only по Jira/Bitbucket: только чтение + запись работы в локальную память (`jwu job …`).
- Прогресс трекай через `jwu job` (фазы/записи/связи с PR); разовую заметку можно `jwu note <KEY>`.
- Статусы важнее устаревших комментов — всегда сверяйся с текущим `status`.
- Завершённые/текущие работы видны при открытии задачи (`jwu task`) и PR (`jwu pr`), и в дашборде (вкладка «Работы»).
- Экономь контекст: нужное из карточки, без обхода всех связей и всех PR.
