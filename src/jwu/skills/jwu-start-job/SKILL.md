description: Use when the user wants to START a new jwu «работа (job)» — on a Jira/GitHub task key or without one («начни работу по PROJ-399», «проанализируй задачу», «новый цикл правок», «поправь конфликт в PR 1092», «почини сборку», «/jwu-start-job [KEY]»). Creates the job, gathers context (task, comments, PRs, builds, attachments), makes a phased plan, and — only when code will change — a dedicated git worktree per repo in the workspace jobs folder; brings up the job's own test stand by the workspace testenv rule when needed. Logs progress into the job while working. Analysis only until the user confirms edits. To continue an existing/closed job — jwu-continue-job; to finish — jwu-close-job.

# jwu: начать работу (job)

## Overview

Работа (job) — один цикл работы ради одной цели: сделать задачу, поправить конфликт,
починить сборку, внести правки по PR. У работы журнал (фазы, решения, баги, тесты), связь
с задачей (0–1) и PR (N), **свои рабочие копии** и **свой стенд**, если они нужны. Цель
достигнута — работу закрывают скиллом **jwu-close-job** (итог для трекинга времени +
уборка). Продолжить начатую или переоткрыть закрытую — **jwu-continue-job**.

Аргумент — ключ задачи (`PROJ-399`, `dndeck#42`) или ничего. Голый номер без префикса —
спроси полный ключ. Пока просят «проанализировать» — **только анализ и план, без правок**.

> **MCP-first.** Предпочитай MCP-инструменты jwu, bash `jwu …` — фолбэк. Чтение:
> `jwu_context(key)`, `jwu_task(key)`, `jwu_jobs(task, status)`, `jwu_pr(pr_id, project, repo)`,
> `jwu_builds`, `jwu_build`, `jwu_attachments(key, download)`, `jwu_branches(key)`.
> Работа: `jwu_job_start(task_key, title)`, `jwu_job_add(job_id, text, kind, status)`,
> `jwu_job_link(job_id, pr, project, repo)`, `jwu_job_worktree(job_id, repo, branch, base)`,
> `jwu_job_resource(job_id, kind, ref)`, `jwu_disk()`.
> **Воркспейс = где лежит код.** jwu работает в контексте *воркспейса*: он определяется
> автоматически по текущей папке, проверить — `jwu_workspace_current()`
> (bash: `jwu workspace current --json`).
>
> **Код проекта лежит ИМЕННО в папках воркспейса.** Их список с тегами приходит сразу
> в `jwu_workspace_current()` и в ответе `jwu_job_start()` (поля `paths` и `known_tags`),
> отдельный вызов нужен только чтобы отфильтровать по тегу — `jwu_workspace_paths(tag=…)`
> (bash: `jwu workspace paths`). Ищи и правь только в этих папках;
> остальное на диске к задаче отношения не имеет. У папок есть **теги** («legacy-бэкенд»,
> «новая-версия», «фронт») — по ним понятно, что где: `jwu_workspace_paths(tag="legacy-бэкенд")`.
> Не угадывай по имени каталога — спроси теги. Пользователь просит пометить папку —
> `jwu_workspace_tag(path, add=[...])` (bash: `jwu workspace tag <DIR> --add <тег>`).
>
> **У воркспейса есть ПРАВИЛА** — то, что знает о проекте человек, но не знает код:
> запреты (⛔ `constraint`), инструкции (`howto`), тестовое окружение (🧪 `testenv` — как
> работе поднять СВОЙ стенд и снести его),
> соглашения (`convention` — ветки, формат коммита), грабли (`gotcha`), справка (`info`).
> Правила приходят готовым текстом в поле `rules_md` — оно есть и в `jwu_workspace_current()`,
> и в ответе `jwu_job_start()`. Общие правила там целиком, у правил конкретных
> репозиториев — только заголовки. Как только понял, в какой папке правишь, возьми её
> правила целиком: `jwu_rules(tag="legacy-бэкенд")` (bash: `jwu rules --tag legacy-бэкенд`).
> **Записи `⛔ ЗАПРЕТ` обязательны к исполнению** и важнее твоего удобства: если правило
> мешает выполнить просьбу — не обходи его молча, скажи об этом пользователю.
> Пользователь формулирует правило уровня проекта («не пушь в develop», «стенд поднимается
> так-то») — предложи сохранить: `jwu_rule_add(title, text, kind, tag)`
> (bash: `jwu rule add "…" --kind constraint`).
>
> **Провайдер контура** (`provider` в ответе `jwu_workspace_current()`) говорит, откуда
> берутся задачи и PR: `jira` (Jira + Bitbucket + Jenkins), `github` (Issues + PR + Actions)
> или `local`. Инструменты одни и те же — меняется только формат ключа задачи: `PROJ-123`
> у Jira, `dndeck#42` у GitHub. Если `provider=local` — инструменты задач **не вызывай**:
> якорь работы там либо локальная фича (`jwu_features` / `jwu feature list`), либо ничего
> (`jwu job start --title "…"`). У GitHub нет таймтрекера — `jwu_worklog` там откажет. Если папка не привязана ни к одному воркспейсу — скажи
> об этом пользователю и предложи подключить проект.
> Если папка не привязана ни к одному воркспейсу (`source` не `cwd`) — **не логируй работу**:
> записи уедут в чужой контур. Сначала подключи проект — скилл **jwu-workspace-setup**
> (`jwu init`).

## Шаги

0. **Где и по каким правилам.** `jwu_workspace_current()` — папки, теги, правила (`rules_md`).
   Папку задачи определил — сразу `jwu_rules(tag="<тег>")` целиком. Запреты (⛔) действуют
   на весь цикл. `provider=local` — якорь работы локальная фича (`jwu_features()`), ключ
   задачи не выдумывай; нет фичи — работа без якоря.

1. **Что уже известно.** `jwu_context(KEY)` — закреплённый статус, решения, грабли, локальные
   ветки по задаче. Потом карточка: `jwu_task(KEY)`. **Статус Done/Closed** — правки не
   планируй, сообщи и спроси.

2. **Есть ли уже работа.** `jwu_jobs(task=KEY)`:
   - **активная по той же цели** — не плоди новую: это **jwu-continue-job**, скажи пользователю;
   - **закрытая по той же цели** (например, вернули с тестов) — предложи переоткрыть
     (**jwu-continue-job**) или начать новую, если цель другая;
   - иначе — `jwu_job_start(KEY, title="<цель цикла>")`. Запомни `job_id`.
   **Цель в заголовке** — по ней потом решают, когда закрывать: «Сделать задачу»,
   «Конфликт PR #1092 с develop», «Красная сборка #1887», «Правки по ревью PR #1027».

3. **Контекст — экономно.** Комменты (сверяй время с последним пушем: коммент после пуша не
   учтён), PR и замечания (`jwu_pr`, привяжи `jwu_job_link`), сборки (красная — скилл
   **build-failure**), связанные задачи — только явно упомянутые. **Вложения** — сначала
   спроси «нашёл N картинок, M логов — смотреть?», качай после «да».

4. **План по фазам** (записывай `kind=phase`):
   - **Фаза 0 — рабочее место.** Только если будут **правки кода** (чистый анализ — пропусти):
     1) `jwu_disk()` — `ok=False` → стоп: скажи, сколько свободно и что можно убрать
        (`leftovers` закрытых работ, docker «можно освободить»), жди решения;
     2) на **каждый** репозиторий, который будешь править, —
        `jwu_job_worktree(job_id, repo="<папка воркспейса>", branch="<ветка>")`. Ветка по
        задаче уже есть (`jwu_branches`) — передай её; нет — по `convention` воркспейса.
        Папка копий не задана — попроси `jwu workspace jobs-dir <путь>`.
     3) **дальше весь код — в копии** (`ref` из ответа), основную папку не трогай.
   - **Фаза 1 — конфликт и красный CI**, всегда первой.
   - **Фаза 2 — анализ реализации и план правок** (предложения ревьюеров — попробовать).
   - **Фаза 3 — правки.** Нужен стенд — см. «Стенд работы» ниже.
   - **Фаза 4 — ревью до коммита**: **jwu-job-review** (субагента предложи, подтверди у
     пользователя). Блокеры — назад в фазу 3.
   - **Фаза 5 — коммит и пуш** после «да» пользователя, по правилам веток и коммитов.
   Порядок всегда: правки → ревью → коммит.

5. **Покажи план** и жди подтверждения правок.

6. **Цель достигнута** (задача сделана, конфликт поправлен, сборка зелёная, правки по PR
   внесены и запушены) — **предложи закрыть работу**: скилл **jwu-close-job**. Не оставляй
   сделанную работу открытой: без закрытия нет итога для трекинга времени, а стенд и копии
   продолжают есть диск.

## Стенд работы

Нужно тестировать на стенде — работа поднимает **свой**, по правилу воркспейса
**🧪 `testenv`** (`jwu_rules()` → kind `testenv`, с тегом репозитория). Нет такого правила —
спроси у пользователя, как поднимать, и предложи сохранить его `jwu_rule_add(…, kind="testenv")`.

1. `jwu_disk()` перед подъёмом и перед сборкой образов — мало места → стоп и вопрос.
2. **Всё помечай работой:** compose — `docker compose -p jwu-job<id> …`; `docker run/build/
   volume create/network create` — с `--label jwu.job=<id>`. Порты — со смещением по номеру
   работы, как сказано в правиле (иначе два стенда подерутся).
3. Что метку не несёт (образ, собранный чужим скриптом, каталог кеша, дамп БД) —
   `jwu_job_resource(job_id, kind, ref)`. Уборка при закрытии снесёт ровно это и помеченное.
4. Запиши в журнал, как поднят стенд и где он (`kind=note`): адрес, порты, логин тестовый.

## Журнал работы

Веди журнал по ходу, не в конце: закончил шаг — запись.

### Типы записей

| тип | бейдж | когда использовать |
|---|---|---|
| `phase` | — | веха процесса: Ф1 мердж → Ф2 анализ → Ф3 правки → Ф4 коммит. Статус: `--status pending\|done`. |
| `note` | · | нейтральный контекст/факт/прогресс (стенд, доступы, наблюдения). Дефолт. |
| `decision` | 🧭 РЕШЕНИЕ | **наш выбор подхода с обоснованием** («решили делать так, потому что…»): выбранный вариант, причина, отвергнутые альтернативы. |
| `remark` | ✎ | замечание **ревьюера** из PR (а не свой вывод!). |
| `constraint` | ⛔ ЗАПРЕТ | чего делать **НЕЛЬЗЯ**: «не трогать X», «гонять без Y», «не пушить в Z». |
| `warning` | ⚠ ВНИМАНИЕ | риск/потенциальная проблема — ещё не подтверждённый баг и не запрет. |
| `bug` | 🐛 БАГ | **найденный** баг: симптом, где, как воспроизвели. |
| `bug-resolved` | ✅ БАГ ИСПРАВЛЕН | баг **починили** — отдельной записью с сутью фикса. |
| `test-pass` | 🧪 ТЕСТЫ OK | прогон тестов **прошёл**: что гоняли + итог. |
| `test-fail` | 🧪 ТЕСТЫ УПАЛИ | прогон **упал**: команда, сколько/какие упали, суть ошибки. |
| `todo` | 📌 TODO | отложенная **актионабельная** работа в рамках цикла: что ещё доделать. |
| `summary` | 📝 ИТОГ | **одна строка простыми словами, что сделано** за законченный кусок работы: «перенёс правку в 10.8 и починил тесты», «разобрал падение сборки — виноват develop». Без хешей, путей, номеров сборок — это читает человек в сводке дня (Telegram «Что сделал сегодня») и трекинг времени. |
| `review` | 🔍 РЕВЬЮ | **шапка прогона ревью** PR субагентом-ревьювером: кто ревьюил, PR, итерация, вердикт, счётчики и **блок «Замечания:» со списком якорей** (`[B1]…/[I1]…/[M1]…` — блокер/важное/мелкое). Должна быть самодостаточной: записи в jwu неизменяемы, эту шапку нельзя будет потом отредактировать. Ставится скиллом **jwu-job-review** ровно один раз на прогон; конкретные находки — отдельными `remark`/`bug`/`warning`/`constraint`, в начале текста которых **обязательно** повторяется якорь шапки. |

Бейджевые типы подсвечиваются и в `jwu job show`, и в дашборде (вкладка «Работы»).

### Правило проекта — это НЕ запись работы

Записи работы живут ровно один цикл: `constraint` в работе — «в этой задаче не трогаем X».
Если пользователь произносит что-то про **проект вообще** — «никогда не пушь в develop»,
«стенд поднимается вот так», «фронт у нас на pnpm», «миграции руками не правим» — это
**правило воркспейса**, оно должно пережить и эту работу, и эту сессию.

Что делать: **предложи сохранить** (не сохраняй молча — формулировку надо согласовать) и
запиши `jwu_rule_add(title, text, kind, tag)` (bash: `jwu rule add "…" --kind …`):

| Сказанное | kind |
|---|---|
| «никогда/нельзя/не смей …» | `constraint` |
| «делается так: …», «тесты гоняем …» | `howto` |
| «стенд поднимается …», «для тестов нужен docker-compose …», «порты …» | `testenv` |
| «у нас принято …», «ветка от …», «коммит в формате …» | `convention` |
| «осторожно, тут …», «на этом уже обжигались» | `gotcha` |
| «бэк лежит там-то», «за это отвечает …» | `info` |

`tag` ставь, если правило только про один репозиторий (тег его папки); иначе оставь пустым.
Сомневаешься, правило это или разовое ограничение — **спроси**: «записать как правило
воркспейса (навсегда) или как ограничение этой работы?»

### Дисциплина ведения

- **Фазы.** Фиксируй каждую веху `--kind phase`, закрывай `--status done`. Большую задачу веди по одной фазе (Ф1 мердж/конфликт — всегда первой).
- **Баги «нашли → исправили».** На находку — `bug`; на фикс — **парный** `bug-resolved` ОТДЕЛЬНОЙ записью. Исходную `bug`-запись НЕ правь и НЕ удаляй — нужна история «нашли → исправили».
- **Тесты.** На каждый значимый прогон — отдельная запись по результату (`test-pass` / `test-fail`). Если падение = дефект кода, заведи ещё и парный `bug`.
- **Запрет vs предупреждение.** Жёсткое «нельзя» → `constraint`; «осторожно, может сломаться / под вопросом» → `warning`.
- **Решение vs запрет.** `decision` — это НАШ выбор с обоснованием («решили чинить парсер, а не править конфиг на стенде, потому что…»); `constraint` — внешнее «нельзя». Если поймал себя на том, что пишешь «почему сделали так» в `note` — это `decision`.
- **`todo` — только in-cycle.** Отложенное в рамках текущего цикла. Работа закрывается `done`, поэтому «на следующий цикл / на потом вообще» пиши не сюда, а `jwu note <KEY>` на самой задаче — иначе потеряется. Закрытый пункт можно пометить `--status done`.
- **Не подменяй тип на `note`/`remark`,** если по сути это решение / баг / тест / запрет / предупреждение / todo. Тип несёт смысл — по нему потом фильтруют и читают лог.
- **Итог шага — `summary`.** Закончил кусок работы (фаза закрыта, закоммитил, ответил ревьюеру, разобрался с падением) — добавь `summary` одной строкой простыми словами. Минимум одна за сессию по каждой задаче, с которой работал: без неё сводка дня покажет только заголовок задачи.
- **`remark` только для ревью.** Свои находки/блокеры — это `bug`/`warning`, а не `remark`.

### Триггеры по фразе пользователя

- «запиши решение / зафиксируй, почему … / решили …» → `--kind decision`
- «добавь ограничение / констрейнт / зафиксируй запрет» → `--kind constraint`
- «добавь todo / надо ещё … / не забыть …» → `--kind todo`
- «нашли баг / запиши баг / есть баг …» → `--kind bug`
- «баг исправлен / починили баг / резолвнут» → `--kind bug-resolved`
- «добавь предупреждение / warning / осторожно с …» → `--kind warning`
- «запиши прогон тестов / тесты прошли / тесты зелёные» → `--kind test-pass`; «тесты упали / красные» → `--kind test-fail`
- «отметь фазу … (done)» → `--kind phase` (+ `--status done`)
- «запиши итог / что сделал» → `--kind summary`
- «запиши ревью / зафиксируй прогон ревью / результат ревьювера …» → `--kind review` (шапка прогона; конкретные находки — отдельными `remark`/`bug`/`warning`/`constraint`). Обычно ставится автоматически скиллом **jwu-job-review**, руками — только если запускал ревьювера руками.


## Подтверждение

- Пока просят анализ — **не редактируй код, не коммить, не пушь**.
- Правки, коммиты, пуш — **только после явного «да»** пользователя.
- Запись в журнал работы, рабочая копия, стенд — локально, без подтверждения; но на нехватку
  места — всегда стоп и вопрос.
