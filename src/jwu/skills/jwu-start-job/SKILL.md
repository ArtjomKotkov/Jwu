# jwu: начать работу (job)

## Вход по поручению с доски

Main передаёт цель и точные ключи выбранных пунктов, но не создаёт и не резервирует работы. Бриф — не подтверждение владения. Просьба только посмотреть или объяснить не требует взятия. Для поручения «взять в работу» действуй в чате воркера:

1. Пройди **jwu-session-init** в своей папке; сверь `source=cwd`, slug и правила. Выбери постоянное уникальное имя `S` для этой сессии доски (например, `worker-<ID этого чата>`, не ID Main). Передавай его явно и при показе, и при взятии: MCP может быть общим для нескольких чатов.
2. Прочитай `jwu_todo(workspace=slug, session=S, refresh=False)`; CLI для чтения — `jwu --workspace SLUG todo --session S --no-refresh --json`. По `items` найди **точное** равенство `item.key` ключу брифа и сверь группу/цель. Используй **номер этой строки у себя**, не номер у Main. Для PR ключ — из доски целиком, не `issue_key` и не голый номер. Если ключ отсутствует, неоднозначен или цель изменилась — сообщи расхождение; соседний пункт, всю группу или ручной старт не подставляй.
3. Сверь работы по задаче и по полной ссылке PR, включая `paused`, `done`, `cancelled` (не только `active`); прочитай журнал совпавшей цели. Своя уже взятая работа или явно переданная существующая работа с подтверждённой передачей и без параллельного владельца → **jwu-continue-job** по точному ID, без повторного take. Чужая/неясная бронь → сообщи ID и владельца, остановись по этому пункту. Для паузы или закрытого цикла покажи остаток и запроси решение о возобновлении именно этой работы; не создавай дубль и не переоткрывай по одному факту назначения. Для завершённой цели без остатка достаточно итога.
4. Только для свободных выбранных строк вызови `jwu_todo_take(workspace=slug, session=S, numbers=[n], keys=[item.key])` без `for_worker`. Это атомарная проверка и создание для штатных групп. Если MCP недоступен, CLI `jwu --workspace SLUG todo N --session S --no-refresh --json` использует сохранённый показ **этой** сессии, но не принимает `keys`: используй его только если снимок проверен и никто другой не может его перезаписать; иначе остановись. Для групп аддонов сначала проверь контракт обработчика: без подтверждённой защиты от двойного взятия остановись.
5. Разбери `taken` и `skipped` по каждому ключу. При гонке, исчезновении или иной причине пропуска не вызывай `jwu_job_start`: он всегда создаёт новую запись, даже если нашёл `existing_jobs`. После ошибки с неизвестным результатом сначала перечитай доску и работы. Для каждого успеха сначала сверь ключ и раздел в `taken`; при расхождении не приступай к работе. Затем проверь точный `job_id` через `jwu --workspace SLUG job show ID --json`: статус, якорь/PR и запись «Взято сессией» с твоим именем и ключом. Только теперь переходи к анализу/плану или ревью по назначенному скиллу. Решения о правках и публикации остаются в чате воркера.

**Прямой вызов без доски.** Ручной старт новой цели, локальной фичи или работы без якоря описан ниже. Это отдельный сценарий, не запасной способ обойти пропуск на доске.

## От анализа до первой правки

Для новой задачи, бага, конфликта, возврата QA, исправления сборки или замечаний к PR порядок один. Простое ревью чужого PR без правок идёт по своему процессу. Если после ревью попросили исправлять — это уже работа над изменением.

1. **Анализ.** Прочитай поручение, журнал и прошлые решения, карточку и комментарии, относящиеся к делу вложения, PR, замечания и результаты проверок. Сверь с текущим диффом, кодом и ближайшими тестами. Объясни пользователю, что должно работать, что сейчас не так, что подтверждено и что пока гипотеза. Для конфликта назови поведение, которое нужно сохранить с каждой стороны. Недоступный контекст обозначь явно.
2. **План.** Разбей изменение на участки с проверяемым результатом. Назови границы и порядок: что меняем, чего не трогаем. Для каждого нужного прогона укажи что проверяем, где (копия, сервисы или CI), когда и какой результат достаточен. Объедини дорогие проверки на итоговой версии; ранний узкий тест оставь только для конкретной гипотезы или обязательного RED/GREEN. Не отменяй обязательные проверки проекта.
3. **Решение в чате воркера.** Покажи в чате воркера весь план с проверками, дай утвердить или поправить. В Hermes помести сам план в вопрос `clarify` над кнопками: пользователь должен видеть, на что соглашается. Назначение работы и бриф — не согласие. Если этот точный план ещё не согласован, дождись решения. До согласия не применяй патч, не начинай мерж, не создавай стенд или рабочую копию и не запускай тесты. После согласования запиши именно выбранный план и расписание проверок как `decision` в журнал этой работы; перечитай запись. Если правила требуют короткой сверки перед правками, проведи её.
4. **Исполнение.** Иди по записанному плану. При продолжении не согласовывай неизменный план заново. Если изменились цель, объём, порядок работ или условия проверки, остановись до исполнения изменённого плана. Объясни причину и покажи обновлённый план целиком: что уже сделано, какие участки остаются, что добавилось или отпало, где и когда пройдут проверки. Согласуй с пользователем всю новую версию, а не только разницу. Запиши её в журнал как актуальный план и только затем продолжай. План сам по себе не разрешает публикацию.

## Overview

Работа (job) — один цикл работы ради одной цели: сделать задачу, поправить конфликт,
починить сборку, внести правки по PR. У работы журнал (фазы, решения, баги, тесты), связь
с задачей (0–1) и PR (N), **свои рабочие копии** и **свой стенд**, если они нужны. Цель
достигнута — работу закрывают скиллом **jwu-close-job** (итог для трекинга времени +
уборка). Продолжить начатую или переоткрыть закрытую — **jwu-continue-job**.

Аргумент — ключ задачи (`PROJ-399`, `dndeck#42`) или ничего. Голый номер без префикса —
спроси полный ключ. Пока просят «проанализировать» — **только анализ и план, без правок**.

> **MCP-first.** Предпочитай MCP-инструменты jwu, bash `jwu …` — фолбэк. Чтение:
> `jwu_context(key)`, `jwu_task(key)`, `jwu_jobs(task, status)`, `jwu_pr(pr_id, project, repo)`,
> `jwu_builds`, `jwu_build`, `jwu_attachments(key, download)`, `jwu_branches(key)`.
> Работа: `jwu_job_start(task_key, title)`, `jwu_job_add(job_id, text, kind, status)`,
> `jwu_job_link(job_id, pr, project, repo)`, `jwu_job_worktree(job_id, repo, branch, base)`,
> `jwu_job_resource(job_id, kind, ref)`, `jwu_disk()`.
> **Воркспейс = где лежит код.** jwu работает в контексте *воркспейса*: он определяется
> автоматически по текущей папке, проверить — `jwu_workspace_current()`
> (bash: `jwu workspace current --json`).
>
> **Код проекта лежит ИМЕННО в папках воркспейса.** Их список с тегами приходит сразу
> в `jwu_workspace_current()` и в ответе `jwu_job_start()` (поля `paths` и `known_tags`),
> отдельный вызов нужен только чтобы отфильтровать по тегу — `jwu_workspace_paths(tag=…)`
> (bash: `jwu workspace paths`). Ищи и правь только в этих папках;
> остальное на диске к задаче отношения не имеет. У папок есть **теги** («legacy-бэкенд»,
> «новая-версия», «фронт») — по ним понятно, что где: `jwu_workspace_paths(tag="legacy-бэкенд")`.
> Не угадывай по имени каталога — спроси теги. Пользователь просит пометить папку —
> `jwu_workspace_tag(path, add=[...])` (bash: `jwu workspace tag <DIR> --add <тег>`).
>
> **У воркспейса есть ПРАВИЛА** — то, что знает о проекте человек, но не знает код:
> запреты (⛔ `constraint`), инструкции (`howto`), тестовое окружение (🧪 `testenv` — как
> работе поднять СВОЙ стенд и снести его),
> соглашения (`convention` — ветки, формат коммита), грабли (`gotcha`), справка (`info`).
> Правила приходят готовым текстом в поле `rules_md` — оно есть и в `jwu_workspace_current()`,
> и в ответе `jwu_job_start()`. Общие правила там целиком, у правил конкретных
> репозиториев — только заголовки. Как только понял, в какой папке правишь, возьми её
> правила целиком: `jwu_rules(tag="legacy-бэкенд")` (bash: `jwu rules --tag legacy-бэкенд`).
> **Записи `⛔ ЗАПРЕТ` обязательны к исполнению** и важнее твоего удобства: если правило
> мешает выполнить просьбу — не обходи его молча, скажи об этом пользователю.
> Пользователь формулирует правило уровня проекта («не пушь в develop», «стенд поднимается
> так-то») — **предложи** сохранить и покажи формулировку; ⛔ записывай только после его «да»:
> `jwu_rule_add(title, text, kind, tag, user_approved=True)`
> (bash: `jwu rule add "…" --kind constraint`).
>
> **Провайдер контура** (`provider` в ответе `jwu_workspace_current()`) говорит, откуда
> берутся задачи и PR: `jira` (Jira + Bitbucket + Jenkins), `github` (Issues + PR + Actions)
> или `local`. Инструменты одни и те же — меняется только формат ключа задачи: `PROJ-123`
> у Jira, `dndeck#42` у GitHub. Если `provider=local` — инструменты задач **не вызывай**:
> якорь работы там либо локальная фича (`jwu_features` / `jwu feature list`), либо ничего
> (`jwu job start --title "…"`). У GitHub нет таймтрекера — `jwu_worklog` там откажет. Если папка не привязана ни к одному воркспейсу — скажи
> об этом пользователю и предложи подключить проект.
> Если папка не привязана ни к одному воркспейсу (`source` не `cwd`) — **не логируй работу**:
> записи уедут в чужой контур. Сначала подключи проект — скилл **jwu-workspace-setup**
> (`jwu init`).

## Шаги

> **Сначала правила.** Ответа `jwu_workspace_current()` с `rules_md` нет в контексте этой
> сессии (новая сессия, `/clear`, компакт) — пройди **jwu-session-init**. Без правил
> воркспейса не начинай, не правь и не закрывай.

0. **Где и по каким правилам.** `jwu_workspace_current()` — папки, теги, правила (`rules_md`).
   Папку задачи определил — сразу `jwu_rules(tag="<тег>")` целиком. Запреты (⛔) действуют
   на весь цикл. `provider=local` — якорь работы локальная фича (`jwu_features()`), ключ
   задачи не выдумывай; нет фичи — работа без якоря.

1. **Что уже известно.** `jwu_context(KEY)` — закреплённый статус, решения, грабли, локальные
   ветки по задаче. Потом карточка: `jwu_task(KEY)`. **Статус Done/Closed** — правки не
   планируй, сообщи и спроси.

2. **Есть ли уже работа.** `jwu_jobs(task=KEY)`:
   - **активная по той же цели** — не плоди новую: это **jwu-continue-job**, скажи пользователю;
   - **закрытая по той же цели** (например, вернули с тестов) — предложи переоткрыть
     (**jwu-continue-job**) или начать новую, если цель другая;
   - иначе **при ручном старте вне доски** — `jwu_job_start(KEY, title="<цель цикла>")`. Запомни `job_id`.
   **Цель в заголовке** — по ней потом решают, когда закрывать: «Сделать задачу»,
   «Конфликт PR #1092 с develop», «Красная сборка #1887», «Правки по ревью PR #1027».

3. **Контекст — экономно.** Задачу, её PR, замечания и сборки собери **одним** `jwu_query`
   (методы — `jwu_query_help()`), вернув только нужное: описание и комменты задачи, по PR —
   состояние, ревьюеры, замечания (автор, файл, строка, текст), `builds(...).build_state` и
   `autotests.summary`. Так в контекст идёт выжимка, а не сырые ответы (в разы меньше).
   Комменты (сверяй время с последним пушем: коммент после пуша не
   учтён), PR и замечания (`jwu_pr`, привяжи `jwu_job_link`), сборки (красная — скилл
   **jwu-build-failure**), связанные задачи — только явно упомянутые. **Вложения** — качай
   без вопроса (картинки, логи, документы; видео — только если без него не понять):
   `jwu_attachments(KEY, download=True)` и сразу `jwu_job_resource(job_id, "path", <каталог>)` —
   уборка при закрытии его снесёт. Прочитал и выписал нужное в журнал — удали каталог сам.

4. **План по фазам.** До согласования только опиши применимые фазы. При исполнении записывай `kind=phase`:
   - **Фаза 0 — рабочее место.** Только если будут **правки кода** (чистый анализ — пропусти):
     1) `jwu_disk()` — `ok=False` → стоп: скажи, сколько свободно и что можно убрать
        (`leftovers` закрытых работ, docker «можно освободить»), жди решения. Если
        `hard_ok=True` — меню: «создать копию при малом месте» / «сначала убрать» /
        «подождать»; выбрал первое — `jwu_job_worktree(…, low_disk_ok=True)`.
        `hard_ok=False` — ниже жёсткого порога, обхода нет: только убрать;
     2) на **каждый** репозиторий, который будешь править, —
        `jwu_job_worktree(job_id, repo="<папка воркспейса>", branch="<ветка>")`. Ветка по
        задаче уже есть (`jwu_branches`) — передай её; нет — по `convention` воркспейса.
        Перед созданием проверь политику `worktree` для репозитория и ветки; соблюдай отдельное `ask`/`grant` и остановись при `deny`. Папка копий не задана — попроси `jwu workspace jobs-dir <путь>`.
     3) **дальше весь код — в копии** (`ref` из ответа), основную папку не трогай.
   - **Фаза 1 — конфликт и красный CI**, если применимо. Анализ не разрешает менять историю. Для синхронизации покажи точные ветку, цель и режим и используй защищённый `jwu_git_sync` только после согласия на эту операцию и всех допусков Git.
   - **Фаза 2 — анализ реализации и план правок** (предложения ревьюеров — попробовать).
   - **Фаза 3 — правки.** Нужен стенд — см. «Стенд работы» ниже.
   - **Фаза 4 — ревью до коммита**: **jwu-job-review** — сам, без вопроса (см. «Поток после
     «да» на план»). Блокеры — назад в фазу 3.
   - **Фаза 5 — финиш**: тексты голосом пользователя (коммит, PR и тексты аддонов) сразу, потом один вопрос меню — что публиковать, и закрытие.
   Порядок всегда: правки → ревью → коммит.

5. **Согласуй весь точный план один раз** по разделу «От анализа до первой правки» с вариантами «Делаем по плану / Поправить план / Только анализ». Если решение уже есть и условия не изменились, не спрашивай повторно. После согласия запиши и перечитай
   `jwu_job_add(job_id, "План согласован: <весь план с границами, шагами и расписанием проверок>", kind="decision")`: по этой
   записи поток продолжится сам и в новой сессии (**jwu-continue-job**).

6. **Дальше — «Поток после «да» на план»** ниже: исполняй согласованное, останавливаясь только для нового решения или при блокировке правилами.

## Поток после «да» на план

«Да» на план разрешает только включённые в него фазы 0–4. Между ними веди журнал, не спрашивая заново. Если меняются объём, порядок работ или условия проверки — согласуй обновлённый план целиком по разделу «От анализа до первой правки». Соблюдай ограничения по месту, правила воркспейса и лимит кругов ревью.

**Ревью (фаза 4)** — `jwu_job_reviewer(repo)` → `reviewer` и `max_iterations` (по умолчанию 3);
запусти **jwu-job-review** с этим ревьювером, не спрашивая. Блокеры или важные — правь (фаза
3), собирай правки пакетом и снова отдавай на ревью. Запуски — по разделу «Один финальный прогон, один стенд работы». Итераций уже `max_iterations`, а ревьювер снова
просит правок — **стоп**: вопрос меню «Ревью собирается на <N+1>-й круг: <что осталось
одной строкой>» с вариантами «ещё круг», «оставить как есть и идти к коммиту», «посмотрю
сам». Мелкое ([M…]) круг не запускает — запиши и иди дальше.

**Итог и тексты — все сразу.** Когда ревью чистое, скажи коротко: что сделал (3–5
пунктов простыми словами), тесты, сколько итераций ревью и что в них нашли. И сразу, без
вопроса, готовь тексты голосом пользователя через агента голоса (`voice_agent` из
`jwu_job_reviewer`): **коммит-месседж** (**jwu-commit-message**) и **заголовок и описание PR**
(по журналу работы; PR уже есть — обновлённое описание). Аддоны могут добавить свои тексты на
финише (например, инструкцию для QA): загляни в `jwu_addons()` — подсказка в `after` у ключа
`jwu-start-job` назовёт скилл; готовь и его текст. Подготовка ничего не публикует. Покажи всё
целиком одним сообщением.

**Одно меню на понятный результат.** Готовишь исправление к отправке — после проверок предложи довести его до PR за одно согласование, если ветка, текст и параметры PR уже показаны. Для нового PR: «Отправить ветку и открыть PR в <целевая ветка>»; если коммита ещё нет, явно включи его в выбор. Для существующего PR: «Закоммитить и отправить в PR #N» или, если коммит уже готов, «Отправить готовый коммит в PR #N». Описание PR, ревьюверов и другие применимые внешние эффекты покажи и согласуй в том же меню; не подразумевай их под «пушем». Если следующий шаг отличается только технически, не спрашивай заново после каждого шага. «Только локальный коммит» предлагай лишь по просьбе пользователя или при названном препятствии к отправке.

Если проверка подтверждённо падает и на чистой целевой ветке, напиши причину по-человечески («проверка миграций падает и без нашей правки»), а не просто «принять исключение». Когда правила допускают исключение, в том же меню предложи «Отправить исправление несмотря на этот сбой» с точным перечислением согласуемых операций (коммит, пуш, открыть PR — только применимые) или «Не отправлять». Исключение только на коммит пуш не покрывает. Запрет политики, обязательный `grant`, другой реальный блокер или изменившиеся условия публикации не обходи. Публикация не означает перевод Jira, ручной запуск CI или закрытие работы.

**Не запрашивай локальный коммит дважды.** Явное согласие на коммит этого набора изменений в этой ветке или на цепочку, которая включает коммит, достаточно: после обязательных проверок выполни коммит без отдельной карточки. Если точного согласия ещё нет, получи его один раз в меню на весь следующий результат. Согласие на правки или тесты не разрешает коммит; согласие только на коммит не разрешает пуш. Не останавливайся после коммита, если следующие шаги уже согласованы и не возник новый блокер.

До меню собери проверенное локальное превью: репозиторий, ветка, база, файлы и коммиты. `jwu_git_push(dry_run=True)` требует чистой копии и делает fetch: не применяй его к будущему коммиту и без разрешённого обновления ссылок. Сверь после коммита, что к отправке остался согласованный набор. Ревьюверов получи через `jwu_pr_people()` и проверку имён; переходы Jira — через `jwu_issue_transitions(KEY)` только если нужен переход. Если этих данных не хватает для точного превью, уточни только недостающее. Показанный и согласованный текст, адресат и объём не запрашивай повторно.

**По «да» — по порядку, без новых вопросов:**
1. коммит — `jwu_git_commit(message, path=<копия работы>, files=[…], user_approved=True)` с показанным сообщением и согласованными файлами; предварительно проверь, что в индексе нет чужих или несогласованных файлов (голый
   `git commit` режет хук политики);
2. пуш — **только** `jwu_git_push(job_id=…, user_approved=True)`, не `git push`:
   он пушит лишь ветку копии этой работы, без force, под политикой git. Ответ `blocked` —
   как в **jwu-session-init** («Git — только через jwu»): `grant` — передай пользователю
   `ask_user` и жди допуска через `jwu_git_grant_wait(grant_id)`, `deny` — стоп. Ошибка git — стоп, покажи причину (разошлась
   ветка — `jwu_git_sync`, незакоммиченное);
3. PR — `jwu_pr_create(target, title, description, source=<ветка из ответа пуша>,
   reviewers=[логины], from_job=job_id)` с показанными заголовком и описанием; `jwu_job_link`. Для существующего PR пуш обновляет ветку; метаданные меняй только если это явно согласовано, новый PR не открывай;
4. текст аддона для задачи — `jwu_comment(KEY, text, dry_run=False)` — уже показан и одобрен;
5. переход — `jwu_issue_transition(KEY, <выбранный>)`.
После каждого внешнего шага перечитай точный объект и проверь результат. Ошибка на шаге — стоп: скажи, что подтверждено и чего не сделано; не повторяй запись вслепую.

**Закрытие** — по `jwu-close-job`. Не считай его разрешённым публикацией, стандартная уборка входит в согласованное закрытие после проверок безопасности; архив чата — отдельное решение. Если закрытие уже согласовано, не спрашивай снова. Скажи
итог: ссылки на PR и коммент, что убрано, сколько места освободилось.

### Один финальный прогон, один стенд работы

1. Собери согласованную логику и изменения тестов целиком → отдай код на предварительное ревью → собери и исправь замечания пакетом → запусти согласованные тесты на итоговой версии. Не запускай широкие наборы, Playwright, сборку фронта или стенд после каждой мелкой правки и между проходами ревью. До финала используй чтение диффа и дешёвые проверки без сервисов. Ранний целевой тест — только если нужен для воспроизведения, проверки рискованного допущения или обязательного RED/GREEN. Назови, что именно такой прогон должен выяснить; не поднимай ради него весь стек, если хватит меньшего.
2. Если нужны сервисы, сначала проверь ресурсы этой работы. Подними один изолированный стенд с её метками и используй его повторно. Для нового прогона обнови только изменившийся код, компонент или бандл; сбрось только нужные тестовые данные, схему либо кеш своей работы и проверь, что загружена актуальная версия. Не переиспользуй грязное состояние как доказательство. Полное пересоздание — только если частичный сброс не даёт корректной изоляции, стенд повреждён или несовместим с новой конфигурацией. Назови причину. Не трогай чужие ресурсы; штатная уборка — при закрытии, не между тестами. Сразу записывай точные пути прогонов и кэшей, Compose-проект, тестовые тома и ID собственных образов, чтобы `jwu-close-job` мог убрать их без угадывания.
3. Повторяй только проверки, результат которых мог измениться после правки или чей предыдущий прогон не дошёл до тестов. Перед повтором назови причину и самый узкий достаточный набор. Привяжи результат к версии кода и условиям прогона. Если правила публикации требуют независимое ревью **после** тестов на том же снимке, соблюди этот порядок: раннее ревью экономит прогоны, но не заменяет обязательное финальное. Не урезай согласованную проверку и не обходи ограничения по диску, стенду или разрешениям.

## Тесты — всегда под наблюдением

Тесты любят зависать. Любой прогон дольше минуты (тесты, сборка, линт, миграции):
- запускай **в фоне** с общим таймаутом (`timeout <N>` или флаг раннера) и пиши вывод в файл;
- следи за ним (Monitor или проверка файла): нет нового вывода **5 минут** или вышел общий
  таймаут — это зависание: останови процесс (и контейнеры прогона), запиши `test-fail`
  «завис на <последний тест/шаг>», дальше — разбирай этот тест отдельно (`-x`, таймаут на
  тест, `-k <имя>`), а не перезапускай всё вслепую;
- в журнал — итог прогона (`test-pass` / `test-fail`) с командой и временем.

## Стенд работы

Нужно тестировать на стенде — работа поднимает **свой**, по правилу воркспейса
**🧪 `testenv`** (`jwu_rules()` → kind `testenv`, с тегом репозитория). Правило короткое и
ссылается на **инструкцию** — её открой целиком `jwu_guide(name)` и иди по шагам. Нет такого
правила — спроси у пользователя, как поднимать; предложи сохранить полную инструкцию
(`jwu_guide_save`) и короткое правило со ссылкой на неё — оба только после его «да».
Удалённые серверы (dev-стенды, тестовые хосты) — не тут: это SSH-стенды воркспейса
(`ssh_servers` в контексте, `jwu_ssh_servers()`), там же что на них можно; по умолчанию —
только чтение.

1. `jwu_disk()` перед подъёмом и перед сборкой образов — мало места → стоп и вопрос.
2. **Всё помечай работой:** имена — из ответа `jwu_job_start` (`docker.compose_project`,
   `docker.label`; ещё их отдают `jwu_job_resources` и `jwu_job_ports`), бери как есть — из номера
   работы их не собирай: compose — `docker compose -p <compose_project> …`; `docker run/build/
   volume create/network create` — с `--label <label>`. **Порты** — не из compose по
   умолчанию, а `jwu_job_ports(job_id, ["db", "redis", "web", …])`: jwu выдаст свободные и
   запишет за работой (иначе два стенда подерутся); подставь их переменными или override.
3. Что метку не несёт (образ, собранный чужим скриптом, каталог кеша, дамп БД) —
   `jwu_job_resource(job_id, kind, ref)`. Уборка при закрытии снесёт ровно это и помеченное.
4. Запиши в журнал, как поднят стенд и где он (`kind=note`): адрес, порты, логин тестовый.

## Журнал работы

Веди журнал по ходу, не в конце: закончил шаг — запись.

### Типы записей

| тип | бейдж | когда использовать |
|---|---|---|
| `phase` | — | веха процесса: Ф1 мердж → Ф2 анализ → Ф3 правки → Ф4 коммит. Статус: `--status pending\|done`. |
| `note` | · | нейтральный контекст/факт/прогресс (стенд, доступы, наблюдения). Дефолт. |
| `decision` | 🧭 РЕШЕНИЕ | **наш выбор подхода с обоснованием** («решили делать так, потому что…»): выбранный вариант, причина, отвергнутые альтернативы. |
| `remark` | ✎ | замечание **ревьюера** из PR (а не свой вывод!). |
| `constraint` | ⛔ ЗАПРЕТ | чего делать **НЕЛЬЗЯ**: «не трогать X», «гонять без Y», «не пушить в Z». |
| `warning` | ⚠ ВНИМАНИЕ | риск/потенциальная проблема — ещё не подтверждённый баг и не запрет. |
| `bug` | 🐛 БАГ | **найденный** баг: симптом, где, как воспроизвели. |
| `bug-resolved` | ✅ БАГ ИСПРАВЛЕН | баг **починили** — отдельной записью с сутью фикса. |
| `test-pass` | 🧪 ТЕСТЫ OK | прогон тестов **прошёл**: что гоняли + итог. |
| `test-fail` | 🧪 ТЕСТЫ УПАЛИ | прогон **упал**: команда, сколько/какие упали, суть ошибки. |
| `todo` | 📌 TODO | отложенная **актионабельная** работа в рамках цикла: что ещё доделать. |
| `summary` | 📝 ИТОГ | **одна строка простыми словами, что сделано** за законченный кусок работы: «перенёс правку в 10.8 и починил тесты», «разобрал падение сборки — виноват develop». Без хешей, путей, номеров сборок — это читает человек в сводке дня (Telegram «Что сделал сегодня») и трекинг времени. |
| `review` | 🔍 РЕВЬЮ | **шапка прогона ревью** PR субагентом-ревьювером: кто ревьюил, PR, итерация, вердикт, счётчики и **блок «Замечания:» со списком якорей** (`[B1]…/[I1]…/[M1]…` — блокер/важное/мелкое). Должна быть самодостаточной: записи в jwu неизменяемы, эту шапку нельзя будет потом отредактировать. Ставится скиллом **jwu-job-review** ровно один раз на прогон; конкретные находки — отдельными `remark`/`bug`/`warning`/`constraint`, в начале текста которых **обязательно** повторяется якорь шапки. |

Бейджевые типы подсвечиваются и в `jwu job show`, и в дашборде (вкладка «Работы»).

### Правило проекта — это НЕ запись работы

Записи работы живут ровно один цикл: `constraint` в работе — «в этой задаче не трогаем X».
Если пользователь произносит что-то про **проект вообще** — «никогда не пушь в develop»,
«стенд поднимается вот так», «фронт у нас на pnpm», «миграции руками не правим» — это
**правило воркспейса**, оно должно пережить и эту работу, и эту сессию.

⛔ **Правило пишется только с «да» пользователя.** Предложи сохранить, покажи title и
text, дождись «да» на эту формулировку — тогда `jwu_rule_add(title, text, kind, tag,
user_approved=True)`. Сам правила не придумывай: свои выводы, «прецеденты», находки этой
сессии, грабли конкретной задачи — это журнал работы или заметка на задаче (`jwu_note`),
а не правило воркспейса. Правка и удаление правил — так же, только с «да».

| Сказанное | kind |
|---|---|
| «никогда/нельзя/не смей …» | `constraint` |
| «делается так: …», «тесты гоняем …» | `howto` |
| «стенд поднимается …», «для тестов нужен docker-compose …», «порты …» | `testenv` |
| «у нас принято …», «ветка от …», «коммит в формате …» | `convention` |
| «осторожно, тут …», «на этом уже обжигались» | `gotcha` |
| «бэк лежит там-то», «за это отвечает …» | `info` |

`tag` ставь, если правило только про один репозиторий (тег его папки); иначе оставь пустым.
Сомневаешься, правило это или разовое ограничение — **спроси**: «записать как правило
воркспейса (навсегда) или как ограничение этой работы?»

### Дисциплина ведения

- **Фазы.** Фиксируй каждую веху `--kind phase`, закрывай `--status done`. Большую задачу веди по одной фазе (Ф1 мердж/конфликт — всегда первой).
- **Баги «нашли → исправили».** На находку — `bug`; на фикс — **парный** `bug-resolved` ОТДЕЛЬНОЙ записью. Исходную `bug`-запись НЕ правь и НЕ удаляй — нужна история «нашли → исправили».
- **Тесты.** На каждый значимый прогон — отдельная запись по результату (`test-pass` / `test-fail`). Если падение = дефект кода, заведи ещё и парный `bug`.
- **Запрет vs предупреждение.** Жёсткое «нельзя» → `constraint`; «осторожно, может сломаться / под вопросом» → `warning`.
- **Решение vs запрет.** `decision` — это НАШ выбор с обоснованием («решили чинить парсер, а не править конфиг на стенде, потому что…»); `constraint` — внешнее «нельзя». Если поймал себя на том, что пишешь «почему сделали так» в `note` — это `decision`.
- **`todo` — только in-cycle.** Отложенное в рамках текущего цикла. Работа закрывается `done`, поэтому «на следующий цикл / на потом вообще» пиши не сюда, а `jwu note <KEY>` на самой задаче — иначе потеряется. Закрытый пункт можно пометить `--status done`.
- **Не подменяй тип на `note`/`remark`,** если по сути это решение / баг / тест / запрет / предупреждение / todo. Тип несёт смысл — по нему потом фильтруют и читают лог.
- **Итог шага — `summary`.** Закончил кусок работы (фаза закрыта, закоммитил, ответил ревьюеру, разобрался с падением) — добавь `summary` одной строкой простыми словами. Минимум одна за сессию по каждой задаче, с которой работал: без неё сводка дня покажет только заголовок задачи.
- **`remark` только для ревью.** Свои находки/блокеры — это `bug`/`warning`, а не `remark`.

### Триггеры по фразе пользователя

- «запиши решение / зафиксируй, почему … / решили …» → `--kind decision`
- «добавь ограничение / констрейнт / зафиксируй запрет» → `--kind constraint`
- «добавь todo / надо ещё … / не забыть …» → `--kind todo`
- «нашли баг / запиши баг / есть баг …» → `--kind bug`
- «баг исправлен / починили баг / резолвнут» → `--kind bug-resolved`
- «добавь предупреждение / warning / осторожно с …» → `--kind warning`
- «запиши прогон тестов / тесты прошли / тесты зелёные» → `--kind test-pass`; «тесты упали / красные» → `--kind test-fail`
- «отметь фазу … (done)» → `--kind phase` (+ `--status done`)
- «запиши итог / что сделал» → `--kind summary`
- «запиши ревью / зафиксируй прогон ревью / результат ревьювера …» → `--kind review` (шапка прогона; конкретные находки — отдельными `remark`/`bug`/`warning`/`constraint`). Обычно ставится автоматически скиллом **jwu-job-review**, руками — только если запускал ревьювера руками.


## Подтверждение

- Пока просят анализ — **не редактируй код, не коммить, не пушь**.
- Правки — после «да» на план; коммит, пуш, PR, ревьюверы, коммент и статус задачи — после
  «да» на финальное меню с показанными текстами. Пуш — только `jwu_git_push(job_id=…)`.
- Вопросы — меню (`clarify` в Hermes Desktop, AskUserQuestion в клиентах с этим инструментом); если форма недоступна или не открылась — те же варианты текстом один раз.
- Ведение журнала — локальная операция воркера. Копия и стенд — только в пределах согласованного плана, после проверки места; при нехватке места — стоп и вопрос.
