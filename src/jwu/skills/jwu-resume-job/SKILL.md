# jwu: подхват работы (job) после потери контекста

## Overview

Контекст очистился / новая сессия / вернулись к задаче через время — а состояние работы ушло.
Прежде чем продолжать или писать код, **восстанови состояние из jwu** (локальная БД, без сети) и
кратко синхронизируйся с пользователем. Не начинай «с чистого листа» по задаче, у которой уже есть работа.

> **MCP-first.** Read-операции предпочитай MCP-инструментами jwu, bash `jwu …` — фолбэк:
> `jwu jobs …` → `jwu_jobs(task, pr, status)` · `jwu changes` → `jwu_changes()` ·
> `jwu pr <id> …` → `jwu_pr(pr_id, project, repo)` ·
> `jwu builds <id>` → `jwu_builds(pr_id, project, repo)` · `jwu build <id>` → `jwu_build(pr_id, project, repo, url)`.
> **Воркспейс = где лежит код.** jwu работает в контексте *воркспейса*: он определяется
> автоматически по текущей папке, проверить — `jwu_workspace_current()`
> (bash: `jwu workspace current --json`).
>
> **Код проекта лежит ИМЕННО в папках воркспейса.** Их список с тегами приходит сразу
> в `jwu_workspace_current()` и в ответе `jwu_job_start()` (поля `paths` и `known_tags`),
> отдельный вызов нужен только чтобы отфильтровать по тегу — `jwu_workspace_paths(tag=…)`
> (bash: `jwu workspace paths`). Ищи и правь только в этих папках;
> остальное на диске к задаче отношения не имеет. У папок есть **теги** («legacy-бэкенд»,
> «новая-версия», «фронт») — по ним понятно, что где: `jwu_workspace_paths(tag="legacy-бэкенд")`.
> Не угадывай по имени каталога — спроси теги. Пользователь просит пометить папку —
> `jwu_workspace_tag(path, add=[...])` (bash: `jwu workspace tag <DIR> --add <тег>`).
>
> **У воркспейса есть ПРАВИЛА** — то, что знает о проекте человек, но не знает код:
> запреты (⛔ `constraint`), инструкции (`howto` — как поднять стенд, прогнать тесты),
> соглашения (`convention` — ветки, формат коммита), грабли (`gotcha`), справка (`info`).
> Правила приходят готовым текстом в поле `rules_md` — оно есть и в `jwu_workspace_current()`,
> и в ответе `jwu_job_start()`. Общие правила там целиком, у правил конкретных
> репозиториев — только заголовки. Как только понял, в какой папке правишь, возьми её
> правила целиком: `jwu_rules(tag="legacy-бэкенд")` (bash: `jwu rules --tag legacy-бэкенд`).
> **Записи `⛔ ЗАПРЕТ` обязательны к исполнению** и важнее твоего удобства: если правило
> мешает выполнить просьбу — не обходи его молча, скажи об этом пользователю.
> Пользователь формулирует правило уровня проекта («не пушь в develop», «стенд поднимается
> так-то») — предложи сохранить: `jwu_rule_add(title, text, kind, tag)`
> (bash: `jwu rule add "…" --kind constraint`).
>
> Если `jira_enabled=false` — Jira-команды и инструменты **не вызывай**: якорь работы там
> либо локальная фича (`jwu_features` / `jwu feature list`), либо ничего
> (`jwu job start --title "…"`). Если папка не привязана ни к одному воркспейсу — скажи
> об этом пользователю и предложи подключить проект.
> Если папка не привязана ни к одному воркспейсу (`source` не `cwd`) — **не логируй работу**:
> записи уедут в чужой контур. Сначала подключи проект — скилл **jwu-workspace-setup**
> (`jwu init`).


## Когда

- После `/clear`, компакта контекста или в начале новой сессии по уже идущей задаче.
- Пользователь говорит «продолжим / на чём остановились / что по <KEY>».
- Ты собираешься залогировать прогресс (jwu-track-job), но лога работы в контексте нет.
- **Не для старта новой задачи** — это jwu-start-job. **Не для нового цикла правок** — там новая работа.

## Шаги

1. **Найти работу.**
   - Сначала `jwu_workspace_current()` — работы скоупятся по воркспейсу, и в чужом их не видно.
   - Якорь работы в выводе — поле `anchor`: ключ задачи Jira, ключ локальной фичи либо `#<id>`
     (работа без якоря). По фиче ищи `jwu jobs --feature <KEY> --json`.
   - Знаешь ключ задачи: `jwu jobs --task <KEY> --json` (бери активную).
   - Не знаешь: `jwu jobs --status active --json`. Несколько активных → покажи список
     (`id / task_key / updated_at`) и **спроси, какую**; одна — бери её.

2. **Загрузить лог:** `jwu job show <JOB_ID>` (или `--json` для разбора по типам).

3. **Реконструировать «где мы»** по типам записей:

   | Что ищешь | Тип записи | Зачем |
   |---|---|---|
   | текущая фаза | последняя `phase` (+ `--status`) | на каком этапе процесса |
   | что осталось | `todo` без `status=done` | незакрытые хвосты |
   | незакрытые баги | `bug` без парного `bug-resolved` | что ещё чинить |
   | действующие запреты | `constraint` (⛔) | чего делать НЕЛЬЗЯ — НЕ нарушай |
   | принятые решения | `decision` (🧭) | не пересматривай без причины |
   | состояние тестов | последний `test-pass`/`test-fail` | зелено/красно в логе работы |
   | состояние CI-сборки PR | `jwu builds <PR> --json` / секция «Сборки» в `jwu pr` | зелёный/красный билд сейчас |

   **Сверь актуальный статус CI с логом работы:** если сборка PR красная (FAILED), а в логе
   нет свежей `test-fail` с разбором — разбери причину скиллом **build-failure** (субагент
   `jenkins-build-analyst` → `jwu build <PR> --json`) и зафиксируй вывод через jwu-track-job.
   Часто красный билд — регресс из целевой ветки, лечится её влитием. (Команды `builds`/`build`
   не зависят от Jira.)

4. **Синхронизируйся с пользователем** — короткая сводка: задача, текущая фаза, что сделано,
   что осталось, действующие запреты, **статус CI-сборки**. Подтверди следующий шаг, прежде чем писать код.

5. **Дальше веди работу** через jwu-track-job (фиксируй фазы/баги/тесты/решения).

## Частые ошибки

- Начать заново и завести **новую** работу, хотя по задаче уже есть активная → проверь `jwu jobs --task <KEY>` ПЕРЕД стартом.
- Пропустить `constraint`-записи и нарушить запрет (напр. «код правим только локально»).
- Продолжать по памяти, не перечитав `jwu job show` → расхождение с реальным состоянием.

## Подтверждение правок

Подхват и чтение — без подтверждения. Но **правки КОДА, коммиты и пуш — только после явного
подтверждения пользователя** (правило проекта). Старт/анализ — в jwu-start-job, ведение — в jwu-track-job.
