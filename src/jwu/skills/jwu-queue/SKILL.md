# jwu: очередь задач сессии

## Overview

Во время разработки в чат прилетают мелкие замечания: «ещё поправь импорт», «добавь тест
на пустой список», «переименуй поле». Каждое такое сообщение выбивает сессию из текущего
шага, а список «что ещё просили» живёт только в контексте и теряется при компакте.

Очередь jwu решает это: просьба **кладётся в конец очереди в БД** и сессия **возвращается
к текущему делу**. Пункты выполняются по одному в основном потоке либо отдаются субагентам,
пока есть свободные слоты. Очередь переживает `/clear`, компакт и смену сессии.

> **MCP-first.** `jwu_queue()` · `jwu_queue_add(text, mode, job_id)` ·
> `jwu_queue_take(mode, worker)` · `jwu_queue_finish(item_id, status, result)` ·
> `jwu_queue_edit(item_id, text, mode, job_id, position)` · `jwu_queue_clear(include_queued)` ·
> `jwu_queue_slots(slots)`. Bash-фолбэк: `jwu queue [list|add|take|done|fail|cancel|release|edit|move|clear|slots]`
> (у всех есть `--json`). Источник истины по режимам и статусам — `QUEUE_MODES` /
> `QUEUE_STATUSES` в `src/jwu/core/models.py` репозитория jwu.
>
> Всё в контексте **воркспейса** текущей папки (`jwu_workspace_current()`); `source` не `cwd` —
> очередь уедет в чужой контур, сначала **jwu-workspace-setup**.

## Когда

- Пользователь включает режим: «работаем через очередь», «включи очередь», `/jwu-queue`.
  С этого момента и до конца сессии действует раздел «Главное правило».
- Пользователь явно просит: «поставь в очередь …», «что в очереди», «следующий», «сними #3».
- Сессия возобновилась (после `/clear`, компакта, в новой сессии), а в очереди есть
  пункты `queued`/`running` — очередь показывается в сводке **jwu-session-init**, режим
  считается включённым, если пользователь его не выключил.
- **Не нужен**, если пользователь ведёт одну задачу и ничего не ставит в очередь.

## Главное правило: новая просьба → в очередь → обратно к делу

Пока режим включён, **любое новое задание из чата**, пришедшее во время выполнения
текущего пункта или шага работы:

1. **Сразу** `jwu_queue_add(text, mode)` — в конец очереди. **`mode="main"`, если
   пользователь явно не сказал «параллельно» / «отдай агенту»** — см. «Режим пункта». Это одно короткое действие,
   оно делается **до** возврата к текущей задаче. Если прерваться сейчас нельзя (идёт
   правка файла, коммит, прогон тестов — любое атомарное действие, которое нельзя бросить
   на середине), — доделать **этот атомарный шаг** и положить в очередь **первым же** следующим
   действием. Не откладывать «до конца задачи».
2. Текст пункта — **суть просьбы своими словами пользователя**, одной внятной формулировкой,
   самодостаточной без контекста чата (другой агент или другая сессия должны понять, что
   делать). Несколько просьб в одном сообщении — несколько пунктов, в порядке упоминания.
3. Ответить пользователю одной строкой: `в очередь: #12 → <текст>` (`→` main, `⇉` parallel)
   — и **продолжить текущее дело** с того места, где прервались. Никаких «сейчас сделаю».
4. Если просьба — не задание, а вопрос, уточнение или правка к ТЕКУЩЕМУ пункту, в очередь
   она не идёт: ответить / учесть сразу.

Исключение: пользователь прямо говорит «это срочно, брось текущее» — тогда пункт
ставится первым (`position=1`) и текущий пункт возвращается в очередь
(`jwu_queue_finish(id, status="queued")`) после ближайшего атомарного шага.

## Режим пункта: `main` или `parallel`

> ⛔ **`parallel` ставится ТОЛЬКО по явным словам пользователя в ЭТОЙ просьбе.** Нет слов
> «параллельно» / «отдай агенту» / «пусть агент» — `mode="main"`, даже если пункт выглядит
> независимым и «так было бы быстрее». Поставил `parallel` сам — это ошибка, не оптимизация.


- `main` — **ДЕФОЛТ**: просьба без слов про параллельность всегда идёт сюда. Выполняет
  **сам основной поток**, подряд, по одному, в порядке очереди. Для всего, что трогает те же файлы, что и текущая работа, требует решений
  пользователя или контекста сессии.
- `parallel` — отдаётся **субагенту** (Agent), как только есть свободный слот. Для
  независимых, хорошо отделимых пунктов: отдельный файл/модуль, документация, разбор,
  поиск по коду, прогон чего-то долгого.
- Режим берётся из слов пользователя: «параллельно», «отдай агенту», «пусть агент
  сделает» → `parallel`; «потом», «следом», «после этого» → `main`. Не сказано — `main`.
  Сомневаешься, можно ли параллелить, — `main`: конфликт правок дороже ожидания.
- Лимит слотов — `jwu_queue_slots()` (настройка воркспейса `queue.slots`, по умолчанию 3).
  Пользователь просит «3 параллельно» / «не больше одного агента» → `jwu_queue_slots(N)`.

## Цикл основного потока

Когда текущий пункт (или текущая задача) закончен — закрыть его и взять следующий:

1. `jwu_queue_finish(id, "done", result="…")` — итог одной строкой. Не вышло —
   `"failed"` с причиной. Если у пункта есть `job_id` — продублировать итог записью в
   работу (`jwu_job_add`, журнал работы): очередь — не журнал, закрытые пункты чистятся.
2. `jwu_queue_take(mode="main")`. В основном потоке выполняется **один** пункт за раз:
   `busy=True` означает, что предыдущий не закрыт — закрой (`done`/`failed`) или верни
   (`status="queued"`), не бери второй.
3. Перед выполнением пункта — проверить, не ждёт ли он подтверждения пользователя
   (правки кода по правилу воркспейса — только после «да»). Если пункт требует
   решения, спросить и, не дожидаясь, взять следующий, который не требует.
4. Пункт выполнен — п.1. Очередь пуста (`item=null, busy=false`) — сказать «очередь
   пуста» и остановиться.

Пункт очереди — это **шаг**, а не новая работа: он выполняется внутри текущей работы
(job) и логируется в неё. Пункт, который оказался отдельной задачей, — завести работой
через **jwu-start-job** и закрыть пункт с `result="выделен в работу #N"`.

## Параллельные пункты и слоты

Проверять после каждого `jwu_queue_add` с `mode="parallel"` и после каждого закрытия
пункта: `jwu_queue_take(mode="parallel", worker="<имя-агента>")`, пока он отдаёт пункты.
`busy=True` — слоты заняты, ждать не надо: следующий `take` — когда освободится.

На каждый взятый пункт — **один субагент** (Agent, фоновый) с самодостаточным промптом:
текст пункта, воркспейс и папка, правила контура (`rules_md`, ⛔ запреты обязательны),
что НЕ трогать (файлы текущей работы основного потока), и что вернуть: краткий итог +
список изменённых файлов. Субагент **не коммитит и не пушит** и не трогает очередь —
закрывает пункт основной поток по его отчёту: `jwu_queue_finish(id, "done"|"failed",
result=…)` + запись в работу. Субагент пропал (нет отчёта) — `status="queued"` (release),
пункт возьмёт следующий.

Запуск субагента — это прерываемый шаг: новая просьба из чата всё так же сначала идёт в
очередь.

## Показ очереди

«Что в очереди» / `/jwu-queue` без аргументов → `jwu_queue()` и список построчно:

```
Очередь · ждёт 3 · выполняется 1 · слоты 1/3 · основной поток: #12
  #12 → выполняется   починить тест на пустой список
  #13 → в очереди     переименовать поле status → state
  #14 ⇉ выполняется agent-docs   обновить docs/commands.md
  #15 → в очереди     прогнать линтер
```

Закрытые по умолчанию не показываются (`all_items=True` — вместе с ними).
«Очисти очередь» → `jwu_queue_clear()` убирает только закрытые; снести ожидающие —
только по явному «да, и ожидающие тоже» (`include_queued=True`).

## При возобновлении сессии

Контекст потерян, а `jwu_queue()` показывает `running`-пункты: это хвосты прошлой
сессии. Основной `running` — проверить по работе и git, что успели; если доделано —
закрыть `done`, иначе вернуть `queued` и продолжить. Параллельные `running` без живого
субагента — вернуть `queued`.

## Частые ошибки

- Начать делать новую просьбу сразу, «раз уж маленькая», — ровно то, от чего очередь
  защищает. В очередь, потом обратно.
- Дописать просьбу «в голове» и не вызвать `jwu_queue_add` — при компакте она исчезнет.
- Взять второй `main`-пункт, не закрыв первый.
- Параллелить пункт, который правит те же файлы, что и основной поток.
- Ставить `parallel`, потому что «так быстрее»: режим выбирает пользователь, не агент.
  Не сказал «параллельно» — `main`.
- Считать очередь журналом: итоги — в работу (`jwu_job_add`), очередь чистится.
- Логировать в очередь работу чужого контура (`source` не `cwd`).
