# jwu: очередь ревью

## Overview

Пакетное ревью чужих PR в два захода:

- **Фаза A — разбор, наружу НИЧЕГО.** Отбор PR → ревьюеры-субагенты пулом → фильтр
  замечаний → черновики комментов голосом пользователя → сводный md файлом пользователю.
- **Фаза B — отправка по одному PR.** PR целиком (о чём задача, что изменилось, по каждому
  комменту — проблема и текст, статус) → один вопрос → отправить комменты и статус →
  status-заметка → следующий PR.

Один PR — скилл **jwu-review-pr**; свой дифф до коммита — **jwu-job-review**.

> **MCP-first.** `jwu_review_queue(include_approved, prs, repos)` — очередь и пути;
> `jwu_pr`, `jwu_task`, `jwu_pr_diff(pr_id, path, numbered=True)` — контекст (их зовут
> сами субагенты); запись — `jwu_pr_comment`, `jwu_pr_review`, `jwu_note`.
> Bash-фолбэк: `jwu review queue --json`, `jwu pr <id> --diff --numbered`.

## Аргументы

- глубина: `light` (по умолчанию — только блокеры и критичное) | `full`;
- параллельность: `N` (по умолчанию 3) — сколько ревьюеров одновременно;
- фильтр: номера PR и/или репозитории;
- `--include-approved` — ревьюить и PR, где мой статус уже APPROVED.

## Фаза A — разбор (ничего не отправляется)

1. **Очередь.** `jwu_review_queue(include_approved, prs, repos)`. Покажи одной таблицей:
   что ревьюим (PR, репо, задача, ревьювер) и что пропущено с причиной. Каталог сводки —
   `dir` (данные jwu, вне репозиториев проекта); там же будут разделы по PR.
2. **Ревьюеры пулом по N.** Для каждого PR — `Agent` с `subagent_type = reviewer_agent`
   (ревьювер репозитория из настроек, иначе `reviewer-jwu-sample`; задать —
   `jwu review agents --repo R --reviewer X`). Одновременно не больше N; как только один
   закончил — запускай следующий. Промпт каждому — самодостаточный:
   - PR `project/repo#id`, source → target, ключ задачи, режим `light|full`;
   - «это ЧУЖОЙ PR, ревью для комментариев автору»;
   - «сам возьми `jwu_pr`, `jwu_task(key)`, `jwu_pr_diff(pr_id, path, numbered=True)` —
     дифф не приходит через оркестратора»;
   - «код сверяй с `origin/<target>`: `git fetch origin <target>` и
     `git show origin/<target>:<path>` в клоне из папок воркспейса (`jwu_workspace_paths`).
     Ветки НЕ переключай, рабочее дерево не трогай, ничего не коммить. Клона нет — пиши,
     что вывод только по диффу»;
   - «запиши свой раздел в `review_file` и верни его».
3. **Фильтр — сразу за ревьювером** этого PR (не жди остальных): `Agent` с
   `subagent_type = filter_agent` (по умолчанию `review-filter-sample`). Передай PR,
   target, задачу, путь к `review_file`, режим и путь `facts_file`. Выход — факты для
   комментов (куда, происхождение new/made-reachable, сценарий, следствие, просьба),
   предлагаемый статус и отброшенное с причинами. `pre-existing` автору не пишется.
4. **Черновики голосом.** По каждому PR с оставшимися фактами — агент голоса
   (`jwu_voice_profile()` → `agent`): `channel = pr_comment` (ответ в тред автора —
   `pr_reply`), `audience = colleague`, `facts` — пункты из `facts_file`, `context` — кусок
   numbered-диффа или цитата треда, `limits` — «3–5 предложений на коммент». Одним вызовом
   на PR, тексты пронумерованы так же, как факты.
5. **Сводка** → `summary` (`<dir>/summary.md`):
   - сверху таблица `PR | репо | задача | вердикт | главное`, номер PR — ссылкой на него;
   - раздел на каждый PR: предлагаемый статус, блокеры / критичное / важное с `file:line`,
     под каждым — черновик коммента; «Для сводки» (pre-existing) отдельной строкой;
   - в конце — пропущенные PR и причины.
6. **Отдай файл — всегда `SendUserFile`.** `summary.md` отправляй пользователю файлом в
   любой сессии, не только удалённой: путь в тексте он не видит и открыть не может. Нет
   `SendUserFile` — скажи об этом прямо и дай путь. Коротко в чат: сколько PR, где блокеры.
7. `jwu_note("PROJ/repo#ID", "ревью: черновики в <summary>", kind="context")` по каждому
   PR — чтобы следующая сессия нашла сводку.

## Фаза B — отправка, по одному PR

Строго **один PR за сообщение**, по порядку сводки. Сначала подготовка, потом показ.

**Подготовка (молча):**

- `jwu_pr` — свежее состояние: коммиты, комменты и треды, сборка, ревьюеры. Сравни с моментом
  прошлого ревью пользователя (его последний коммент или статус в этом PR): что появилось
  после — новые коммиты, ответы автора в тредах, комменты других ревьюеров.
- Черновики, которые пользователь уже написал руками, — выкинь (совпадение по смыслу).
- Автор задал пользователю вопрос в треде — **первым идёт ответ в его тред** (`reply_to`).
- Задача — `jwu_task(KEY)`: что за баг или фича.

**Показ — ровно в таком порядке:**

1. **Шапка:** `N/M — repo#PR · КЛЮЧ-ЗАДАЧИ · автор` и под ней ссылка на PR (`url` из
   `jwu_review_queue` / `jwu_pr`) — кликабельно, чтобы открыть PR в один тап.
2. **О чём задача** — 2–3 предложения простым языком: какой баг или фича (из карточки
   Jira) и что автор в PR сделал. Без деталей реализации.
3. **Состояние PR** — одна-две строки: что изменилось с прошлого ревью пользователя
   (новые коммиты, ответы автора в тредах, новые комменты других ревьюеров), статус
   сборки, какие прежние черновики выкинуты, потому что уже написаны руками.
4. **По каждому комменту — отдельный блок:**
   - заголовок: номер, куда уйдёт (новый inline `path:line` / ответ в тред #id / общий
     коммент), важность (блокер / критично / важно);
   - **Проблема** — для ПОЛЬЗОВАТЕЛЯ, не для автора PR: почему этот коммент вообще есть —
     что было до PR, что PR изменил, какой реальный сценарий ломается и чем это грозит
     (500, регрессия, нарушение правила проекта, повтор незакрытого треда, на который
     автор ответил формально). 3–5 предложений простым языком — чтобы пользователь решил,
     отправлять ли, не открывая код. Берётся из фактов фильтра (`facts_file`), не из
     текста коммента;
   - сам текст коммента цитатой (`> …`) — ровно то, что уйдёт в PR.
5. **Статус** — предлагаемый и текущий (`APPROVED` / `NEEDS_WORK` / не ставить).
6. **Один вопрос в конце:** отправить комменты и статус / править / пропустить.

**Ответ пользователя:**

- **«Отправить»** — по порядку: ответы в треды, inline-комменты (`jwu_pr_comment(pr_id,
  text, path, line)`; тип строки jwu берёт из диффа; `anchored: false` — сразу скажи и
  предложи удалить через `jwu_pr_comment_delete` и отправить заново), общий коммент; затем
  статус `jwu_pr_review(pr_id, status, text)` — он был в вопросе, отдельного «да» не нужно.
  Потом `jwu_note("PROJ/repo#ID", "ревью сделано, ждём …", kind="status", pin=True)`.
- **«Править»** — текст правит агент голоса по фактам и правке; покажи PR заново в том же
  формате и снова один вопрос. После — одной строкой «записать правку в профиль голоса?».
- **«Пропустить» / «дальше»** — в этот PR ничего не уходит; следующий PR.
- Можно отправить только часть («отправь 1 и 3, статус не ставь») — делай ровно это.

## Текст от имени пользователя (голос)

Итоговую формулировку любого текста, который уйдёт наружу от имени пользователя или
отдаётся ему «для копирования», пишет **агент голоса**, а не этот скилл:

1. Собери **факты** — что сказать (сценарий → следствие → просьба; или что сделано),
   на что отвечаем (цитата), нужные имена из кода. Формулировать не надо.
2. `jwu_voice_profile()` → поле `agent` (дефолт `voice-writer-sample`, проектный задаётся
   `jwu voice agent <имя>`). Запусти его через Agent (`subagent_type` = `agent`) и передай
   `channel`, `audience`, `facts`, `context`, `limits`. Агент только пишет, наружу ничего не шлёт.
3. Покажи пользователю текст целиком (и «что я предположил», если не пусто) → правки →
   явное «да» → отправка этим скиллом.
4. «Не похоже на меня» — запусти агента ещё раз с `recheck` (прежний текст в `previous`,
   слова пользователя в `remark`): он сверит черновик с реальными текстами из корпуса и
   перепишет. Предложит правило для профиля — покажи его пользователю.
5. Пользователь поправил или отклонил текст — спроси одной строкой «Записать правку в
   профиль голоса?»; «да» → `jwu_voice_feedback(channel, verdict, before, after, reason)`.

Каналы: `pr_comment`, `pr_reply`, `pr_review_body`; аудитория `colleague`.

## Чего делать НЕ надо

- Отправлять что-либо в фазе A, или в фазе B без ответа «отправить» по конкретному PR.
- Показывать несколько PR в одном сообщении или переписывать «Проблему» текстом коммента.
- Писать автору `pre-existing` и натянутое: мелочи, стиль, «проверь якорь», «уточни
  формулировку», вне скоупа задачи.
- Держать дифф в контексте оркестратора — его берут субагенты сами.
- Класть сводку в репозиторий проекта.
- Запускать больше N ревьюеров одновременно.
- Апрувить «раз замечаний нет» без явного «да» пользователя на статус.
