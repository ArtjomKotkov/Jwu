# jwu: итоги дня по работам (для трекинга времени)

> **Воркспейс = где лежит код.** jwu работает в контексте *воркспейса*: он определяется
> автоматически по текущей папке, проверить — `jwu_workspace_current()`
> (bash: `jwu workspace current --json`).
>
> **Код проекта лежит ИМЕННО в папках воркспейса.** Их список с тегами приходит сразу
> в `jwu_workspace_current()` и в ответе `jwu_job_start()` (поля `paths` и `known_tags`),
> отдельный вызов нужен только чтобы отфильтровать по тегу — `jwu_workspace_paths(tag=…)`
> (bash: `jwu workspace paths`). Ищи и правь только в этих папках;
> остальное на диске к задаче отношения не имеет. У папок есть **теги** («legacy-бэкенд»,
> «новая-версия», «фронт») — по ним понятно, что где: `jwu_workspace_paths(tag="legacy-бэкенд")`.
> Не угадывай по имени каталога — спроси теги. Пользователь просит пометить папку —
> `jwu_workspace_tag(path, add=[...])` (bash: `jwu workspace tag <DIR> --add <тег>`).
>
> **У воркспейса есть ПРАВИЛА** — то, что знает о проекте человек, но не знает код:
> запреты (⛔ `constraint`), инструкции (`howto` — как поднять стенд, прогнать тесты),
> соглашения (`convention` — ветки, формат коммита), грабли (`gotcha`), справка (`info`).
> Правила приходят готовым текстом в поле `rules_md` — оно есть и в `jwu_workspace_current()`,
> и в ответе `jwu_job_start()`. Общие правила там целиком, у правил конкретных
> репозиториев — только заголовки. Как только понял, в какой папке правишь, возьми её
> правила целиком: `jwu_rules(tag="legacy-бэкенд")` (bash: `jwu rules --tag legacy-бэкенд`).
> **Записи `⛔ ЗАПРЕТ` обязательны к исполнению** и важнее твоего удобства: если правило
> мешает выполнить просьбу — не обходи его молча, скажи об этом пользователю.
> Пользователь формулирует правило уровня проекта («не пушь в develop», «стенд поднимается
> так-то») — предложи сохранить: `jwu_rule_add(title, text, kind, tag)`
> (bash: `jwu rule add "…" --kind constraint`).
>
> **Провайдер контура** (`provider` в ответе `jwu_workspace_current()`) говорит, откуда
> берутся задачи и PR: `jira` (Jira + Bitbucket + Jenkins), `github` (Issues + PR + Actions)
> или `local`. Инструменты одни и те же — меняется только формат ключа задачи: `PROJ-123`
> у Jira, `dndeck#42` у GitHub. Если `provider=local` — инструменты задач **не вызывай**:
> якорь работы там либо локальная фича (`jwu_features` / `jwu feature list`), либо ничего
> (`jwu job start --title "…"`). У GitHub нет таймтрекера — `jwu_worklog` там откажет. Если папка не привязана ни к одному воркспейсу — скажи
> об этом пользователю и предложи подключить проект.
> Если папка не привязана ни к одному воркспейсу (`source` не `cwd`) — **не логируй работу**:
> записи уедут в чужой контур. Сначала подключи проект — скилл **jwu-workspace-setup**
> (`jwu init`).

## Overview

Пройтись по всем jwu-работам (jobs), затронутым **сегодня**, и для каждой задачи дать
**очень короткую** выжимку «что сделано» — чтобы пользователь разнёс время по задачам.
Это ретроспектива (что уже сделано), а не план на будущее.

Источник — локальная БД jwu, без сети: одна команда отдаёт работы со всеми записями.
Работы берутся **из текущего воркспейса**. В воркспейсе без Jira итог тот же, только вместо
ключей задач в `anchor` будут ключи локальных фич (или `#<id>` у работ без якоря), а трекать
время потом будет некуда — см. jwu-track-time.

## Шаги

1. Собери работы за сегодня (записи с сегодняшней датой). Дату можно передать аргументом
   (`/jwu-post-analyze-day 2026-05-21`), иначе берётся сегодняшняя:

   ```bash
   today=${1:-$(date +%F)}
   jwu jobs --json | jq --arg d "$today" '
     map(select(any(.records[]?; .ts[0:10] == $d) or (.updated_at[0:10] == $d)))
     | map({task_key, status,
            prs: [.prs[]? | "\(.repo)#\(.pr_id)"],
            done: [.records[]? | select(.ts[0:10] == $d) | "[\(.kind)] \(.text)"]})'
   ```

   В `done` лежат только сегодняшние записи: `phase` — этапы, `remark` — замечания ревью,
   `note` — заметки/результаты. Если массив пуст — за день по работам ничего нет, так и скажи.

2. Сожми каждую задачу в **5-10 слов**. Если сделано много — несколько коротких фраз
   (по 5-8 слов), а не пересказ записей. Не копируй текст записей дословно.
   Только **суть по задаче**: что конкретно реализовано/починено/решено.

   **Не включай рутинные действия вообще** — это шум, а не результат по задаче:
   - прогон ревьювера / «провёл ревью» — это лишь нейропрогон, не работа по задаче;
   - коммиты и пуши — «закоммитил», «запушил», «создал/обновил PR» не пиши;
   - git-механика — переключение веток, `git add`, ребейзы как самоцель.

   **Обобщай оставшуюся рутину без деталей**, если она реально часть работы:
   - тесты — упоминай только большие/отдельные тесты (писал/чинил нагрузочные,
     интеграционные, объёмный набор кейсов); штатный прогон после правок — не пиши;
   - конфликты/мердж — стоит писать: «разрешил конфликт» (без числа коммитов/конфликтов,
     списка файлов, рецепта).

   Если по задаче за день — лишь рутина (ревью-прогон, коммит, пуш) и ничего
   содержательного, так и напиши коротко (например «правок по сути нет»), а не
   выдумывай результат.

3. Выведи список: **одна задача — одна строка, только номер задачи**. Без PR,
   без `repo#id`, без ссылок и скобок с метаданными:

   ```
   PROJ-12593: перенёс фикс stat v2 в release-10.8
   PROJ-399: разрешил конфликт, откатил low-memory конфиг, ответил ревьюерам
   ```

   Несколько работ по одной задаче — объедини в одну строку.

## Заметки

- Read-only: только чтение БД jwu, ничего не пишем и не синкаем.
- `ts`/`updated_at` — UTC ISO; фильтр по `[0:10]` сравнивает дату. Работал за полночь —
  передай нужную дату аргументом.
- Это итог дня. «Что делать дальше / на ревью / поправить» — это `/jwu-analyze-day`.
