# jwu: перевести задачу по процессу

> **Воркспейс = где лежит код.** Контур определяется по текущей папке, проверить —
> `jwu_workspace_current()`. Правила контура приходят там же в `rules_md`;
> **записи `⛔ ЗАПРЕТ` обязательны к исполнению** — если в проекте принято двигать
> задачи только вручную или только после ревью, это главнее скилла.
>
> **Провайдер**: переходы есть у `jira`. У GitHub Issues только open/closed —
> инструмент честно откажет.

## Главное правило

**Статус меняется только после явного «да».** Его видит вся команда, а обратный переход
из нового статуса может быть недоступен — набор переходов зависит от схемы проекта.

## Инструменты

- `jwu_issue_transitions(key)` — читающий, зови свободно (bash: `jwu issue transitions KEY`).
- `jwu_issue_transition(key, target)` — ВНЕШНЯЯ запись (bash: `jwu issue transition KEY "…"`,
  требует `--yes`; без него `--json` вернёт `confirm_required`).

## Алгоритм

1. **Спроси инстанс, а не память:** `jwu_issue_transitions(key)`. Список зависит от
   ТЕКУЩЕГО статуса — «In Progress» из одного статуса есть, из другого нет.
2. **Покажи пользователю** доступные переходы с тем, во что они переводят (`name → to`).
   Если он назвал статус, которого в списке нет, — скажи об этом и покажи, что есть;
   не подбирай похожий сам.
3. **Выполни** выбранный после «да»: `jwu_issue_transition(key, target)`. Имя перехода
   можно писать в любом регистре, можно передать id.
4. Скажи, в какой статус задача перешла (`status` в ответе), и запиши в работу, если
   она есть: `jwu_job_add(job_id, "Статус <KEY> → <status>", kind="phase")`.

## Чего делать НЕ надо

- Двигать задачу «по дороге», выполняя другую просьбу.
- Закрывать задачу за пользователя, потому что «работа же сделана».
- Пытаться обойти отсутствующий переход правкой полей.

## Связанные скиллы

- **jwu-task-create** — завести задачу.
- **jwu-task-comment** — комментарий (в SDESK его читает клиент).
- **jwu-track-time** — залогировать время по задаче.
