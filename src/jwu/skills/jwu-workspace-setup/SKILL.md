# jwu: подключение проекта (init)

## Overview

**Воркспейс** — контур работы в jwu: набор папок + **один провайдер** задач и PR + свои
локальные данные (работы, фичи, заметки, анализы, снапшоты). Контуры не пересекаются:
личный проект не видит рабочих задач и наоборот.

Провайдер выбирается при создании и меняется в любой момент (`jwu workspace provider`):

| provider | задачи | PR | сборки |
|---|---|---|---|
| `local` | локальные фичи jwu | — | — |
| `jira` | Jira (+SDESK) | Bitbucket | Jenkins |
| `github` | GitHub Issues | GitHub PR | GitHub Actions |

Смешивать нельзя: у проекта один источник правды.

Главное, что делает этот скилл: **папка проекта должна резолвиться в свой воркспейс**. Пока
она не привязана, jwu отдаёт данные другого контура — и записи о работе уедут не туда.

## Когда обязателен

- Собираешься логировать работу (`jwu job …`) в папке, которая ещё не привязана.
- `jwu workspace current` показывает не тот контур либо ругается «не понял, в каком воркспейсе».
- Новый репозиторий/проект, который хочется вести в jwu.

## Шаги

1. **Проверь, подключено ли уже.** Это первый и самый важный шаг:

   ```bash
   jwu workspace current --json     # что резолвится ЗДЕСЬ и почему (source)
   ```

   `source: cwd` — папка привязана, всё хорошо, **ничего создавать не надо**.
   `source: active | only` — резолв случайный (последний выбранный / единственный контур),
   папка НЕ привязана: продолжай со шага 2.
   Ошибка «не понял, в каком воркспейсе» — тоже шаг 2.

2. **Посмотри предложение jwu** (ничего не меняет):

   ```bash
   jwu init --json          # MCP: jwu_workspace_suggest()
   ```

   Вернёт: `already_initialized` (тогда стоп — проект уже подключён), либо
   `reason: confirm_required` с предложением — какой slug, какие репозитории найдены,
   какие теги предлагаются, и список **уже существующих воркспейсов**.

3. **Спроси пользователя** — это решение его, не угадывай:
   - завести **новый** контур для проекта (обычно так для личного/отдельного проекта);
   - либо **привязать папку к существующему** (если это ещё один репозиторий того же проекта).

4. **Примени:**

   ```bash
   jwu init --yes                        # создать контур по предложению
   jwu init --yes --slug dndeck --name "DnDeck"
   jwu init --attach work                # привязать папку к существующему контуру
   ```

   Провайдер по умолчанию `local`: личному проекту внешний трекер не нужен. Иначе —
   `jwu init --yes --provider github` (или `--provider jira --bitbucket`), потом
   `jwu configure -W <slug>`. Сменить позже: `jwu workspace provider github`.

5. **Расставь теги**, если репозиториев несколько — это ответ на «где что лежит»:

   ```bash
   jwu workspace add-path ~/dev/backend-v2 --tag новая-версия
   jwu workspace tag ~/dev/backend --add legacy-бэкенд --add django
   jwu workspace paths                       # проверить: все папки с тегами
   ```

   Предложи теги **сразу**, когда папок больше одной, — потом никто не вспомнит, что где.

6. **Убедись, что теперь резолвится правильно:**

   ```bash
   jwu workspace current      # source должен стать cwd
   ```

## Зачем это агенту

Папки воркспейса — ответ на вопрос «где лежит код проекта». Любой jwu-скилл сначала
спрашивает `jwu_workspace_current()` и `jwu_workspace_paths()` и работает только в этих
папках. Без привязки агент будет искать по всему диску и писать записи в чужой контур.

## Чего не делать

- **Не создавай второй воркспейс, если папка уже резолвится** (`source: cwd`). `jwu init`
  сам это проверяет и просто подтверждает подключение — но и ты не обходи проверку.
- Не подключай Jira/Bitbucket «на всякий случай»: без них контур работает сразу и не просит кредов.
- Не переноси чужую папку между контурами без спроса (`remove-path` + `add-path`).
- Не печатай значения секретов (`jwu workspace show --show-secrets`) без явной просьбы.

## Если сервер MCP старый

Инструменты `jwu_workspace_*` появились вместе с воркспейсами. Если их нет в списке
инструментов или `jwu_workspace_current()` не отвечает — MCP-сервер запущен со старым кодом
(живёт процессом). Скажи пользователю перезапустить сессию; до этого пользуйся bash `jwu …`,
он всегда актуален.

## После подключения — заведи правила

Подключённый контур знает, ГДЕ лежит код, но не знает, КАК с ним работают. Предложи
записать стартовые правила (`jwu_rule_add` / `jwu rule add "…" --kind …`) — по одному
вопросу за раз, не анкетой:

- что здесь **нельзя** делать (`constraint`) — «не пушить в develop», «не править миграции руками»;
- как **поднять стенд и прогнать тесты** (`howto`) — многострочную инструкцию удобно
  завести через `jwu rule add "Как поднять стенд" --kind howto --file -`;
- что где лежит и кто за что отвечает (`info`), как принято называть ветки и коммиты
  (`convention`).

Если у репозитория есть тег — привяжи правило к нему (`--tag`), чтобы оно не мешалось
в других проектах контура. Пользователь не хочет сейчас — не настаивай: это можно сделать
позже (`jwu rules`, вкладка «Правила» в дашборде).

## Что дальше

- Личный контур: `jwu feature add "…"` — ключи (`DNDECK-1`) годятся как префикс ветки
  и коммита; работу начинай через **jwu-start-job**.
- Рабочий: **jwu-start-job** → **jwu-track-job** → **jwu-job-review**.

## Связанные скиллы

**jwu-start-job** — начать работу в контуре. **jwu-track-job** — вести её лог.
