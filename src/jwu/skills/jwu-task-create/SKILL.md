# jwu: завести задачу в Jira

> **Воркспейс = где лежит код.** jwu работает в контексте *воркспейса*: он определяется
> автоматически по текущей папке, проверить — `jwu_workspace_current()`
> (bash: `jwu workspace current --json`). Папки проекта и их теги приходят там же
> (`paths`, `known_tags`), правила контура — текстом в `rules_md`.
> **Записи `⛔ ЗАПРЕТ` обязательны к исполнению**: если правило запрещает заводить
> задачи в каком-то проекте или требует формата — оно главнее этого скилла.
>
> **Провайдер контура** (`provider`): создание задач сделано для `jira`. При `github`
> и `local` инструмент честно откажет — не пытайся обойти.

## Главное правило

**Задача не создаётся без явного «да» пользователя.** Это запись во внешнюю систему:
задачу увидит команда, а в SDESK — клиент. Отменить создание через API нельзя.

Порядок трёхшаговый, нарушать нельзя:

1. **Собрать** текст задачи.
2. **Показать** пользователю целиком — summary, описание, проект, тип, все поля.
3. **Дождаться подтверждения** и только потом создать.

«Заведи задачу» — это ещё **не** подтверждение payload: пользователь не видел, что ты
собрал. Подтверждение — «да» уже **после** показа текста.

## Инструменты

**MCP-first**: `jwu_issue_create`, `jwu_issue_link`; читающие (зови свободно) —
`jwu_issue_create_meta`, `jwu_issue_similar`.
Bash: `jwu issue create|link|link-types|similar`.

У `jwu_issue_create` есть `dry_run`, и **по умолчанию он `True`** — вызов ничего не пишет,
а возвращает готовый payload (`fields`), результат проверки по `createmeta` (`check`)
и похожие задачи (`similar`). Реальное создание — отдельный вызов с `dry_run=False`,
допустимый **только** после «да».

В bash то же даёт `--dry-run` (подтверждения не требует), а создание требует `--yes`;
без него команда с `--json` вернёт `{"ok": false, "reason": "confirm_required", …}`
и ничего не отправит.

## Алгоритм

1. **Проект и тип.** Ключ проекта спроси, если он не назван явно — не угадывай.
   Проект незнакомый → `jwu_issue_create_meta(project)`: доступные типы и обязательные
   поля. У разных проектов они разные, вслепую задача просто не создастся.
2. **Собери описание.** Источники — разбор в текущей работе (`jwu_job_show`), тред
   дежурства, диалог. Пиши по-русски, **wiki-разметкой Jira Server** (не Markdown,
   не ADF): `{code}…{code}` для кода и логов, `*жирный*`, `# ` для нумерованного списка.
   Структура типового баг-репорта: что происходит → как воспроизвести → что ожидалось →
   что видим → окружение/версия → ссылки на логи, PR, соседние задачи.
3. **Dry-run.** `jwu_issue_create(project=…, summary=…, description=…, dry_run=True)`.
   - `check.problems` не пуст — правь поля и повтори; там написано, какого поля
     не хватает и какие значения допустимы.
   - `similar` не пуст — это похожие задачи проекта за год. **Покажи их пользователю
     и спроси, заводить ли новую**: разбираемый баг вполне может оказаться копией
     задачи годичной давности по другому аккаунту.
4. **Покажи пользователю** итоговый текст целиком (не пересказ!) и спроси: создавать ли,
   в этот ли проект.
5. **Создай** — тот же вызов с `dry_run=False`. Верни ключ и ссылку из `issue`.
6. **Связи.** Задачи почти всегда заводятся со связями на соседние. Предложи связать:
   `jwu_issue_link(inward=<новая>, outward=<соседняя>, link_type="Relates")`. Имена типов
   зависят от инстанса — бери из `jwu issue link-types` (например, «Related», а не
   «Relates»). Задачи разных инстансов (Jira ↔ SDESK) связать нельзя.
7. **Запиши в работу**, если она есть: `jwu_job_add(job_id, "Заведена <KEY>: <summary>",
   kind="phase")`.

## Описание из работы jwu

Если задача заводится по итогам работы, описание не надо писать с нуля:
`jwu_issue_create(..., from_job=<id>)` (bash: `--from-job <ID>`) собирает черновик из
её лога — фазы, найденные баги, ревью, прогоны тестов. Это **черновик**: покажи его
пользователю и правь по замечаниям. Со своим `description` не сочетается.

## SDESK — отдельная осторожность

Задачи с ключом SDESK живут в клиентском инстансе: то, что там написано, **читает
клиент**. Перед созданием скажи об этом явно и покажи текст дословно.

## Правка задачи (без удаления)

- Поля: заголовок, описание (wiki), исполнитель (логин; снять — пусто), приоритет, метки
  (список целиком). Текущие значения — `jwu_task(KEY)`.
- Покажи «было → стало» по каждому полю → «да» → `jwu_issue_update(key, summary=…,
  description=…, assignee=…, priority=…, labels=[…])` (bash: `jwu issue edit KEY --summary …
  --description-file f.md --yes`).
- **Удалять задачи jwu не умеет и не будет** — просят удалить: предложи закрыть переходом
  (скилл jwu-task-status) или сделать в вебе.

## Текст от имени пользователя (голос)

Итоговую формулировку любого текста, который уйдёт наружу от имени пользователя или
отдаётся ему «для копирования», пишет **агент голоса**, а не этот скилл:

1. Собери **факты** — что сказать (сценарий → следствие → просьба; или что сделано),
   на что отвечаем (цитата), нужные имена из кода. Формулировать не надо.
2. `jwu_voice_profile()` → поле `agent` (дефолт `voice-writer-sample`, проектный задаётся
   `jwu voice agent <имя>`). Запусти его через Agent (`subagent_type` = `agent`) и передай
   `channel`, `audience`, `facts`, `context`, `limits`. Агент только пишет, наружу ничего не шлёт.
3. Покажи пользователю текст целиком (и «что я предположил», если не пусто) → правки →
   явное «да» → отправка этим скиллом.
4. «Не похоже на меня» — запусти агента ещё раз с `recheck` (прежний текст в `previous`,
   слова пользователя в `remark`): он сверит черновик с реальными текстами из корпуса и
   перепишет. Предложит правило для профиля — покажи его пользователю.
5. Пользователь поправил или отклонил текст — спроси одной строкой «Записать правку в
   профиль голоса?»; «да» → `jwu_voice_feedback(channel, verdict, before, after, reason)`.

Канал: `task` (заголовок и описание задачи); аудитория — кто задачу будет делать или читать (`colleague`, `analyst`, `qa`).

## Чего делать НЕ надо

- Создавать задачу «на всякий случай», чтобы показать результат.
- Звать `dry_run=False` сразу, без показанного пользователю payload.
- Придумывать значения обязательных полей — спроси или возьми из `createmeta`.
- Править описания и удалять задачи: jwu этого не умеет намеренно.
- Ставить в описание упоминания AI-ассистента и любую атрибуцию.

## Частые ошибки

| Ошибка | Правильно |
|---|---|
| Создали задачу сразу после «заведи задачу» | Сначала dry-run и показ текста, потом «да» |
| Описание Markdown-разметкой | Wiki-разметка Jira Server: `{code}`, `*жирный*` |
| Угадали ключ проекта по названию папки | Спросить пользователя |
| Получили 400 и пересказали своими словами | Показать `check.problems` / текст ошибки дословно |
| Завели дубль годичной давности | Посмотреть `similar` из dry-run и показать пользователю |

## Связанные скиллы

- **jwu-task-comment** — комментарий в задачу (в SDESK его читает клиент).
- **jwu-task-status** — перевести задачу по процессу.
- **jwu-task-attach** — приложить к задаче har, скриншот, выгрузку.
- **jwu-task-branches** — в какие релизные ветки доехал фикс задачи.
