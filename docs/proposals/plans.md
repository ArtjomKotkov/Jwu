# План работы — предложение

Черновик задачи для jwu — по итогам одного длинного дня в стороннем проекте: крупная переделка, около 15 агентов,
два плана в markdown-файлах, десятки решений владельца в чате.

> **Статус:** этап 1 сделан в jwu 3.3.0 (план, шаги, зависимости и ожидания, доказательства с проверкой ссылок,
> остаток, журнал событий, связь шагов с работами, `jwu_plan*`, `jwu plan …`). Пользоваться — [docs/plans.md](../plans.md).

## Что болело

- **План жил в трёх местах**: два markdown-файла с планами и голова сессии. Владелец трижды спрашивал «чо там», «какой план»,
  «сколько осталось» и каждый раз получал пересказ, а не состояние.
- **«Готово» на слово.** Агент «вернул показ» — на деле 17 пунктов из 41, остальное выписал. Сессия передала
  «готово» дальше. Проверить было нечем: у шага не было поля «чем проверено».
- **Порядок держался в голове.** Серверную часть фичи влили раньше фронта, и полчаса из интерфейса нельзя было
  сохранить запись. Зависимость «4в после 4б» была написана в таблице, но ничто её не проверило.
- **Решения тонули в чате.** «это — отдельная запись, а не настройка», «чужие данные не трогать», «формула считается при выполнении
  ноды». Каждое пришлось вручную пересылать работающим агентам и раскладывать по файлам памяти.
- **Вопросы к владельцу терялись в длинных ответах.** Владелец: «ничего не понял, если есть вопросы — спроси
  интерактивно».
- **Что где лежит**: в ветке, на стенде, только в рабочей копии агента — восстанавливалось по `git log` и памяти
  сессии.

Очередь задач сессии была плоским списком дел без связей (в 3.3.0 убрана — не использовалась). Работа (`job`) — журнал одной задачи. Фича (`feature`) — якорь.
Ни одна из них не отвечает на вопросы «что дальше, что ждёт меня, что уже на стенде, чем это проверено».

## Что предлагаю

Новая сущность — **план** (`plan`) воркспейса: дерево шагов с состояниями, зависимостями, доказательствами и
решениями. Работа и фича остаются как есть. План их связывает.

### Модель

```
Plan
  id, workspace_id, key (PLAN-3), title, goal          # цель одной фразой: «вся механика — через новый движок»
  status: active | paused | done | dropped
  priority: int; focus: bool                            # план в фокусе: прочие планы ждут разрешения владельца
  rules: [str]                                          # правила владельца для всех шагов («агенты на самой сильной модели», «без rm -rf»)
  created_at, updated_at

PlanStep
  id, plan_id, key (3, 4а, 4б), title, detail           # detail — что сделать, самодостаточно для агента
  parent_id                                             # подшаги
  status: todo | doing | review | done | waiting_owner | blocked | dropped
  after: [step_id]                                      # зависимости: не начинать, пока они не done
  waits: [Wait]                                         # чего ждёт, кроме шагов: вопрос, владелец, внешнее, ресурс
                                                        #   (см. «Блокировки»); blocked вычисляется из after + waits
  together_with: [step_id]                              # вливать только вместе (сервер и фронт одной правки)
  executor: main | agent:<id> | owner                   # кто делает
  model: opus | sonnet | ...                            # модель агента, если правило плана задаёт
  est, spent                                            # оценка и сколько ушло (часы или токены)
  evidence: [Evidence]                                  # без него в done не перевести
  links: job_id, worktree, commits[], migrations[], issue, files[]
  where: none | branch | main | stand | prod            # куда дошло
  leftovers: [str]                                      # «не сделано» агента; при done — обязательно пусто
                                                        #   или каждый пункт превращён в новый шаг
  created_at, started_at, finished_at

Evidence
  kind: tests | build | stand | browser | screenshot | review | owner
  text                                                  # «go test ./... ok», «снимок экрана: …/screen-1.png»
  ref                                                   # путь, коммит, ссылка
  at, by

Decision
  id, plan_id, step_id?, text, quote                    # quote — слова владельца как есть
  scope: step | plan | workspace                        # workspace — тогда предложить записать правилом
  at, supersedes: decision_id?                          # отмена прежнего решения — явной ссылкой

Question
  id, plan_id, step_id?, text, options[{label, detail, recommended}]
  status: open | answered | dropped
  answer, answered_at
  blocks: [step_id]                                     # шаги, которые стоят, пока нет ответа
```

### Правила, которые jwu держит сам

1. **Нет `done` без доказательства.** `jwu_plan_step(..., status="done")` без `evidence` — отказ. Для шагов с кодом
   нужно минимум `tests` или `build`. Для шагов с интерфейсом — ещё `browser` или `screenshot`. Набор настраивается
   в правилах плана.
2. **Нет `done` с остатком.** Непустой `leftovers` — отказ, пока каждый пункт не стал новым шагом или вопросом
   владельцу. Агент не может «выписать и не сделать» молча.
3. **Зависимости.** Шаг нельзя перевести в `doing`, пока не `done` всё из `after`. Шаги из `together_with`
   переходят в `where=main` только вместе: jwu не даст закоммитить в основную ветку один без другого (через
   `jwu_git_commit`, проверкой по `links.files`).
4. **Вопрос стопорит.** Пока у шага открыт вопрос — шаг в `waiting_owner`, и его нельзя взять.
5. **Решение рассылается.** Новое решение с `scope=plan` попадает в `detail` всех шагов в `todo` и `doing`. Строка
   «решения с прошлого раза» приходит работающим агентам, когда они читают свой шаг (`jwu_plan_step_get`).
6. **«Где лежит» обновляется само**: коммит в main по файлам шага — `main`; накат на стенд по правилу воркспейса —
   `stand`.

### Блокировки — шаг знает, чего ждёт

Состояние «заблокирован» jwu вычисляет сам, руками его не ставят. У каждого шага есть список того, чего он ждёт
(`waits`), и каждый пункт списка — ссылка, а не текст:

| Чего ждёт | Пример | Когда снимается |
|---|---|---|
| другой шаг (`after`) | «4в ждёт 4б» | шаг-причина перешёл в `done` |
| пару (`together_with`) | «сервер фичи ждёт фронт фичи, чтобы влиться вместе» | обе части готовы к слиянию |
| вопрос владельцу | «ждёт ответа: отдельной записью или настройкой?» | на вопрос ответили |
| владельца-исполнителя | «данные владелец переносит сам» | владелец отметил шаг |
| внешнее | «ждёт отчёт агента», «ждёт CI», «ждёт свободный стенд / разрешение войти под тестовым пользователем» | событие пришло (уведомление агента, сборка, ответ) |
| ресурс | «ждёт, пока владелец не работает в приложении» (вход под тестовым пользователем закрывает его сессию) | владелец сказал «можно» |

Что из этого следует:

- **Вид «кто кого держит»**: `jwu_plan(key, view="blocks")` — дерево причин: что стоит, из-за чего, и что
  освободится, если закрыть одну причину. Наверху — причины, которые держат больше всего шагов (критический путь).
- **Снятие само.** Шаг-причина закрылся — зависимые шаги переходят в `todo`, и сессия получает уведомление
  «освободилось: 4в, 6». Агента запускать не надо — `jwu_plan_next` отдаёт их первыми.
- **Цикл — отказ.** `after`, который замыкает круг, jwu не принимает.
- **Закрытие причины.** Шаг-причина `dropped` — зависимые не освобождаются молча: jwu спрашивает, снять зависимость
  или снять и их.
- **Обратная проверка.** Нельзя откатить причину из `done` (вернули на доработку), пока зависимые в `doing`: jwu
  предупреждает, какие шаги строились на ней.
- **«Чо там» отвечает и про ожидания**: `jwu_plan_now` показывает не только «идёт» и «следующее», но и «стоит —
  ждёт <что>», и первым — то, что ждёт владельца.

### Несколько планов сразу

В воркспейсе живут несколько планов одновременно: «новый движок», «общие действия», «перенос данных»,
«CI/CD». Отсюда:

- **Связи между планами.** Шаг одного плана может ждать шаг другого (`after: PLAN-2/5`) — те же блокировки, через
  границу плана. Пример: «перенос данных» ждёт «движок: экран на фронте».
- **Приоритет плана** (`priority`) и правило владельца «пока не закончен PLAN-3 — другие не брать» (`focus`): тогда
  `jwu_plan_next` по прочим планам отдаёт только то, что владелец явно разрешил. Это ровно сегодняшнее «фигли ты
  переключаешься, пока мы с движком не закончили».
- **Общий учёт ресурсов.** Слоты агентов, стенд, вход под тестовым пользователем — общие на воркспейс. `jwu_plan_next` раздаёт слоты по
  всем активным планам с учётом приоритета, а не каждому плану отдельно, и не пускает два шага разных планов на одни
  и те же файлы.
- **Сводка по всем.** `jwu_plan_now()` без ключа — все активные планы: по строке на план (сколько сделано, что идёт,
  что ждёт владельца), сверху — вопросы владельцу из всех планов разом. Строка состояния показывает план в фокусе и
  число вопросов по всем.
- **Шаг в одном плане.** Шаг принадлежит одному плану; если работа нужна двум — второй ждёт его ссылкой, без копии.
- **Перенос.** Шаг или ветку шагов можно перенести в другой план (`jwu_plan_step(step, plan=…)`), решения и
  доказательства едут с ними.
- **Решения уровня воркспейса** (`scope=workspace`) действуют на все планы.

### Команды (MCP-first)

| Инструмент | Что делает |
|---|---|
| `jwu_plan_create(title, goal, rules)` | новый план |
| `jwu_plan(key?)` | план целиком: дерево шагов, открытые вопросы, решения; поле `markdown` — готовая сводка |
| `jwu_plan_now(key?)` | коротко: что идёт, что ждёт владельца, что следующее и что можно запускать параллельно. Ответ на «чо там» |
| `jwu_plan_step_add(plan, title, detail, after, together_with, executor, est)` | шаг |
| `jwu_plan_step(step, status?, evidence?, links?, leftovers?, where?)` | правка шага с проверками из правил выше |
| `jwu_plan_step_get(step)` | шаг для агента: `detail` + правила плана + решения + что сделано в зависимостях |
| `jwu_plan_next(plan, slots)` | какие шаги можно брать сейчас (зависимости закрыты, нет открытых вопросов, файлы не пересекаются с идущими) |
| `jwu_plan_decide(plan, text, quote, scope, step?)` | записать решение владельца |
| `jwu_plan_ask(plan, text, options, blocks)` | вопрос владельцу; сессия тут же показывает его меню AskUserQuestion |
| `jwu_plan_answer(question, answer)` | ответ: снимает `waiting_owner`, ответ ложится решением |

Bash-фолбэк: `jwu plan [list|show|now|add|step|decide|ask|answer]`, у всех `--json`.

### Как видно человеку

- **Строка состояния**: `PLAN-3 · 9/12 · идёт: уборка · ждёт вас: 1 вопрос`.
- **Страница плана** на дашборде jwu (рядом с `dashboard-jobs`): дерево шагов цветом состояния, у каждого — где
  лежит и чем проверено, вверху открытые вопросы кнопками. Открывается с телефона: владелец работает через remote.
- **Уведомление** (Telegram, как у демона) — когда появился вопрос и когда шаг перешёл в `done`, с доказательством.

### Как этим пользуются сессия и агенты

- Скилл `jwu-plan`: «составь план», «что по плану», «что дальше». Сессия ведёт план, агентам отдаёт шаг
  (`jwu_plan_step_get`) вместо самодельного промпта. Агент пишет в шаг доказательства и остаток, а не только
  финальный отчёт в чат.
- `jwu-session-init` показывает активный план одной строкой из `jwu_plan_now`.
- Решение со `scope=workspace` jwu предлагает записать правилом воркспейса (`jwu_rule_add`), а не только в память
  сессии.

## С чего начать

1. Модель и хранение (`Plan`, `PlanStep`, `Evidence`, `Decision`, `Question`) + `jwu_plan`, `jwu_plan_now`,
   `jwu_plan_step(_add)`. Правило 1 (нет `done` без доказательства) и правило 3 (зависимости).
2. Вопросы и решения (`ask`/`answer`/`decide`), стопор шага, рассылка решений.
3. Строка состояния и страница на дашборде.
4. `together_with` в `jwu_git_commit`, авто-`where`, уведомления, скилл `jwu-plan`.

Первый этап уже закрыл бы три из шести болей дня: «чо там», «готово на слово» и порядок.
